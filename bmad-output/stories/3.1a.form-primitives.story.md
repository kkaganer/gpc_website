# 3.1a: Form primitives — core inputs, tokens and the shared live region

**Story ID:** 3.1a
**Epic:** 3 — The public form
**Slug:** form-primitives
**Status:** ready-for-dev

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.
> **Split notice:** this story was split from the single assigned story 3.1 (`form-primitives`)
> because building all of the accessible-primitive surface in one sitting exceeds the one-dev-day
> bound. This half (3.1a) ships the core input, token and announcement primitives every other
> Epic 3 story needs first. The choice-control primitives (`RadioGroup`, `Checkbox`,
> `ChoiceChipGroup`, `CharacterCounter`) ship in **3.1b**, which depends on this story only for
> `src/index.css` tokens (no code dependency).

## Story

As a **developer building any `/join` form section**,
I want **a shared set of accessible text-input primitives, the corrected design tokens, and the
page's single `aria-live` announcement channel**,
so that **every subsequent Epic 3 story composes from the same accessible, WCAG-compliant
building blocks instead of hand-rolling label/input pairing again**.

## Acceptance Criteria

<!-- LOCKED. External dev tools must not edit Acceptance Criteria. -->

1. `src/index.css`'s `@theme` block gains the corrected/added tokens from DESIGN.md §1 —
   `--color-primary-700` (`#c9107f`), the full primary ramp, semantic colours (`--color-success`,
   `--color-warning`, `--color-error`, `--color-info`) with their tints, `--color-border`
   (`#6b7280`), `--color-divider`, `--color-text-muted` — without removing or renaming any
   existing token (`--color-primary`, `--color-dark`, `--color-warm`, `--color-amber`,
   `--font-heading`, `--font-body`) that other pages already reference.
2. `Button.jsx` supports a `size` prop (`sm` in addition to the existing default), a `loading`
   prop that shows the shared spinner glyph in place of the label's leading edge and sets
   `aria-busy="true"` plus `aria-disabled="true"` (never the native `disabled` attribute), and a
   `disabled` visual state that stays focusable. Existing callers of `Button` (with no new props)
   render unchanged.
3. A new `FormField` component renders a single-line text input, a `textarea`, or a `select`
   (via a `type`/`as` prop) with a generated `id`, a `<label htmlFor>` pointing at it, help text
   rendered **above** the input, and — when an `error` prop is passed — an error message below
   the input tied to the input via `aria-describedby` and `aria-invalid="true"` on the input.
4. Given no `error` prop is passed to `FormField`, when it renders, then no error text, no
   `aria-invalid`, and no error-only `aria-describedby` id is present in the DOM.
5. A new shared `LiveRegion` component plus a `useLiveRegion()` hook exposes one `announce(text)`
   function; calling it updates the text content of exactly one `aria-live="polite"` DOM node
   that a consuming page mounts once. No component created by this story creates a second
   `aria-live` region.
6. A new `Banner` component renders the four DESIGN.md §2.10 variants (`error`, `success`,
   `warning`, `info`) with the correct semantic colour pair, an icon, and `role="alert"` only on
   the `error` variant (`success`/`warning` get `role="status"`; `info` gets no role).

## Dev Notes

<!-- LOCKED. Concrete guidance compiled from the planning docs WITH SOURCE CITATIONS. -->

- **Why this exists at all:** the site has no `id`/`htmlFor` pairing anywhere today, no
  `focus-visible` styling, and `prefers-reduced-motion` is honoured nowhere — this is the
  "single largest departure from existing patterns" the feature makes.
  [Source: EXPERIENCE.md#dev-handoff-notes — "Non-negotiables"]
- **Token corrections are load-bearing, not cosmetic.** White text on the current
  `--color-primary` `#fc16a0` measures **3.64:1** and fails WCAG AA (needs 4.5:1); the new
  `--color-primary-700` `#c9107f` measures **5.43:1** on white / **5.24:1** on the warm
  background and must carry all primary-button and link text. `--color-border` `#6b7280`
  (4.83:1) replaces `#d1d5db` (1.47:1), which fails the 3:1 non-text contrast rule for input
  borders (WCAG 1.4.11). `--color-amber` `#f59e0b` (2.15:1) is not used for text or UI anywhere
  in this feature. [Source: DESIGN.md#1.1-color-palette] [Source: DESIGN.md#0-scope-and-posture]
- **Do not touch existing token names** (`--color-primary`, `--color-dark`, `--color-warm`,
  `--color-amber`, `--font-heading`, `--font-body`) — they are consumed across the rest of the
  site via Tailwind's generated utilities and via `src/utils/constants.js`'s `BRAND` object;
  renaming breaks unrelated pages. [Source: inputs/codebase-constraints-brief.md#5]
- **Button today:** `{ variant = 'primary'|'secondary'|'outline', children, className, href,
  ...rest }`, polymorphic (`href` starting `http` → new-tab `<a>`; other `href` → `<Link>`; none
  → `<button>`), fixed `px-6 py-3`, **no size variant, no disabled styling, no loading state**.
  [Source: inputs/codebase-constraints-brief.md#4]
- **Button target spec:** height 48px mobile/tablet, 44px desktop; radius `--radius-full`;
  min-width 120px; loading state replaces the label's leading edge with a spinner and the label
  becomes the progress verb (e.g. "Sending…"), `aria-busy="true"`; disabled uses
  `aria-disabled="true"` and **stays focusable** so an AT user can discover why — the native
  `disabled` attribute hides the reason and must not be used.
  [Source: DESIGN.md#2.1-button-primary]
- **`FormField`'s anatomy, top to bottom:** Label (with a `*` in `--color-primary-700` when
  required) → help text (14px, `--color-text-muted`, **always above the input**, never below —
  below-input helper is covered by the on-screen keyboard on a phone at exactly the moment it's
  needed) → the 48px/16px input → error message (14px, `--color-error`, icon + text).
  [Source: DESIGN.md#2.4-text-input-textarea-select]
- **Accessibility contract for `FormField`:** every input gets an `id`; the `<label>` uses a
  matching `htmlFor`; help and error text are referenced by `aria-describedby` on the input;
  `aria-invalid="true"` only when in error. **Field-level error text is `aria-describedby` text
  with `aria-invalid`, not its own `role="alert"` region** — DESIGN.md §2.4 says error containers
  "carry `role=alert`", but the adjudicated ruling overrides this: only the page's single error
  summary is `role="alert"` (A13); per-field messages must not duplicate it, or a failed submit
  announces every error twice. [Source: DESIGN.md#2.4-text-input-textarea-select]
  [Source: EXPERIENCE.md#1-joining--the-public-form — "D7 — one polite region, one alert region"]
  [Source: ux-drafts/ADJUDICATIONS.md#a13-one-live-region-per-page]
- **`FormField` needs an `autocomplete` prop** — the feature requires `given-name`, `email`,
  `postal-code`, `url`, `organization` set per field (WCAG 1.3.5).
  [Source: DESIGN.md#2.4-text-input-textarea-select]
- **Input text is 16px minimum, non-negotiable** — anything smaller triggers iOS Safari's
  auto-zoom on focus, breaking the layout mid-form. [Source: DESIGN.md#1.2-typography]
- **Validation timing is not this story's job** but `FormField` must not preclude it: validation
  runs on blur, and re-validation after an error may run on change — this story only needs to
  accept and render an externally-computed `error` string; the on-blur wiring belongs to the
  section components that consume `FormField` (3.3, 3.4, 3.5) and the summary orchestration in
  3.7. [Source: DESIGN.md#2.4-text-input-textarea-select]
- **One live region, one alert region, per page** — the `LengthSignal` (3.2), branch-change
  announcements (3.3), the day/time matrix count (3.4), the character counter (3.1b/3.5), and
  loading/sending states all write into the **same** throttled `aria-live="polite"` node this
  story creates. Four simultaneous regions on `/join` would produce interleaved, unintelligible
  speech — this is why `useLiveRegion()` is a single shared hook, not a pattern each section
  reinvents. [Source: EXPERIENCE.md#1-joining--the-public-form — "D7"]
  [Source: ux-drafts/ADJUDICATIONS.md#a13-one-live-region-per-page]
- **`Banner` variants and roles**, verbatim: Error — `--color-error` on `#fee2e2`,
  `role="alert"`; Success — `--color-success` on `#dcfce7`, `role="status"`; Warning —
  `--color-warning` on `#fef3c7`, `role="status"`; Info — `--color-info` on `#dbeafe`, no role
  (static content). Structure: icon → title (16px/600) → body (16px) → optional action button.
  [Source: DESIGN.md#2.10-inline-banner]
- **No global toaster exists or is added** — `Banner` is always rendered inline, adjacent to what
  it describes; there is no `<Toaster>` provider in this feature.
  [Source: ux-drafts/ADJUDICATIONS.md#a6-no-global-toaster]
- **`prefers-reduced-motion` reset is global CSS**, not a per-component concern of this story —
  it is out of this story's scope but this story's components must not introduce any animation
  that isn't already covered by a global reset (no per-component transition that ignores the
  media query). [Source: ux-drafts/ADJUDICATIONS.md#a20-prefers-reduced-motion-is-reset-globally]
- **No new runtime dependency.** All of the above is hand-rolled JSX/CSS — no form library, no
  headless-UI package. [Source: architecture.md#adr-007-client-state] [Source: prd.md#NFR-012]
- **Naming:** `PascalCase.jsx` components in `src/components/ui/`; hooks `useThing.js` in
  `src/hooks/`. [Source: architecture.md#adr-006-naming-conventions]

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify per AC, test types, fixtures, edge cases. -->

- **Approach:** component-level tests (React Testing Library idiom, matching existing test setup
  if any exists) plus a manual keyboard/AT smoke pass, since this story's output is entirely
  presentational infrastructure with no server dependency.
- **Key scenarios:** `Button` renders each `size`/`loading`/`disabled` combination with correct
  ARIA attributes and remains a real `<button>`/`<a>`, never a `<div>`; `FormField` associates
  `label`↔`id` and toggles `aria-describedby`/`aria-invalid` correctly with and without an
  `error` prop; `LiveRegion` updates the same DOM node's text on repeated `announce()` calls
  rather than creating new nodes; `Banner` renders the correct `role` per variant.
- **Per-AC verification:** AC #1 → grep `src/index.css` for each named token and confirm no
  existing token line was deleted or renamed; AC #2 → render `Button` with `loading` and assert
  `aria-busy`/`aria-disabled` and that the spinner is `aria-hidden`; AC #3/#4 → render `FormField`
  with and without `error` and assert the DOM diff is exactly the error paragraph +
  `aria-describedby`/`aria-invalid`; AC #5 → call `announce()` twice and assert the DOM still has
  exactly one node with `aria-live="polite"`; AC #6 → snapshot each `Banner` variant's `role`
  attribute against the table above.
- **Fixtures / mocks:** none — no network or Supabase dependency in this story.
- **Edge cases to cover:** `Button` with both `href` and `loading` (should not happen but must
  not crash); `FormField` with `type="select"` and an empty `options` array (renders, does not
  throw); a `mailto:` `href` on `Button` renders `<a href="mailto:...">`, not a router `<Link>`
  (the known existing bug this feature must not inherit — verify in the manual pass since it's
  easy to miss in a unit test that stubs the router).
