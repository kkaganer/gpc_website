# 4.4: Duplicate and idempotency handling

**Story ID:** 4.4
**Epic:** 4 — Submission pipeline
**Slug:** duplicate-and-idempotency
**Status:** ready-for-dev

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As **a member**,
I want **resubmitting the join form — whether a genuine retry or a second submission with my existing email — to update my existing record instead of creating a duplicate**,
so that **I never end up as two people in GPC's member list, a retried request never doubles my data, and I don't silently overwrite my live listing**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. Given a submission arrives whose `idempotency_key` already exists on a `member_submissions` row (e.g. a client retry after a timeout), when `submit_membership()` runs, then no new `members`, `member_submissions`, `member_consents`, or `directory_listings` row is created, and the endpoint returns the same `200 { ok: true }` shape as the original request.
2. Given a submission arrives for an email that already exists in `members`, with a **new** `idempotency_key` (a genuine resubmission, not a retry), when `submit_membership()` runs, then the existing `members` row is updated with the new answers rather than a second `members` row being created, and a new `member_submissions` row is inserted so the submission history is preserved.
3. Given a genuine resubmission (AC #2) completes, when the HTTP response is returned, then it is the identical `200 { ok: true }` shape used for a first-time submission — the response never discloses whether the email was already registered.
4. Given a resubmitting member has no existing `directory_listings` row and opts into the directory on this submission, when the function runs, then a new `directory_listings` row is created in `pending` status, exactly as for a first-time opt-in.
5. Given a resubmitting member already has a `directory_listings` row with `status = 'published'`, and opts into the directory again on this submission, when the function runs, then the existing listing row is updated (`submitted_*` columns set to the new values, `status` set to `'pending'`) rather than a second row being created, and the currently-public columns (the ones granted to `anon`: `business_name`, `description`, `category_id`, `website_url`, `instagram_url`, `enquiry_email`) are left unchanged until an admin approves the resubmission.
6. Given an admin views the member record or the listing after a resubmission, when they inspect it, then they can see that a resubmission occurred and on what date — the `member_submissions` history and the listing's updated `submitted_*`/`updated_at` values make this visible, even though the member-facing HTTP response discloses nothing.

## Dev Notes

<!-- LOCKED. Concrete guidance compiled from the planning docs WITH SOURCE CITATIONS.
     Cite every fact: [Source: prd.md#anchor] / [Source: architecture.md#anchor]. Own inferences: [Inference]. -->

- **Idempotency key, client-side origin.** *"Sends an idempotency key generated once per form session … so a retry after a timeout cannot create a second member."* [Source: architecture.md#component-join-form-public]; EXPERIENCE.md names this **A19**: *"The client generates one idempotency key per form session and sends it with every attempt; retries reuse it."* [Source: EXPERIENCE.md#1-joining--the-public-form]. This story is the **server** half — the client half is Epic 3's concern (already assumed by 4.1/4.2's function/handler signatures, which accept `p_idempotency_key`/`idempotencyKey` but do not yet de-duplicate on it before this story).
- **Column already exists.** `member_submissions.idempotency_key text unique` is created in Epic 1's migration `028`, not by this story [Source: architecture.md#5-data-model]. This story adds the *use* of that uniqueness (an explicit existence check before insert), not the column itself — do not add a second migration touching that column.
- **Email upsert, why it works.** *"`members` … `email` (citext, unique) … Unique email is what makes FR-007 resubmission an upsert."* [Source: architecture.md#5-data-model]. `citext` means the conflict target is case-insensitive by design already — no extra lowercasing needed in SQL, though 4.2's handler should still normalize for consistency in validation error messages [Inference].
- **The resubmission rule, verbatim.** *"Resubmission (FR-007) sets `status = 'pending'` on the existing listing and populates `submitted_*` columns alongside the published ones — it does not create a second listing and does not alter what is currently public."* [Source: architecture.md#adr-012-moderation-is-a-text-status-vocabulary-with-a-reason-not-a-boolean]. The distinction between the "live" columns (`business_name`, `description`, `category_id`, `website_url`, `instagram_url`, `enquiry_email` — the ones granted to `anon` per ADR-001) and the `submitted_*` mirror columns is what makes this safe: only the mirror moves; publication is a separate admin act (Epic 5's `5.3`).
- **Non-disclosure still applies here.** *"Given a duplicate submission, when it completes, then the member sees the ordinary confirmation state — the response never reveals whether the email was already registered."* [Source: prd.md#FR-007]. This story must not add any branch in `api/join/submit.js` that differentiates the HTTP response for a resubmission — the uniform `200 { ok: true }` 4.2 already returns is correct as-is; if anything, this story should confirm no such branch is accidentally introduced.
- **Admin visibility, without breaking non-disclosure.** *"Admins can see that a member re-submitted and on what date."* [Source: prd.md#FR-007]. This is satisfied entirely server-side by the data model itself — a second `member_submissions` row with its own `submitted_at`, and the listing's `submitted_*`/`updated_at` change — no member-facing signal is needed or wanted. The admin-facing rendering of this (a "Resubmission" pill, submitted-vs-published diff) is Epic 5's `5.3`, out of scope here; this story only needs to make the underlying data distinguishable.
- **`create or replace function` gotcha — [Inference].** Postgres preserves a function's existing grants across `create or replace function` **only if the argument list (name + types) is unchanged**; adding a required new parameter without a default, or changing a type, forces an effective drop-and-recreate that can silently lose the `service_role`-only grant `1.1`'s/4.1's lockdown pair established. Prefer reusing 4.1's existing parameters (the idempotency key and consent/listing jsonb blobs are already present) rather than adding new ones; if a new parameter is genuinely unavoidable, give it a `default` and **re-issue the full `revoke`/`grant` pair in this migration regardless**, per ADR-002's rule that "every function gets the lockdown pair in the same migration" — treat that as applying to every migration that replaces the function's body, not only its first creation [Source: architecture.md#adr-002-persistence-conventions].
- **FR/NFR coverage:** FR-007 (all four ACs) [Source: prd.md#FR-007]; NFR-011 (no submission silently lost — an idempotent retry must not silently create a duplicate either, which is the inverse failure mode of the same requirement) [Source: prd.md#NFR-011].
- **Out of scope for this story:** the admin-facing "Resubmission" UI, the submitted-vs-published diff screen, and the pending-count/queue-placement implications of a resubmitted *published* listing reappearing in the queue — all Epic 5 (`5.2`/`5.3`).

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. NEVER run tests or quote coverage here. -->

- **Approach:** integration verification via the Supabase SQL editor / scripted requests against a preview deployment (no unit-test framework exists in this repo [Source: inputs/codebase-constraints-brief.md#1-stack--deployment-reality-non-negotiable]), calling `submit_membership()` directly for the SQL-level cases and hitting `POST /api/join/submit` for the HTTP-response cases.
- **Key scenarios:** (a) send the same full payload twice with the same `idempotency_key` → second call is a no-op, row counts unchanged after the first call; (b) send two payloads for the same email with different `idempotency_key`s and different answers → one `members` row updated, two `member_submissions` rows; (c) resubmission opting into the directory for the first time → one new `directory_listings` row, `pending`; (d) resubmission against an existing `published` listing with changed business details → the same listing row updated, `status` back to `pending`, public-facing columns unchanged, `submitted_*` columns holding the new values; (e) both HTTP responses (first submission and resubmission) compared byte-for-byte to confirm no distinguishing signal.
- **Per-AC verification:** AC #1 → row counts before/after a repeated-idempotency-key call are identical; AC #2 → `members` row count stays at one, `member_submissions` count increments; AC #3 → diff the two HTTP response bodies; AC #4 → new `directory_listings` row appears only when none existed before; AC #5 → published listing's `business_name`/`description`/etc. unchanged in the row while `submitted_business_name`/`status` change; AC #6 → query `member_submissions` for the member and confirm two rows with distinct `submitted_at` values exist, usable by an admin view later.
- **Fixtures/mocks:** a first-submission payload and a second payload for the same throwaway email with different answers and a different `idempotency_key`; a third payload reusing the first payload's exact `idempotency_key` to test the no-op path; a pre-seeded `published` listing (via a direct SQL fixture, not through the public pipeline, since no admin publish flow exists yet in this epic) to exercise AC #5 without depending on Epic 5.
- **Edge cases:** a resubmission that opts *out* of a previously-published listing (member no longer wants a listing) — confirm this story does not silently unpublish anything, since unpublishing is an explicit admin/member-initiated act elsewhere (Epic 5/8), not an automatic side effect of a resubmission; a resubmission arriving for a member whose listing is currently `held` or `rejected` (not `published`) — confirm the same update-in-place rule applies regardless of prior status, since ADR-012 only distinguishes "currently public" (`published`) from everything else for the "does not alter" guarantee.
