# 4.1: Submit membership transaction function

**Story ID:** 4.1
**Epic:** 4 — Submission pipeline
**Slug:** submit-membership-transaction
**Status:** ready-for-dev

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As **the data controller**,
I want **the member, submission, consent and pending-listing rows for a first-time join to be written by one atomic Postgres transaction function**,
so that **no submission is ever partially persisted, and a client cannot author its own consent evidence**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. Given a first-time submission with no directory opt-in (identity fields, `answers`, `hold_data` consent granted, a `newsletter` consent choice), when `submit_membership()` is called, then in one transaction it inserts exactly one `members` row, one `member_submissions` row referencing it, and one `member_consents` row for each of the `hold_data` and `newsletter` purposes (each carrying all six ADR-010 fields), and it creates no `directory_listings` row.
2. Given the same inputs plus `p_wants_listing = true` and valid listing fields (`business_name`, `category_id`, `description`, `enquiry_email` required; `website_url`/`instagram_url` optional) and `publish_listing` consent granted, when the function runs, then it additionally inserts exactly one `directory_listings` row with `status = 'pending'` and its `submitted_*` columns populated from the given values, plus a `member_consents` row for `publish_listing`.
3. Given `p_wants_listing = false`, when the function runs, then no `directory_listings` row is created and no `publish_listing` consent row is created, regardless of what listing-shaped data is supplied in the call.
4. Given the `hold_data` purpose is not granted `true`, when the function is invoked, then it raises an exception and writes nothing to any of the four tables — `hold_data` consent is the precondition for any record existing at all.
5. Given the function is invoked by any Postgres role other than `service_role`, when the call is attempted, then it is refused with a permission error — no `EXECUTE` grant exists for `anon` or `authenticated`.
6. Given any single insert inside the function fails (e.g. a `NOT NULL` violation on a required listing field), when the transaction ends, then no partial row from that call remains in `members`, `member_submissions`, `member_consents`, or `directory_listings`.

## Dev Notes

<!-- LOCKED. Concrete guidance compiled from the planning docs WITH SOURCE CITATIONS.
     Cite every fact: [Source: prd.md#anchor] / [Source: architecture.md#anchor]. Own inferences: [Inference]. -->

- **Migration numbering.** ADR-002 reserves `028`–`031` for Epic 1's four migrations (1.1–1.4) and explicitly excludes this function from Epic 1: *"the `submit_membership()` transaction function (Epic 4, because it encodes submission logic rather than schema)"* [Source: epics.md#epic-1-data-foundation]. No number is reserved for it in the migration sequence table [Source: architecture.md#adr-002-persistence-conventions]. This story uses `032` as the next sequential number. **[Inference] — flag to the orchestrator:** other epics (5's moderation functions, 7's insights aggregation) will also want new migration numbers after `031`; final numbering across epics needs to be confirmed at merge time to avoid a collision like the one `supabase/migrations-archive/` already documents [Source: inputs/codebase-constraints-brief.md#1-stack--deployment-reality-non-negotiable].
- **Function is the one write mechanism, never the browser.** *"Members, submissions, consents and the pending listing are written in one transaction via a single `SECURITY DEFINER` function, so a partial submission is impossible (NFR-011)."* [Source: architecture.md#adr-004-one-trusted-server-write-path-the-browser-never-writes-member-data]. No public `INSERT` policy exists on any of these tables — the function, called only by the service-role client from `POST /api/join/submit` (story 4.2), is the sole path in.
- **Lockdown pattern to copy.** Same shape as `erase_member()`: `SECURITY DEFINER`, "grantable to `service_role` only" and "never granted to `authenticated`" [Source: architecture.md#adr-015-erasure-and-withdrawal-run-through-one-security-definer-function]. Every function gets `revoke execute … from public, anon; grant execute … to <role>;` in the **same migration** it is created in — missing this once let `anon` call `reject_activity` in production [Source: architecture.md#adr-002-persistence-conventions].
- **Table shapes to write against**, all from the data model [Source: architecture.md#5-data-model]:
  - `members`: `id · first_name · email (citext, unique) · postcode · heard_about · group_choice (text + CHECK business_mums|career_mums|both) · erased_at · created_at/updated_at`. This story writes a plain `INSERT` only — duplicate-email handling (upsert) is explicitly out of scope here and is delivered by **4.4**.
  - `member_submissions`: `id · member_id · answers jsonb (ADR-009) · form_config_version text · idempotency_key text unique · submitted_at`. This story writes one row per call; idempotency-key de-duplication is **4.4**'s concern, not this story's.
  - `member_consents`: per ADR-010, one row per consent event, six fields always: `member_id, purpose, granted, consent_text, consent_version, method, captured_at` [Source: architecture.md#adr-010-consent-records-are-append-only-and-version-bearing-enforced-by-trigger]. The table's `before update or delete` trigger makes rows immutable — this function only ever `INSERT`s, never touches an existing row.
  - `directory_listings`: `id · member_id · slug (NOT set here — generated only at first publication, ADR-013, owned by Epic 5) · business_name · category_id · description · website_url · instagram_url · enquiry_email · status default 'pending' · submitted_business_name/submitted_description/submitted_* · published_at · actioned_by/actioned_at`. This story inserts with `status = 'pending'` and populates the `submitted_*` mirror columns from the same values — the "live" public columns and the `submitted_*` columns start out equal and diverge only after an admin edit (Epic 5) [Source: architecture.md#adr-012-moderation-is-a-text-status-vocabulary-with-a-reason-not-a-boolean].
- **Answer shape.** `p_answers` must already be `{key,label}`-shaped per question per ADR-009 — building that shape from the raw request is 4.2's job (using the registry from 2.1); this function stores whatever `jsonb` it is given as-is [Source: architecture.md#adr-009-answers-store-option-keys-and-a-label-snapshot].
- **Consent text/version resolution — [Inference].** Architecture states consent text/version/`captured_at`/`method` are "assigned server-side from the published form config version" [Source: architecture.md#adr-004-one-trusted-server-write-path-the-browser-never-writes-member-data] but does not fix which layer resolves the *text*. This story's function accepts `p_consents jsonb` keyed by purpose (`{"hold_data": {"granted": bool, "text": "…", "version": "…"}, "newsletter": {...}, "publish_listing": {...}}`) — the *text and version* are resolved by the caller (4.2, from the currently published `form_config_versions` row) and passed in, because that lookup already has to happen for the form to render; but `captured_at` and `method` are computed **inside this function**, never trusted from any caller argument, since that is the strongest reading of "assigned server-side" for values that are legal evidence. Document this signature choice in the migration header so 4.2's Dev Notes and this one stay consistent.
- **FR coverage.** FR-004 (evidenced consent, server half) and FR-005 (single trusted write path) [Source: prd.md#FR-004], [Source: prd.md#FR-005]. FR-003's "every listing has the same shape" / "none is stored" when declined [Source: prd.md#FR-003] is enforced structurally by AC #3, not by a later filter.
- **Naming.** `snake_case`, verb-first SQL function name, exactly `submit_membership(...)` as named in ADR-006's naming table [Source: architecture.md#adr-006-naming-conventions].
- **No abuse-layer or email logic here.** Origin/honeypot/rate-limit checks are 4.3's; the outbound-email queue write belongs to Epic 5, not this function [Source: architecture.md#adr-014-outbound-email-is-a-queue-table-drained-by-a-pluggable-sender]. This function's only job is the atomic write of the four tables listed above.

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. NEVER run tests or quote coverage here. -->

- **Approach:** No test runner exists in this codebase [Source: inputs/codebase-constraints-brief.md#1-stack--deployment-reality-non-negotiable] (no vitest/jest in `package.json`). Verify via the Supabase SQL editor / `psql` against a local or preview database, following the header comment's own "commented-out verification query" convention [Source: architecture.md#adr-002-persistence-conventions] — not a new test framework (adding one is a logged-decision-worthy new dependency).
- **Key scenarios:** (a) full happy path with listing opt-in, asserting row counts of 1/1/2/1 across the four tables; (b) happy path without opt-in, asserting 1/1/2/0 and no `publish_listing` consent row; (c) `hold_data` withheld, asserting 0/0/0/0 and an exception; (d) a forced constraint violation (e.g. NULL `business_name` while `p_wants_listing = true`) asserting the whole call rolls back to 0/0/0/0, not a partial 1/1/2/0.
- **Per-AC verification:** AC #1 → row-count query after a no-listing call; AC #2 → row-count + column-value query after a listing call; AC #3 → assert zero `directory_listings` and zero `publish_listing` consent rows when `p_wants_listing = false` even if listing fields are non-null; AC #4 → call with `hold_data.granted = false`, assert exception raised and all four tables unchanged; AC #5 → attempt the call as `anon`/`authenticated` via `set role` and assert `permission denied`; AC #6 → force a constraint violation and assert the transaction leaves no trace.
- **Fixtures/mocks:** no member/submission data is ever seeded into the shared database outside a preview deployment — this is a real constraint, not a suggestion, because there is no separate dev database [Source: architecture.md#10-deployment-architecture]. Use throwaway emails (`test+<uuid>@example.invalid`) and clean up afterward.
- **Edge cases:** duplicate `idempotency_key` on a second call (expected to still insert today — that guard is 4.4's, so this story's tests should note it as a known gap rather than a defect); an email that already exists (expected to raise a unique-violation today, since the upsert is 4.4's).
