# 7.2: Member record

**Story ID:** 7.2
**Epic:** 7 — Member records and insights
**Slug:** member-record
**Status:** ready-for-dev

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As **Ash, a GPC admin**,
I want **to open one member's complete record — every answer, their directory listing, and their
full consent history — and copy the exact consent wording they agreed to**,
so that **I can answer "what do you hold about me?" accurately from one screen, without database
access**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. Given an admin with a valid bearer token calls `GET /api/admin/members/:id` for a member who
   exists and has not been erased, then the response includes: identity (first name, email,
   postcode, `heard_about`, `group_choice`, joined date); every submitted answer including
   free-text, with unanswered questions rendered as "Not answered" — never blank, `null`, or a lone
   dash; the directory listing's submitted-vs-published values, distinguished wherever an admin has
   edited a field; and the complete append-only consent history (purpose, granted, `consent_text`,
   `consent_version`, `method`, `captured_at`) for every purpose.
2. Given the member has been erased, or no member with that id exists, then the endpoint returns
   `404 { error }` with no partial data rendered on either success or failure path.
3. Given a retired choice option appears among a member's historical answers, when the record
   renders, then it is grouped by its stable key and shown with the label the member actually saw
   at the time, marked "retired" — never dropped, never rewritten to the option's current label.
4. Given the "Copy consent record" control is used for one consent row, when the clipboard write
   completes, then the copied text is `text/plain` only, matches the exact serialisation specified
   in Dev Notes, and never includes the member's name or email.
5. Given the page loads, or a copy/export action confirms, then no name or email appears in the
   document title, the confirmation text, or any error message — the title is exactly "Member
   record | GPC Admin" and confirmations state actions or counts only.
6. Given a request to `GET /api/admin/members/:id` is missing a bearer token, or the token is
   invalid or expired, then the response is `401 { error }` with no data body.

## Dev Notes

<!-- LOCKED. Concrete guidance compiled from the planning docs WITH SOURCE CITATIONS.

**Privacy boundary, restated for this screen.** This is one of the only screens where private
member data is legitimately on screen; every read goes through a server-verified bearer token, the
detail key in the URL is the record uuid and nothing else (safe to share internally), and no
personal data may appear in the title, logs, or notifications
[Source: EXPERIENCE.md#5-member-records-and-demand-insights]. NFR-002 requires the endpoint to
reject a missing/malformed/expired token with `401` and no data body
[Source: prd.md#NFR-002]. FR-012's fourth acceptance criterion is this story in full: "every
answer they gave is shown, including free-text answers and the exact consent record with its
timestamp and version" [Source: prd.md#FR-012].

**Auth block — copy verbatim**, identical to 7.1:
```js
const token = req.headers.authorization?.replace('Bearer ', '')
if (!token) return res.status(401).json({ error: 'Not authenticated' })
const { data: { user: caller }, error } = await supabase.auth.getUser(token)
if (error || !caller) return res.status(401).json({ error: 'Invalid or expired session' })
```
[Source: architecture.md#adr-003-authn-via-supabase-auth-authz-is-binary-with-attribution-instead-of-tiers].

**Erasure handling.** `erase_member()` "deletes the member... writes a minimal non-identifying
tombstone (`erased_at`, `request_id`)"
[Source: architecture.md#adr-015-erasure-and-withdrawal-run-through-one-security-definer-function].
Treat both "no row at all" and "row present with `erased_at` set" as `404`, since which of the two
the schema ends up doing is Epic 1/8's implementation detail, not this story's to resolve.
**[Inference]** — defends against either outcome. The 404 copy is specified: **"We couldn't find
that member." / "The link may be out of date, or the record may have been erased at the member's
request."** [Source: EXPERIENCE.md#5-member-records-and-demand-insights]. This is also the answer
to the drop-off note that "we erased you" and "we never had you" are deliberately indistinguishable
— FR-023 keeps only a non-identifying erasure record
[Source: EXPERIENCE.md#5-member-records-and-demand-insights].

**Answers, retirement and rename — ADR-009.** Every choice answer is stored as `{key, label}`;
aggregation and display both key off `key`, and the member record specifically **displays `label`**
— the snapshot of what the member actually saw, so a retired option still reads correctly years
later [Source: architecture.md#adr-009-answers-store-option-keys-and-a-label-snapshot]. Where the
option has since been renamed, the admin UI shows the current label and notes the change; it never
silently merges [Source: architecture.md#adr-009-answers-store-option-keys-and-a-label-snapshot].

**"Copy consent record" — the exact clipboard serialisation. This is the artefact Ash pastes into a
DSAR reply, so it is specified rather than left to the implementer**
[Source: EXPERIENCE.md#5-member-records-and-demand-insights]. `text/plain` **only** — no
`text/html` flavour, because a pasted HTML blob is not evidence. One block per consent row, newest
first, in on-screen order, blank line between blocks:

```
GPC consent record
Record: 8f2c4a1b-19d7-4b0e-9a3c-77e1f0c2ab54
Copied: 2026-08-18 14:22:10 UTC by ash@example.org

NEWSLETTER - WITHDRAWN
Version: newsletter@1.2.0
Recorded: 2026-07-22 08:02:55 UTC
Captured via: unsubscribe link
Text shown at the time:
"I'd like the GPC weekly newsletter."

HOLD MY DATA - GIVEN
Version: hold_data@1.2.0
Recorded: 2026-03-04 19:41:07 UTC
Captured via: web form (/join)
Text shown at the time:
"I agree that GPC Community admins may hold the personal data I submit in this form. I've read the privacy notice (https://greenwichparentsandcarers.co.uk/privacy)."
```

`consent_text` is reproduced byte-for-byte from storage — any URL is already expanded there, so
nothing is transformed at copy time. Every timestamp is the stored UTC value carrying the literal
"UTC". **Name and email are deliberately absent**: the uuid identifies the record and the recipient
already knows who they are, so the artefact stays safe if pasted into the wrong window. A per-row
`[copy]` emits that row's block under the same three header lines. A row with no version serialises
as `Version: NOT RECORDED - treat as unevidenced.`
[Source: EXPERIENCE.md#5-member-records-and-demand-insights]. A consent row with no version also
renders on-screen in an error-tinted row: **"This record predates consent versioning. Treat it as
unevidenced and re-ask before relying on it."**
[Source: EXPERIENCE.md#5-member-records-and-demand-insights].

**Consent evidencing requirement.** NFR-004: "100% of stored consents carry consent text, version
identifier, UTC timestamp and capture method. Zero consent records are mutable after creation"
[Source: prd.md#NFR-004]; this story only ever reads `member_consents`, by construction — "no write
path at all" for `ConsentHistory` [Source: EXPERIENCE.md#5-member-records-and-demand-insights],
consistent with the table's append-only trigger
[Source: architecture.md#adr-010-consent-records-are-append-only-and-version-bearing-enforced-by-trigger].

**Component list.** `MemberDetail`; `BackToListLink`; `RecordSection` (a titled `Card`, used five
times, reusing `src/components/ui/Card.jsx` which has no internal padding by contract — wrap
consumers in `p-6`) [Source: inputs/codebase-constraints-brief.md#5-public-ui-building-blocks--design-tokens];
`FieldPair`; `FreeTextBlock`; `AnswerList`; `SubmittedVsPublished`; `ConsentHistory`;
`ActivityTimeline`; `CopyButton` (44×44px touch target)
[Source: EXPERIENCE.md#5-member-records-and-demand-insights].

**Accessibility.** `<h1 tabindex="-1">` takes focus on mount. `FieldPair` is `<dl>`/`<dt>`/`<dd>` so
label–value association is programmatic. Consent entries are an `<ol>`; each `<li>` opens with the
summary line so purpose/decision/version/timestamp are heard before the verbatim text. Timestamps
are `<time datetime="…Z">` with visible text ending "UTC". The "[edited]" badge's accessible name is
"Edited by an admin". Disclosures use `aria-expanded`/`aria-controls`
[Source: EXPERIENCE.md#5-member-records-and-demand-insights]. This satisfies the accessibility
floor's requirement that every input has `id`+`<label htmlFor>` and groups use `<fieldset>`/
`<legend>` [Source: architecture.md#3-architecture-decision-records].

**Export integration point — do not build the dialog here.** Story 7.5 owns `ExportDialog` and the
export endpoint. This story renders the trigger button only; 7.5 wires it. `MemberDetail.jsx` is
therefore shared/contended with 7.5 — see Owned File/Module Scope.

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. NEVER run tests or quote coverage here. -->

- **Approach:** integration tests against `api/admin/members/[id].js` with seeded fixtures covering
  a full record, an erased/missing record, and auth rejection; component tests for
  `MemberDetail.jsx` covering the five sections, retired-option display, and the clipboard copy
  output; a dedicated unit test for the consent-record serialiser function in isolation from the DOM.
- **Key scenarios:** a member with every question answered; a member with unanswered optional
  questions ("Not answered" renders); a member who never opted into the directory ("Not requested"
  section, not an error); a resubmitted member (prior answers behind a disclosure); a listing with
  admin-edited fields (submitted-vs-published, attributed); a withdrawn consent alongside its
  original grant (both rows, both timestamps); a consent row with no version (renders "Not
  recorded" / serialises as "NOT RECORDED").
- **Per-AC verification:** AC #1 → assert every field maps from the fixture, free text is not
  truncated, unanswered fields read "Not answered"; AC #2 → request an erased and a nonexistent id,
  assert `404` and no body content beyond `{ error }`; AC #3 → seed a retired option in a historical
  answer, assert the historical label and "retired" pill render; AC #4 → invoke the copy action and
  assert the produced string matches the specified format byte-for-byte, including the absence of
  name/email; AC #5 → assert `document.title` and every rendered status string against a
  personal-data denylist (member first name, email); AC #6 → call with no/garbage/expired token,
  assert `401` and an empty body.
- **Fixtures / mocks:** a member with a full submission, a directory listing with admin edits, four
  consent rows (grant + withdrawal for one purpose, grants for the other two, one with a missing
  version); an erased member row and a random nonexistent uuid; a fake bearer token for the 401
  cases; `navigator.clipboard.writeText` mocked to capture the exact string written.
- **Edge cases to cover:** a member who declined the directory entirely (no `directory_listings`
  row); a business-branch member viewing career-only questions as "Not asked"; a consent row whose
  `consent_text` itself contains a URL (must appear expanded inline, unchanged, in the copy output).
