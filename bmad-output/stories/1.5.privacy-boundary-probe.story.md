# 1.5: Privacy boundary probe — the NFR-001 release-gate check

**Story ID:** 1.5
**Epic:** 1 — Data foundation
**Slug:** privacy-boundary-probe
**Status:** ready-for-dev

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As **the data controller**,
I want **a documented, repeatable script that enumerates every database object readable with the public anon key and asserts that no private field is among them**,
so that **NFR-001's zero-tolerance guarantee is proved by running something, not by trusting that everyone remembered ADR-001, and the same check can be re-run after any future change touching a read policy or grant**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. Given the probe script runs against the Supabase project with the anon key, when it completes, then it produces its list of anon-readable tables, views and functions by **introspecting** the database (querying `information_schema`/PostgREST's schema for `anon` grants), not from a hardcoded guess at which objects exist.
2. Given `directory_listings` appears in that list, when its anon-readable columns are inspected, then they are exactly `id, slug, business_name, category_id, description, website_url, instagram_url, enquiry_email, published_at` — no more, no fewer — matching ADR-001's column grant from **1.1**.
3. Given `directory_categories` appears in that list, when its anon-readable columns are inspected, then only non-personal fields (`id, key, label, sort_order, retired_at, created_at, updated_at`) are present.
4. Given any of `members`, `member_submissions`, `member_consents`, `abuse_events`, `outbound_emails`, `data_requests`, `erasure_tombstones`, `form_question_config`, `form_options`, `form_config_versions`, `form_settings` (the private tables from **1.1**–**1.4**) is checked, when the probe queries each with the anon key, then either the object does not appear in anon's readable-object list at all, or querying it returns zero rows and zero columns.
5. Given `erase_member`, `sweep_abuse_events`, and `current_member_consent` (the functions from **1.2**/**1.4**) are checked, when the probe calls each with the anon key, then every call is rejected with a permission error.
6. Given the probe completes, when its output is inspected, then it prints a clear pass/fail summary naming every field it checked for and every object it found, in a form that can be pasted directly into the release checklist entry this story also creates.

## Dev Notes

**This story is the verification artifact, not another migration.** It creates no SQL file and touches no migration under `supabase/migrations/028–031` — those are exclusively owned by **1.1**–**1.4**. It documents and builds a script that checks the schema those four stories create.

### What NFR-001 requires, verbatim

"Zero private fields (name, signup email, postcode, phone, any survey answer, any consent record) retrievable by an unauthenticated caller using the public browser key against any table, view, or route." Measurement method: "Pre-launch check enumerating every publicly readable object with the anon key and asserting the absence of those fields; repeated after any change touching read policies. Recorded on the release checklist." [Source: prd.md#NFR-001]

FR-011 states the same guarantee from the product side: "A written test or documented check exists that an unauthenticated caller cannot read the private data, and it is part of the release checklist." [Source: prd.md#FR-011]

Architecture.md restates the measurement method identically and adds: "This codebase has shipped that exact failure once" — `018_secure_ingest_batch_status.sql` exists because a view (`ingest_batch_status`) was anon-readable in production [Source: architecture.md#7-fr--nfr-coverage-matrix] and [Source: inputs/codebase-constraints-brief.md#3-the-publicprivate-boundary--how-it-is-actually-enforced]. **This is the failure mode this probe exists to catch before it reaches production again**, not a theoretical risk.

### Why the probe must introspect, not hardcode

A probe that checks a fixed list of table names (`['members', 'member_submissions', …]`) only catches regressions on tables it already knows about. It would say nothing about a **new** table added in a future migration that accidentally gets an anon grant — exactly the class of mistake `018` was. The measurement method explicitly says "repeated after any change touching read policies" [Source: prd.md#NFR-001], which only has teeth if the check itself discovers what anon can currently read, rather than asserting against a list a human maintains by hand. [Inference — the source states the requirement and its general method but not the specific introspection mechanism; querying `information_schema.role_table_grants where grantee = 'anon'` is the standard Postgres way to answer "what can this role read" and needs no maintenance as new tables are added.]

### The complete object inventory this probe must reconcile against

From **1.1**: `members`, `member_submissions` (private, no policy) · `directory_listings` (public, 9 granted columns, `status = 'published'` only) · `directory_categories` (public, unconditional). From **1.2**: `member_consents` (private, no policy) · `current_member_consent(uuid, text)` (function, `service_role` only). From **1.3**: `form_question_config`, `form_options`, `form_config_versions`, `form_settings` (all private, no policy). From **1.4**: `abuse_events`, `outbound_emails`, `data_requests`, `erasure_tombstones` (all private, no policy) · `erase_member(uuid, uuid)`, `sweep_abuse_events(boolean)` (functions, `service_role` only, `erase_member` additionally excluded from `authenticated`) [Source: bmad-output/stories/1.1.directory-core-migration.story.md] [Source: bmad-output/stories/1.2.consent-records-migration.story.md] [Source: bmad-output/stories/1.3.form-configuration-migration.story.md] [Source: bmad-output/stories/1.4.abuse-outbound-requests-migration.story.md].

**Scope boundary — flagged explicitly.** This probe is scoped to the schema this feature adds (migrations 028–031). It does not re-audit the 12 pre-existing tables from migrations 001–027, which are unchanged by this project and outside Epic 1's stated scope [Source: epics.md#epic-1-data-foundation]. NFR-001's own wording ("any table, view, or route") is broader than this; a whole-schema audit is a larger undertaking than one dev-day and is not what this story sizes to. ### What "pass" means

Per NFR-001's threshold: **zero** occurrences of any private field, full stop — not "acceptably few" [Source: prd.md#NFR-001]. The script's exit code should be non-zero on any failure, so it can gate a release step even without CI wiring. [Inference]

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. NEVER run tests or quote coverage here. -->

- **Approach:** this story's own subject *is* a verification tool, so "testing" here means proving the probe itself correctly distinguishes pass from fail — run it against the real, correctly-configured schema from **1.1**–**1.4** (expect pass), then deliberately misconfigure one object in a scratch/preview environment and confirm the probe catches it (expect fail), then revert.
- **Key scenarios:** (a) probe passes against the correctly-configured schema; (b) probe fails loudly if `directory_listings` is temporarily given a wider anon column grant than the ADR-001 list; (c) probe fails loudly if a private table is temporarily given an anon `select` policy; (d) probe correctly reports success (rejection) when a locked-down function is called with the anon key; (e) probe's introspection step discovers all objects without needing a hardcoded table list.
- **Per-AC verification:** AC #1 → run the probe and confirm its discovered-objects list matches the inventory in Dev Notes without the list being hardcoded in the script (verify by reading the script's discovery query, not just its output). AC #2 → cross-check the probe's reported `directory_listings` columns against the nine-column ADR-001 list. AC #3 → cross-check `directory_categories`'s reported columns contain no personal-data field. AC #4 → confirm every private table from the inventory is reported as either absent from anon's grant list or zero-column/zero-row. AC #5 → confirm all three functions report a rejected RPC call. AC #6 → read the printed summary and confirm it is copy-pasteable into `docs/release-checklist.md`, and that the checklist file itself exists with the NFR-001 entry.
- **Fixtures / mocks:** none needed for the pass case — it runs against the real (already-verified) schema from 1.1–1.4. For the deliberate-failure scenario, use a Vercel/Supabase **preview** environment, never production, and revert the misconfiguration immediately after confirming the probe catches it [Source: architecture.md#10-deployment-architecture].
- **Edge cases to cover:** an object that exists in the schema but has literally zero rows (e.g. a freshly-migrated `members` table with no data yet) must still be correctly reported as "no anon grant" rather than a false-pass "no data to leak" — the check must be about **grants**, not about current row count, since an empty table today can have rows tomorrow; a function that exists but was never called must still be probed for its grant, not skipped because it has no obvious "return value" to assert on.
