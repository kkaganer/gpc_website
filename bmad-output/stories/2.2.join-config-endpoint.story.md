# 2.2: Join config endpoint

**Story ID:** 2.2
**Epic:** 2 — Form configuration
**Slug:** join-config-endpoint
**Status:** ready-for-dev

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As **the public `/join` form** (built in Epic 3) **and any admin preview surface**,
I want **one public, unauthenticated endpoint that resolves the currently published form
config, the active category taxonomy and the open/closed state into a single JSON payload**,
so that **the form renders the right labels, options and required flags for the version a
member actually saw, without ever touching Supabase directly from the browser.**

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. Given no `Authorization` header, when `GET /api/join/config` is called, then it returns
   `200` with a JSON body containing, for every key in `src/lib/join/questions.js`, the merged
   `{ key, type, branch, maxLength, label, helpText, required, options }` (options resolved
   from the published `form_options` overlay; `listing_category`'s options resolved from
   active `directory_categories` rows instead), plus top-level `{ isOpen, introText,
   closedMessage, configVersion }`.
2. Given a question key exists in the registry but has never had an overlay row written for
   it, when the config is resolved, then that question still appears in the response using its
   registry-declared type/branch/maxLength and a sensible built-in default label — a new
   registry question never breaks the endpoint or requires a migration first
   [Source: architecture.md#adr-008-form-configuration--code-defined-registry-database-overlay-and-versioned-publish].
3. Given an option has been retired (`form_options.retired_at` set), when the **public** config
   is resolved, then that option is absent from the returned `options` array — retired options
   stop being offered to new visitors while past answers remain unaffected (that guarantee is
   enforced elsewhere, at read time of stored answers, not here).
4. Given `form_settings.is_open` is `false`, when the endpoint is called, then `isOpen: false`
   is returned alongside `closedMessage`, and the response still includes the full question
   config (so an admin preview or a client that already fetched config mid-session can still
   introspect it) — the endpoint never omits the question set just because the form is closed.
5. Given the resolver throws for any reason (missing published version row, DB error), when
   the handler responds, then it returns `500 { error: string }`, JSON always, and logs no
   personal data (there is none in this request to log) — `[Source: architecture.md#adr-005-error-and-response-convention]`.
6. The response is safe to cache briefly at the edge — no per-caller or per-session data is
   present anywhere in the payload
   [Source: architecture.md#6-api-specifications — "GET /api/join/config... Safe to cache
   briefly at the edge"].

## Tasks / Subtasks

- [ ] Merge: iterate `require('../../src/lib/join/questions.js').QUESTIONS`, for each entry
  overlay the published version's snapshot data for that `key` if present, else the built-in
  default (AC: #1, #2)
- [ ] For `listing_category`, replace the (always-null) registry options with active
  `directory_categories` rows ordered by `sort_order`, `{ key, label }` shape matching

- [ ] Filter each choice question's `options` array to exclude any option with `retired_at`
  set (AC: #3)

  than `GET` (AC: #5)

  (e.g. `public, max-age=30, stale-while-revalidate=60`) — confirm the exact value has no
  security implication before setting it (AC: #6) [Inference]

## Dev Notes

<!-- LOCKED. Concrete guidance compiled from the planning docs WITH SOURCE CITATIONS.

**Contract, verbatim from the architecture spec.** `GET /api/join/config` — public — "Returns
the current published form config plus active categories and `is_open`. `200` config · `500`
`{ error }`. No auth. Safe to cache briefly at the edge."
[Source: architecture.md#6-api-specifications]. This is the **only** endpoint in the whole
feature set with no bearer-token block — every other `/api/admin/*` and `/api/join/submit`
route in this feature carries auth or anti-abuse; this one deliberately carries neither
because it returns nothing but public configuration content (no personal data, no private
table).

**What "published" means and where it comes from.** ADR-008's three layers: code registry
(this story reads `src/lib/join/questions.js` — 2.1's deliverable — for `key`, `type`,
`branch`, `maxLength`), DB overlay (`form_question_config`/`form_options` hold **draft**
label/help/required/option content), and `form_config_versions` (a `jsonb` snapshot taken at
publish time, `version` text e.g. `2026-08-18.1`, `published_at`, `published_by`). "The public
form reads the **current published version**; preview... resolves the **draft**."
[Source: architecture.md#adr-008-form-configuration--code-defined-registry-database-overlay-and-versioned-publish]
This endpoint therefore reads `form_config_versions`, **not** the raw draft overlay tables —
2.4/2.5 write the draft and snapshot it on publish; this story only ever reads the snapshot.

**Every submission and consent record cites the version this endpoint returned.** "Every
submission records the `form_config_version` it was answered under"
[Source: architecture.md#adr-008-form-configuration--code-defined-registry-database-overlay-and-versioned-publish].
The public form pins the `config_version` string from this response at page load and declares
it back on submit; the server (Epic 4) validates against **the version the member declared**,
not whatever is current by the time they submit
[Source: EXPERIENCE.md#4-configuring-the-form — "A change published while a member is
mid-form"]. This story must return that version string under `configVersion` in the response
so Epic 3 can carry it.

**Bootstrapping assumption.** A published `form_config_versions` row is assumed to always
exist by the time this endpoint is live — seeding it from the registry defaults is Epic 1
story 1.3's job, not this story's
[Source: EXPERIENCE.md#4-configuring-the-form — "Notes for architecture... the configuration
row is seeded from `FORM_STRUCTURE` by migration... which guarantees `/join` renders on first
deploy"]. If no published row exists when this handler runs, that is a data-foundation defect,
not something this endpoint should silently paper over — return `500` rather than inventing a
config from the code registry alone, so the gap is visible rather than masked. [Inference]

**Retirement semantics, precisely.** "Retiring hides an option from the form. It never
changes an answer anyone has already given"
[Source: EXPERIENCE.md#4-configuring-the-form — Screen S2 wireframe, "THE GUARANTEE"]. This
endpoint is the enforcement point for the *hiding* half only — filtering `retired_at`-set
options out of the response so new visitors never see them. The *never changes a stored
answer* half is enforced by the member-record display logic (Epic 7/ADR-009), not here; this
story does not touch `member_submissions.answers`.

**Categories: read-only consumer, not owner.** `directory_categories` is owned by Epic 5 and
takes effect immediately with no draft/publish step
[Source: architecture.md#adr-008-form-configuration--code-defined-registry-database-overlay-and-versioned-publish
— "Categories are not here... One editor, one home."]. This story reads that table (it must
already exist — created by 1.1's `028_directory_core.sql`
[Source: epics.md#epic-1-data-foundation]) but never writes to it, never adds a route for it,
and never lists it in this story's owned scope beyond a read query.

**Error/response shape.** Always JSON; wrap the whole handler in try/catch; `{ error: string
}` + status, never an error-code envelope
[Source: architecture.md#adr-005-error-and-response-convention]. Copy the shape (not the auth
block, which this route omits) from the existing pattern at `api/subscribe.js` and
`api/admin/subscribers.js:53-182` [Source: inputs/codebase-constraints-brief.md#3-the-publicprivate-boundary--how-it-is-actually-enforced].

**No admin-plane touch.** This story adds no admin route, no sidebar entry, no `adminApi.js`
function — it is a pure public read endpoint consumed by Epic 3's `JoinForm` and by 2.6's
preview screen (which resolves the **draft**, a distinct code path 2.6 owns, not this one).

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. NEVER run tests or quote coverage here. -->

- **Approach:** manual/integration verification against a real Supabase preview-deployment
  database once 1.3's migration exists — no local mocking layer exists for Supabase in this
  codebase today, so treat this as a request/response contract check (`curl` against a preview
  deployment or the local `vercel dev` server) rather than a unit test with a stubbed client.
- **Key scenarios:** (a) happy path — a published version exists, form open, categories
  present → full merged payload; (b) form closed → `isOpen: false` plus `closedMessage`,
  questions still present; (c) an option retired since the version was published → absent from
  that question's `options`; (d) a registry key added after the last publish (simulate by
  temporarily adding a throwaway key to 2.1's array) → still appears with defaults, endpoint
  does not 500; (e) no published row at all → `500 { error }`, not a 200 with empty/garbage
  data.
- **Per-AC verification:** AC #1 → inspect full response shape against the registry's 28 keys.
  AC #2 → scenario (d) above. AC #3 → scenario (c) above. AC #4 → scenario (b) above. AC #5 →
  force a DB error (bad env var locally) and confirm `500 { error }` with no HTML body and no
  unhandled rejection. AC #6 → inspect response headers for `Cache-Control` and confirm no
  cookie/session value anywhere in the body.
- **Fixtures/mocks:** a seeded `form_config_versions` row with a small representative subset of
  question keys (does not need all 28) plus one retired option and one active category, so
  every branch of the merge logic is exercised without needing the full 1.3 seed data.
- **Edge cases:** category taxonomy resolves to zero rows (FR-017's "no categories yet" state)
  — the endpoint must still return `listing_category` with an empty `options: []`, not omit
  the key or throw, so Epic 3's D-2 "no categories available" state
  [Source: EXPERIENCE.md#2-the-directory-opt-in-and-consent] has something to render against.

  exist and 1.3 must seed an initial published version); 1.1 (`directory_categories` must
  exist and be readable).

  not this published-only endpoint).
- **External:** none. No new runtime dependency; uses the existing Supabase service-role
  client pattern already present in `api/admin/subscribers.js`.
