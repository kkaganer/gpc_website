# 6.2: Listing detail and not-found (including the site catch-all 404)

**Story ID:** 6.2
**Epic:** 6 — The public business directory
**Slug:** listing-detail-and-not-found
**Status:** ready-for-dev

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As a **public visitor (local parent) who has followed a link to a specific business**,
I want **to view that business's full published listing and make contact, or, if the link no longer resolves, see a calm and honest explanation rather than a broken or blank page**,
so that **I can act on a listing I found, and I am never left wondering whether the site itself is broken**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. Given a slug resolves to a published listing, when `/directory/:slug` renders, then it shows business name, category, full description, website, Instagram (each section present only if the field is set) and the public enquiry contact — and nothing else about the member (no first name unless it is the business name, no signup email, no postcode or area, no phone unless it is the nominated contact, no survey answer, no consent or moderation data, no submission or approval date).
2. Given the visitor acts on the enquiry contact, then the primary action reaches the member's nominated `enquiry_email` via a `mailto:` link — never the signup email — and a "Copy address" control places the same address on the clipboard; where the Clipboard API is unavailable, that control instead renders `aria-disabled="true"` with a "Select the address above to copy it" hint, and the address itself remains present as plain, selectable text.
3. Given the description or any member-submitted free text contains characters that look like HTML or markdown, when rendered, then it displays as literal plain text under `white-space: pre-wrap` — never parsed as markup, never rendered via `dangerouslySetInnerHTML`, and no bare URL inside it is ever auto-linked.
4. Given a slug matches zero published rows (unpublished, withdrawn, or never existed), when the page renders, then the "listing" not-found variant shows ("This listing isn't in the directory") with two recovery actions (`Browse the directory`, `Go to the homepage`), and the slug itself is never echoed anywhere in the rendered output or page title.
5. Given any request path that matches no defined route in `src/App.jsx`, then the new site-wide catch-all route renders the "page" not-found variant, with copy distinct from the listing variant, inside the standard `Layout` (nav, skip link and footer all present).
6. External links (website, Instagram) open with `target="_blank"` and `rel="noopener noreferrer ugc"`, and each carries a visually-hidden "(opens in a new tab)" suffix appended to its accessible name.
7. Given the listing fetch fails outright (network error, timeout, non-2xx), that state is visibly and structurally distinct from a successful fetch that resolved to zero rows — the fetch-failure case never shows the not-found copy, and the zero-rows case never shows the retryable-error copy.

**Architecture and data access**
- This page, like 6.1's index, reads `directory_listings` directly from the browser with the anon key — **no API route in between**. That is safe *only* because of ADR-001: `directory_listings` has no column capable of holding personal data, and the RLS policy restricts rows to `status = 'published'` regardless of which columns are requested. State this explicitly in code comments; this pattern is not a general licence to skip a server route elsewhere in the feature [Source: architecture.md#adr-001-split-public-and-private-data-across-separate-tables-and-revoke-column-access-on-the-public-one] [Source: architecture.md#component-directory-public — "Requires: supabase.from('directory_listings') with the anon key — published rows, granted columns only. No API route; there is nothing private to protect and no reason to add a hop."].
- Anon-granted columns: `id, slug, business_name, category_id, description, website_url, instagram_url, enquiry_email, published_at`. `member_id`, `status`, `reject_reason`, `submitted_*`, `actioned_by`, `actioned_at` are not granted — do not select them, and do not build any UI branch that would depend on their value [Source: architecture.md#5-data-model — Entity: directory_listings].
- **Slugs are immutable** — generated once at first publication, never regenerated on rename. `directory_listings` is addressed publicly by `slug`, internally by `id`. This story never mints or recomputes a slug (that belongs to the moderation/publish flow, story 5.3) — it only reads by the slug already present in the URL [Source: architecture.md#adr-013-listing-slugs-are-generated-once-and-never-regenerate].
- A published listing cannot be structurally empty: name, category, description and enquiry contact are all required at submission and moderation gates publication, so the only legitimate "nothing here" states are (a) zero published rows for this slug, and (b) an unmatched path entirely — there is no third, "empty but published" state to design for [Source: EXPERIENCE.md#6-the-public-directory — Screen S2, state table, "Empty… N/A"].

**FRs satisfied**
- FR-020 (listing detail shows exactly business name/category/description/website/Instagram/enquiry contact and nothing else; enquiry contact reaches the nominated contact, never the signup email; unpublished-after-sharing shows a clear "no longer listed" state; external links marked external; submitted text renders as plain text) [Source: prd.md#FR-020].
- NFR-001 (zero private fields retrievable by the anon key) governs the exhaustive "deliberately absent" field list below [Source: prd.md#NFR-001].
- FR-023 is not delivered here, but this screen's third not-found sentence exists specifically to reassure a member reading it that withdrawal (delivered by Epic 8) already works and is respected [Source: EXPERIENCE.md#6-the-public-directory — Screen S3, "Copy decisions worth defending"].

**The addendum-Q1 constraint — no location, anywhere, restated on this screen**
- No postcode, outcode or area is ever rendered on a listing — this is the same standing decision as 6.1's, not a separate call for the detail page [Source: addendum.md#Q1] [Source: prd.md — Out of Scope, "Publishing any location, even approximate"].
- The enquiry panel repeats the honesty line verbatim as a trust line: *"We don't publish business locations either — if you need someone nearby, just ask."* alongside *"We never publish a member's personal email or home address."* [Source: EXPERIENCE.md#6-the-public-directory — Screen S2 wireframe, "Get in touch" panel]. Do not add a location field, an area string, or a map anywhere on this page.

**UX/UI acceptance detail**
- Field list, deliberately absent and must stay absent: member's first name (unless it is the business name), signup email, postcode/area, phone unless nominated as the public contact, group, any survey answer, any consent record, any moderation note, any submission/approval date, any admin note, "member since" line, byline, avatar, share count. The page renders exactly the six FR-020 fields plus GPC's own framing [Source: EXPERIENCE.md#6-the-public-directory — Screen S2, "What is deliberately absent"].
- **Enquiry contact base case is email, shown in the clear, as real selectable text.** CSS/JS obfuscation breaks screen readers and copy-paste; an address-as-image fails WCAG; a relay form would create a new message store this release has no capability to support. This is the shape to build (phone/contact-page shapes are a documented open question, addendum Q3/Q4, and are not required by this story) [Source: EXPERIENCE.md#6-the-public-directory — Screen S2, "Enquiry contact rendering"] [Source: addendum.md#Q3, #Q4].
- Copy button behaviour: on success, its own label swaps to "Copied ✓" for 2 seconds then reverts (button retains focus, so the label change is itself announced); the shared polite live region additionally carries "Address copied." for assistive technology that does not re-announce a focused element's label change. No toast [Source: EXPERIENCE.md#6-the-public-directory — Screen S2, state table, "Success"] [Source: sharding-context.md — UX rulings, A6].
- External link text is the **hostname or @handle**, never the raw URL (avoids 90-character tracking-parameter strings that also wrap badly at 320px) [Source: EXPERIENCE.md#6-the-public-directory — Screen S2, Accessibility]. `rel="noopener noreferrer ugc"` — `ugc` specifically because the links are member-supplied [Source: EXPERIENCE.md#6-the-public-directory — Screen S2, Accessibility].
- Heading order: `<h1>` name → `<h2>` "Find them online" (omitted with its whole section when both links are absent) → `<h2>` "Get in touch". The About-GPC footnote is a plain paragraph, not a heading [Source: EXPERIENCE.md#6-the-public-directory — Screen S2, Accessibility].
- Loading: `SkeletonDetail` (badge block, two-line title, five description lines, panel block); the "Back to directory" link is live immediately since it needs no data. Error: distinct from not-found — "we could not find out" (network/5xx/timeout) is never the same message as "we found out, and it isn't published"; conflating them would falsely tell a visitor a listing is gone when the network merely hiccupped. `robots` is left untouched on a transient error, so a live listing is never deindexed by a blip [Source: EXPERIENCE.md#6-the-public-directory — Screen S2, state table].
- **Not-found copy is exact and must not be paraphrased.** `listing` variant — `<h1>` "This listing isn't in the directory"; body "It may have been removed, or the link may be wrong. Businesses come and go from the directory — a member can ask us to take their listing down at any time."; actions `[ Browse the directory ]` and "Go to the homepage". `page` variant — `<h1>` "This page isn't here"; body "The link may be wrong, or the page may have moved."; actions `[ Go to the homepage ]` and "Browse the directory". Use "isn't in the directory" / "isn't here", never "not found", "404", or "removed" — the copy must be true whether the listing was unpublished, never existed, or the URL was mangled, none of which the visitor (or the code) can distinguish. **The slug is never echoed** — doing so would confirm to a prober which listings once existed. `/join` is deliberately not offered on either variant. Decorative mark is grey, `aria-hidden`, **not** error-red, no "Oops!" [Source: EXPERIENCE.md#6-the-public-directory — Screen S3, wireframe and "Copy decisions worth defending"].
- **The catch-all route is genuinely new.** `src/App.jsx` has no `path="*"` today; any unmatched path currently renders the shell around an empty `<main>`. Add `<Route path="*" element={<NotFoundPage variant="page" />} />` as the **last child** of the `<Layout>` route group so nav, skip link and footer are present. Without this route, a withdrawn listing and a mistyped path are indistinguishable — one renders blank, the other doesn't render at all [Source: EXPERIENCE.md#6-the-public-directory — Screen S3, "The catch-all route is in scope"] [Source: inputs/codebase-constraints-brief.md — "no 404 route"].
- **This is a soft 404 — HTTP 200 either way.** A client-routed SPA on Vercel with no server rendering cannot return a true 404/410 without an architecture change this story does not make. `<meta name="robots" content="noindex">` is the available mitigation; document this as a known limitation rather than attempting a rewrite [Source: EXPERIENCE.md#6-the-public-directory — Screen S3, state table and "Notes for architecture", "S3 is a soft 404"].
- Route declaration order matters: `/directory/:slug` is declared **after** `/directory` so the literal path is matched first [Source: EXPERIENCE.md#6-the-public-directory — Routes table, "Declared after /directory"].

**Accessibility floor (applies here in full)** — plain-text rendering of all submitted content is the site-wide rule, not specific to this feature, because the site sets **no CSP** and has no other injection mitigation [Source: sharding-context.md — Accessibility floor (NFR-008), "Submitted text renders as plain text, never markup"] [Source: architecture.md#component-directory-public — "the site sets no CSP, so this is the mitigation, not a nicety"]. Touch targets ≥44×44px (the Copy button); visible `:focus-visible`; `<button>`/`<a>` only.

- The `/directory` route and its `?q=`/`?category=` URL contract (needed for "Back to directory" and for `location.state`-based focus/scroll restore) are built by **6.1**; this story assumes both exist [Dependency: see Dependency Maps].

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. NEVER run tests or quote coverage here. -->

- **Approach:** No test runner is configured in this repo — `package.json` has no `test` script and no `vitest`/`jest`/`@testing-library` dependency [Inference, from direct inspection]. Verification is manual/inspection-based against a seeded Supabase environment, run once per AC as a documented checklist.
- **Key scenarios:** a published listing with both website and Instagram present; one with neither (confirming the whole "Find them online" section, including its `<h2>`, is absent); a slug matching a `pending`/`held`/`rejected`/`unpublished` row (must behave identically to a never-existed slug — no status is ever leaked by the difference); an arbitrary mistyped path (`/directoy/x`, `/foo/bar`); a description containing literal `<b>bold</b>`, `**markdown**`, and a bare `https://` URL, to prove none of it is parsed or auto-linked; Clipboard API present vs. simulated-absent; a slow/offline fetch versus a fetch that resolves to zero rows, confirmed as visually distinct.
- **Per-AC verification:** AC #1 → inspect rendered DOM against the "deliberately absent" field list on a seeded listing with every optional field populated; AC #2 → click the mailto action and confirm the `href` target equals `enquiry_email` (not the member's signup email, which must not even be in the fetched payload), then exercise Copy address in both clipboard-available and clipboard-unavailable conditions; AC #3 → seed a description containing HTML- and markdown-looking text and a bare URL, confirm literal rendering with no elements or anchors created from it; AC #4 → request a slug for a non-published row and a slug that has never existed, confirm identical output and that the slug string does not appear in the DOM or `document.title`; AC #5 → request several arbitrary unmatched paths, confirm the `page` variant renders inside `Layout` (nav/skip-link/footer present) with copy distinct from AC #4's; AC #6 → inspect each external link's `target`, `rel`, and computed accessible name; AC #7 → force a network failure (offline/throttled/revoked grant) and separately seed a genuinely absent slug, confirming the two render different components.
- **Fixtures / mocks:** at least one published row with `website_url`/`instagram_url` both set, one with both null, one with only `instagram_url`; one row in each non-`published` status value to exercise AC #4 without conflating "never existed" and "exists but hidden"; a description field populated with HTML-/markdown-looking text and a bare URL for AC #3.
- **Edge cases to cover:** a slug that collides with a static route segment, to confirm route-declaration order behaves as expected; direct cold navigation to `/directory/:slug` versus client-side navigation from the index (both must reach the same rendered state and both must reset scroll/focus to the `<h1>`); confirm `<meta name="robots" content="noindex">` is present on both not-found variants and that the HTTP status is documented as 200 (soft 404), not asserted as a true 404; `prefers-reduced-motion` on the skeleton.
