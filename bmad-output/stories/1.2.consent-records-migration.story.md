# 1.2: Consent records migration — append-only, trigger-enforced

**Story ID:** 1.2
**Epic:** 1 — Data foundation
**Slug:** consent-records-migration
**Status:** ready-for-dev

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As **the data controller**,
I want **every consent event stored in an append-only table that Postgres itself refuses to update or delete**,
so that **GPC can produce what a member consented to, when, and to which version of the wording, and no code path — including a future bug in a service-role script — can quietly rewrite that history**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. Given migration `029_consent_records.sql` is applied, when `member_consents` is inspected, then it has exactly the six evidentiary fields plus identity columns: `purpose` (text + CHECK `hold_data|publish_listing|newsletter`), `granted` (boolean), `consent_text` (text), `consent_version` (text), `method` (text + CHECK `join_form|admin|withdrawal_link`), `captured_at` (timestamptz), alongside `id` and `member_id`.
2. Given a row already exists in `member_consents`, when an `UPDATE` or `DELETE` is attempted against it by any role — including `service_role` — outside the single documented exemption in `erase_member()` (Story 1.4), then the `member_consents_immutable` trigger raises an exception and the statement fails.
3. Given a member has two rows for the same `purpose` (an original grant and a later withdrawal), when `current_member_consent(member_id, purpose)` is called, then it returns the row with the latest `captured_at`, not the first.
4. Given the `anon` or `authenticated` role calls `current_member_consent(...)`, when the call executes, then it is rejected — `EXECUTE` is granted to `service_role` only.
5. Given an unauthenticated client queries `member_consents` directly with the anon key, when the query executes, then zero rows are returned — RLS is enabled with no `anon` policy.
6. Given migration `029_consent_records.sql` is applied a second time, when `supabase db push` executes, then it completes with no error.

### Why this table must exist at all

No `consent_text`, `consent_version`, `consent_method` or equivalent column exists anywhere in the current 27-migration schema. The site's published GDPR policy names Consent as the lawful basis for opt-in data, so GPC currently cannot evidence what any member agreed to [Source: architecture.md#adr-010-consent-records-are-append-only-and-version-bearing-enforced-by-trigger]. FR-004 requires three separately-recorded consents whose stored record includes the exact text shown, a version identifier, the UTC timestamp, and the capture method [Source: prd.md#FR-004]. NFR-004's threshold is that 100% of stored consents carry all four evidentiary fields and that zero consent records are mutable after creation [Source: prd.md#NFR-004].

### Why a trigger, not grants

Revoking `UPDATE`/`DELETE` from `authenticated` would **not** stop the write path this feature actually uses: `service_role` — the credential every server route in this feature writes through (ADR-004, ADR-015) — bypasses RLS and holds broad table grants by default. A grants-only defence would be invisible protection against everyone except the one credential capable of doing the damage. The trigger is the only mechanism that stops `service_role` too: it fires `before update or delete` for every role, and the only way past it is an explicit `alter table … disable trigger`, which is auditable and rare [Source: architecture.md#adr-010-consent-records-are-append-only-and-version-bearing-enforced-by-trigger].

```sql
create or replace function member_consents_no_mutate() returns trigger as $$
begin raise exception 'member_consents is append-only'; end $$ language plpgsql;

create trigger member_consents_immutable
  before update or delete on member_consents
  for each row execute function member_consents_no_mutate();
```
[Source: architecture.md#adr-010-consent-records-are-append-only-and-version-bearing-enforced-by-trigger] — reproduced verbatim; do not paraphrase this trigger's body, since its exact wording is what a future maintainer reads when the exception fires.

**Withdrawal is a new row, `granted = false`, never an `UPDATE`.** A member who withdraws newsletter consent, for example, gets a second `member_consents` row with `purpose = 'newsletter', granted = false` — the original grant row is untouched [Source: architecture.md#adr-010-consent-records-are-append-only-and-version-bearing-enforced-by-trigger].

**The one documented exemption.** Erasure must delete `member_consents` rows too (a member who is erased should have no residual consent record), which this trigger would otherwise block. `erase_member()` — built in **Story 1.4**, migration `031` — disables the trigger for the duration of its transaction and re-enables it before returning; that is the single legitimate path around this trigger, and it is not this story's job to build it, only to make sure the trigger and function names it depends on (`member_consents_immutable`) are exactly as documented here so 1.4 can reference them correctly [Source: architecture.md#adr-010-consent-records-are-append-only-and-version-bearing-enforced-by-trigger] and [Source: architecture.md#adr-015-erasure-and-withdrawal-run-through-one-security-definer-function].

### `member_consents` table — verbatim from ADR-010

```sql
create table if not exists member_consents (
  id              uuid primary key default gen_random_uuid(),
  member_id       uuid not null references members(id) on delete cascade,
  purpose         text not null check (purpose in ('hold_data','publish_listing','newsletter')),
  granted         boolean not null,
  consent_text    text not null,
  consent_version text not null,
  method          text not null check (method in ('join_form','admin','withdrawal_link')),
  captured_at     timestamptz not null default now()
);

comment on column member_consents.consent_text is
  'The exact wording shown to the member. Never edited. A revision is a new row under a new consent_version.';

create index if not exists member_consents_member_purpose_idx
  on member_consents (member_id, purpose, captured_at desc);

alter table member_consents enable row level security;
-- No anon policy, no authenticated policy: reads happen only via service-role
-- (the admin member-record view, and current_member_consent() below).
```
[Source: architecture.md#adr-010-consent-records-are-append-only-and-version-bearing-enforced-by-trigger]

The three `purpose` values match the three consents members actually give on `/join`: `hold_data` (required always), `publish_listing` (required only when opting into the directory), `newsletter` (never required, never pre-ticked) [Source: EXPERIENCE.md#2-the-directory-opt-in-and-consent]. The exact consent copy for each is a deliverable stored verbatim and versioned — `hold_data@1.0.0`, `publish_listing@1.0.0`, `newsletter@1.0.0` in the UX draft's own version numbering [Source: EXPERIENCE.md#2-the-directory-opt-in-and-consent] — but this migration does not store or hardcode any consent text; `consent_text`/`consent_version` are plain `text` columns populated by whichever server path writes the row (Epic 4's `submit_membership()`). **`hold_data`'s retention-period sentence still contains the placeholder `«RETENTION_PERIOD»`** (addendum Q8) — this blocks the first *live* submission, not this migration; the column type is unaffected either way [Source: architecture.md#adr-010-consent-records-are-append-only-and-version-bearing-enforced-by-trigger].

### `current_member_consent` function

Exposes "what is the current state per purpose" without a mutable column — the function reads the latest row by `captured_at`, since the table itself never gets a "current" flag [Source: architecture.md#adr-010-consent-records-are-append-only-and-version-bearing-enforced-by-trigger]. Used by the admin member-record view (FR-012's "exact consent record with its timestamp and version") [Source: prd.md#FR-012].

```sql
create or replace function current_member_consent(p_member_id uuid, p_purpose text)
returns member_consents
language sql
stable
as $$
  select *
  from member_consents
  where member_id = p_member_id
    and purpose = p_purpose
  order by captured_at desc
  limit 1;
$$;

revoke execute on function current_member_consent(uuid, text) from public, anon;
grant execute on function current_member_consent(uuid, text) to service_role;
```
The lockdown pair is mandatory in the same migration that creates the function — Postgres grants `EXECUTE` to `PUBLIC` by default, and `010_lock_down_publish_rpcs.sql` exists in this repo precisely because that was missed once [Source: architecture.md#adr-002-persistence-conventions]. Granted to `service_role` rather than `authenticated`: every component reading private consent data does so via a bearer-token-verified `/api/admin/*` route using a service-role client, not a direct authenticated RPC from the browser [Source: architecture.md#4-component-design]. `security definer` is intentionally **not** used here — `member_consents` has no policies at all, so a plain function running as `service_role` already bypasses RLS via the caller's own role; adding `security definer` would only matter if this were ever granted to `authenticated`, which it is not [Inference].

## Testing

- **Approach:** manual SQL-editor verification against the shared Supabase project — no automated test runner exists in this repo [Inference, confirmed by reading `package.json`]. This migration depends on `members` from **1.1**, so apply `028` first.
- **Key scenarios:** (a) table shape matches Dev Notes; (b) an `UPDATE` on an existing consent row fails with the trigger's exact exception message; (c) a `DELETE` on an existing consent row fails the same way; (d) `current_member_consent` returns the latest row when two rows exist for the same purpose; (e) anon cannot call the function or read the table; (f) re-running the migration is a no-op.
- **Per-AC verification:** AC #1 → `\d+ member_consents` against Dev Notes. AC #2 → as `service_role`, insert a test consent row, then attempt `update member_consents set granted = false where id = …` and confirm it raises `member_consents is append-only`; repeat for `delete`. AC #3 → insert two rows for the same `member_id`/`purpose` with different `captured_at`, call `current_member_consent(...)`, confirm the later row returns. AC #4 → call the function with the anon key (e.g. via PostgREST RPC) and confirm a permission error. AC #5 → `select * from member_consents` with the anon key returns nothing. AC #6 → re-apply via `supabase db push`.
- **Fixtures / mocks:** one test `members` row and two or three hand-inserted `member_consents` rows via the SQL editor with `service_role`, deleted after verification (no seed data left behind — no separate dev database exists) [Source: architecture.md#10-deployment-architecture].
- **Edge cases to cover:** inserting a `purpose` or `method` value outside the CHECK list must fail; inserting `granted` as `null` must fail (`not null`); confirm the trigger fires even when the update targets an unrelated column (e.g. attempting to "fix a typo" in `consent_text` must still be blocked — there is no such thing as a harmless edit to this table).
