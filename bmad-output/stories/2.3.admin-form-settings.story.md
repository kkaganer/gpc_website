# 2.3: Admin form settings

**Story ID:** 2.3
**Epic:** 2 — Form configuration
**Slug:** admin-form-settings
**Status:** ready-for-dev

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As **Ash, a GPC admin**,
I want **one screen where I can see and immediately flip whether `/join` is open, and write
the intro and closed-message copy**,
so that **I can pause sign-ups the moment I need to — while I'm mid-attack or mid-backlog —
without waiting on a separate publish step, per ADR-008's explicit exception.**

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. Given an admin toggles the open/closed switch on `/admin/join-form` and confirms, when the
   toggle completes, then `PUT /api/admin/form-settings` writes `form_settings.is_open`
   **directly, with no draft/publish step** — the very next call to `GET /api/join/config`
   (2.2) reflects the new state. This is the one field in the whole form-configuration surface
   that is never queued as a draft.
2. Given the admin closes the form, when they confirm the dialog, then the dialog states the
   consequence for anyone mid-form before the write happens (per the J2 journey copy in Dev
   Notes) — closing is never a silent, unconfirmed single click, unlike reopening.
3. Given the admin reopens a closed form, when they tap the toggle, then it applies with **no
   confirmation dialog** — reopening has no destructive consequence, so it costs exactly one
   tap.
4. Given the page loads, then it shows: a status card naming the current state and, if closed,
   the date it closed ("Closed since 18 Aug"); the public form's URL, copyable; an intro-text
   field and a closed-message field, both plain text with preserved line breaks, both editable
   as **draft** content (not applied until 2.5's publish step); and a read-only list of every
   registered question grouped by "asked of everyone" / branch-conditional, each row linking to
   2.4's editor.
5. Given the intro or closed-message field is edited, when the change is saved, then it behaves
   as a **draft** edit — the public `/join` (via 2.2) continues serving the currently
   *published* text until an admin publishes (2.5), exactly like a question label edit, and
   this is stated in on-screen copy so the distinction from the open/closed toggle is never
   ambiguous.
6. The admin dashboard shows a live one-line status for the form ("Open · up to date" /
   "Open · N unpublished changes" / "Closed since 12 Aug") sourced from the same data this
   screen reads, so Ash never has to open the settings screen just to check.

## Dev Notes

<!-- LOCKED. Concrete guidance compiled from the planning docs WITH SOURCE CITATIONS.
     Cite every fact: [Source: prd.md#anchor] / [Source: architecture.md#anchor] /
     [Source: ux-design.md#anchor]. Label your own inferences [Inference]. -->

**Why open/closed is immediate — state it on screen, don't just implement it.** "Editing
writes to the overlay tables as draft. Publishing snapshots the resolved config into a new
version row... **Exception:** the open/closed toggle (`form_settings.is_open`) applies
**immediately**, not on publish — closing the form is an emergency control, and making it wait
behind a publish step would be a defect."
[Source: architecture.md#adr-008-form-configuration--code-defined-registry-database-overlay-and-versioned-publish].
FR-009 requires the same: "Given the form is set to closed, when a visitor opens `/join`, then
they see an admin-authored closed message instead of the fields" with no deploy and no
publish gate implied [Source: prd.md#FR-009]. The UX draft states the copy directly: *"If it
changes what the public sees, it stays a draft until you publish it. The one exception is the
switch at the top of this page."* [Source: EXPERIENCE.md#4-configuring-the-form]. Put that
sentence (or its substance) on screen — it is the load-bearing explanation that keeps Ash from
assuming the toggle needs a Publish click too.

**Confirmation asymmetry is deliberate, not an oversight.** Closing gets a `Dialog`
explaining the in-flight consequence; reopening gets none — "reopening costs one tap and no
confirmation" [Source: EXPERIENCE.md#4-configuring-the-form — Journey J2 success criteria].
Verbatim dialog copy to reuse: *"Close the form to new members? Members visiting `/join` will
see your closed message instead of the form. This takes effect straight away. Anyone
part-way through the form right now won't be able to send it. They'll see a message asking
them to email us instead. You can reopen it any time."*
[Source: EXPERIENCE.md#4-configuring-the-form — Journey J2 wireframe].

**Status card and dashboard line — the drop-off risk this exists to prevent.** "The dominant
risk is not failure but false success... Every non-accessibility mitigation here targets that
one failure — the sticky bar, the dashboard change count..."
[Source: EXPERIENCE.md#4-configuring-the-form — Journey J1 drop-off risk]. The dashboard
card's three states are literal copy to reuse: "Open · 3 unpublished changes" / "Open · up to
date" / "Closed since 12 Aug"
[Source: EXPERIENCE.md#4-configuring-the-form — "One sidebar entry appended..."]. The
"unpublished changes" count in that line is **not** this story's to compute correctly in every
case — it depends on the draft-diff logic 2.4/2.5 build; this story wires the display and may
show `0` until those land, but the plumbing (`useFormConfigDraft` exposing a change count)
belongs here so 2.5 can populate it without touching this file again. [Inference]

**Draft vs. live boundary for intro/closed message — a citation gap to flag, not silently
resolve.** `architecture.md`'s data-model section states plainly: "`form_settings` is a
single-row table holding `is_open`, `closed_message`, `intro_text`"
[Source: architecture.md#5-data-model — Entity: `form_config_versions` / ... / `form_settings`],
which reads as though all three are live-only columns. But ADR-008's own prose calls out
**only** `is_open` as the immediate exception, and `EXPERIENCE.md`'s detailed S1 spec states
outright that "Labels, help text, required flags, options, intro text and closed message are
drafted, previewed and published as one atomic set"
[Source: EXPERIENCE.md#4-configuring-the-form — "Draft → publish (A4)"]. This story follows
the more detailed, scenario-tested UX spec: `intro_text` and `closed_message` are **draft**
content resolved the same way question labels are, and `form_settings` as described in
architecture §5 is read here as the table holding the **published** copies of those two
fields (updated only when 2.5 publishes) plus the always-live `is_open`. **This divergence
is unresolved between architecture.md and EXPERIENCE.md and must be confirmed against 1.3's
actual migration DDL once it exists** — flagged for the orchestrator and for whoever authors
1.3. [Inference]

**Read-only question list.** Each row shows label, type-in-plain-English ("Single choice"),
required/branch badges, and an option count for choice questions, linking to 2.4's editor —
copy the row-as-link pattern, not a nested button
[Source: EXPERIENCE.md#4-configuring-the-form — Screen S1 wireframe, "the whole row is one
`<Link>`"]. Branch groups render as `<h3>` labels stating the condition as fact ("Only if they
choose Business Mums or Both"), never as a control — there is nothing to toggle here, branching
is fixed in 2.1's registry
[Source: architecture.md#adr-008-form-configuration--code-defined-registry-database-overlay-and-versioned-publish].
The permanent `InlineDisclosure` explaining why questions cannot be added/removed belongs on
this screen too, verbatim from `EXPERIENCE.md`
[Source: EXPERIENCE.md#4-configuring-the-form — "Why can't I add or remove questions?"].

**Abuse tile is a slot, not this story's build.** FR-006 criterion 5's "Abuse blocked" tile
sits directly under the status card [Source: EXPERIENCE.md#4-configuring-the-form — Screen
S1 wireframe] but is built and owned by 2.7, which is the **only** UX surface of NFR-003
[Source: sharding-context.md — epic-specific direction]. This story reserves the layout slot
and imports 2.7's component once it exists; it must not reimplement any abuse-counting logic.

**Admin-plane pattern to copy.** Bearer-token verification block, verbatim, at the top of
every handler [Source: architecture.md#adr-003-authn-via-supabase-auth-authz-is-binary-with-attribution-instead-of-tiers]:
```js
const token = req.headers.authorization?.replace('Bearer ', '')
if (!token) return res.status(401).json({ error: 'Not authenticated' })
const { data: { user: caller }, error } = await supabase.auth.getUser(token)
if (error || !caller) return res.status(401).json({ error: 'Invalid or expired session' })
```
Copy from `api/admin/subscribers.js:64-73`. Attribution: every write records `actioned_by`
(the caller's `auth.uid()`) and `actioned_at`
[Source: architecture.md#adr-003-authn-via-supabase-auth-authz-is-binary-with-attribution-instead-of-tiers].

**Accessibility floor applies in full** — every input `id`+`<label htmlFor>`, the toggle is a
real `role="switch"` announcing "Form open to new members, switch, on" with its two supporting
lines chained via `aria-describedby`
[Source: EXPERIENCE.md#4-configuring-the-form — Screen S1 accessibility notes], `AdminLayout`
needs the skip link it currently lacks (owned by 5.1 — do not duplicate it here, just don't
regress it) [Source: sharding-context.md#ux-rulings-that-override-the-long-form-drafts — A21
skip-link note].

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. NEVER run tests or quote coverage here. -->

- **Approach:** manual verification against a preview deployment (no test runner configured
  in this repo — see 2.1's Testing note on that gap) plus a keyboard-only pass, since this is
  a WCAG-scoped admin screen.
- **Key scenarios:** toggle close → confirm dialog appears with the in-flight-member copy →
  confirm → `GET /api/join/config` immediately reflects `isOpen: false`; toggle open from
  closed → no dialog, immediate `isOpen: true`; edit intro text and save → `GET
  /api/join/config` still returns the **old** intro text until a publish action exists (2.5
  not yet built — verify the draft write lands in the overlay/draft store and does not leak
  into the published response); dashboard status line matches the settings screen's own status
  card at all times.
- **Per-AC verification:** AC #1 → the immediate-write assertion above, timed (no polling
  delay, no cache staleness). AC #2 → dialog copy and confirm-required behaviour on close. AC
  #3 → no dialog on reopen. AC #4 → full page render check against the wireframe elements
  listed. AC #5 → draft-vs-published divergence for intro/closed text specifically. AC #6 →
  dashboard line matches three named states.
- **Fixtures/mocks:** a `form_settings` row in both `is_open = true` and `is_open = false`
  states; a draft with a pending intro-text edit and no pending edit, to exercise both
  dashboard-line branches.
- **Edge cases:** admin leaves the closed-message field blank and closes the form — verify the
  fallback copy path exists downstream in Epic 3 (this story only needs to allow saving an
  empty string, not invent the fallback text, which is Epic 3's S4 concern
  [Source: EXPERIENCE.md#1-joining--the-public-form — Screen S4, "If the admin left the
  message blank"]); double-submitting the toggle (rapid double-click) must not leave
  `is_open` in an inconsistent state relative to what the UI displays.
