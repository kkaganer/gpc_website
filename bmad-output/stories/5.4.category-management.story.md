# 5.4: Category management — add, rename, reorder, retire; delete only at zero references

**Story ID:** 5.4
**Epic:** 5 — Moderation and shared admin
**Slug:** category-management
**Status:** ready-for-dev

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As **Ash (GPC admin)**,
I want **to add, rename, reorder and retire directory categories from one screen, with delete available only when nothing uses a category**,
so that **the join form's category choices and the public directory filter always reflect the same live taxonomy, and I can never accidentally break a published listing by deleting the category it depends on**.

## Acceptance Criteria

<!-- LOCKED. External dev tools must not edit Acceptance Criteria. -->

1. Given an admin adds, renames, reorders or retires a category at `/admin/directory/categories`, when the change saves, then it takes effect **immediately** — no draft/publish step — and is what the next load of the form's category choices and the directory filter will read.
2. Given a category is renamed, when published listings using it are viewed (admin or public), then they show the new name without needing re-approval, and the listing's own `status`/attribution are untouched.
3. Given a category is retired, when it is no longer offered as a choice on the form, then listings already using it remain published and remain filterable, and the category itself appears in a separate "Retired" section with a **"Put it back on the form"** action.
4. Given an admin attempts to delete a category referenced by at least one listing, when the request is made, then it is refused with the exact referencing-listing count and a **"Retire it instead"** recovery action — deletion only succeeds when zero listings reference the category.
5. Given the category list, when it renders, then reordering is available via `↑`/`↓` buttons on every row at every viewport width — the buttons are never replaced by drag-only reordering.

- Write path: **direct, authenticated `supabase.from('directory_categories')` calls from the browser, not a `/api/admin/*` route.** Categories are non-personal taxonomy content, not member data, so ADR-004's "browser never writes member data" restriction does not apply to them; the existing admin-plane precedent for non-personal-data writes is `supabase.from('directory_listings').update(...)` in `LondonEventsManager.jsx:357-389`. [Source: inputs/codebase-constraints-brief.md#3-the-publicprivate-boundary] **Inference:** this story assumes `directory_categories` carries the standard admin-write RLS policy (`for all to authenticated using (true) with check (true)`) established for other admin-editable tables in this codebase; the exact policy is story 1.1's migration to define — confirm before implementation. [Inference]
- Delete-at-zero-references: rather than a new count-check function, rely on the natural foreign key `directory_listings.category_id references directory_categories(id)` defaulting to `ON DELETE RESTRICT`, and catch Postgres error code `23503` (`foreign_key_violation`) to render the friendly refusal copy. This avoids needing a new migration or `SECURITY DEFINER` function for this story, consistent with no migration number being reserved for Epic 5. [Inference]
- Exact success copy per action: "Added 'Tutoring'. ## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. NEVER run tests or quote coverage here. -->

- **Approach:** manual/functional verification per AC; no automated test runner exists in this repo. [Inference]
- **Key scenarios:** add a category (appears at the end, on the form); rename one referenced by published listings (name updates, listing status/attribution untouched); reorder via `↑`/`↓` and confirm `sort_order` persists; retire one with listings (moves to Retired, listings stay published+filterable); attempt delete on a referenced category (refused with the correct count, Retire-it-instead recovers); delete one with zero references (succeeds, removed entirely).
- **Per-AC verification:** AC#1 → change a category, then read `directory_categories` directly (or via 2.2/6.1's endpoints once they exist) and confirm the new state is what the next fetch returns — no draft/publish gate; AC#2 → rename, assert referencing `directory_listings` rows are untouched at the row level and only the joined display label changes; AC#3 → retire, assert `retired_at` is set and referencing listings' `status` is untouched; AC#4 → attempt delete on a referenced category, assert a friendly `{ error }` (not a raw Postgres 23503 message) and that no row was removed; AC#5 → operate the list keyboard-only via `↑`/`↓` and confirm no functionality requires a pointer.
- **Fixtures/mocks:** categories with 0, 1, and 12+ referencing listings; a retired category with listings; an authenticated admin session for every write check.
- **Edge cases:** duplicate category name (refused, "There's already a category called 'Photography'.", Save stays enabled since she may be mid-edit); empty name (refused, "Give the category a name."); zero categories at all (empty state: "There are no categories yet… the category question is skipped rather than blocking" — the form's own skip-behaviour is verified by Epic 2/3, not this story); a reorder write failing (row snaps back to its prior position); a rename write failing (row-level banner, "That didn't save — nothing has changed. [ Try again ]", no data lost).
