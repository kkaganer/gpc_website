# 8.4a: The data-requests queue — visible, deadline-sorted, one page load away

**Story ID:** 8.4a
**Epic:** 8 — Data rights and privacy
**Slug:** admin-data-requests-queue
**Status:** ready-for-dev
> **Split note:** the orchestrator-assigned story `8.4 admin-data-requests` covers both the queue
> and the erasure/action workflow; combined they exceed one dev-day once `erase_member()`'s
> typed-confirmation flow and email-then-delete ordering are counted. This story is the queue
> half; 8.4b (`admin-data-requests-actions`) is the per-request action workflow.

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As **Ash (an admin)**,
I want **every open unlist, unsubscribe and erasure request in one deadline-sorted list, the
moment a member submits one**,
so that **the site's published 20-working-day commitment is something I can actually see and
meet, not something I have to remember**.

## Acceptance Criteria

<!-- LOCKED. External dev tools must not edit Acceptance Criteria. -->

1. Given `GET /api/admin/data-requests` is called with a valid bearer token, then it returns open
   requests sorted overdue-first, then by ascending `deadline_on`, with `erase` ranked above
   `unlist` above `unsubscribe` within the same due date — and no row includes survey answers,
   postcode or any field beyond what the queue card needs to identify the member and the request.
2. Given the caller has no token, an invalid token, or an expired token, then the endpoint returns
   `401` with no data body.
3. Given `/admin/data-requests` loads, then it renders three `StatTile`s (Overdue, Due ≤5 working
   days, Open) computed over **all** open requests regardless of the active filter, plus a status
   filter (`Open | Completed | Cancelled`) and a type filter, both resetting the `PAGE_SIZE = 25`
   "Show 25 more" pagination when changed.
4. Given a request's `deadline_on` has passed, then its `DeadlinePill` renders explanatory text
   ("Overdue by N working days") — never colour alone — and that row sorts first in the Open view.
5. Given the sidebar, then a new "Data requests" entry links to `/admin/data-requests` without
   reordering or removing any existing `sidebarLinks` entry.
6. Given no requests match the active filter, then the page renders the specified empty-state
   copy instead of a blank list, while the stat tiles still render as `0` (not `—`) once the
   initial load has completed.

- **This route owns data-rights requests, not moderation.** "**A5: this route owns data-rights

  ```js
  if (!token) return res.status(401).json({ error: 'Not authenticated' })
  const { data: { user: caller }, error } = await supabase.auth.getUser(token)
  if (error || !caller) return res.status(401).json({ error: 'Invalid or expired session' })
  ```
  [Source: architecture.md#adr-003-authn-via-supabase-auth-authz-is-binary-with-attribution-instead-of-tiers].

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. NEVER run tests or quote coverage here. -->

- **Approach:** No automated test runner exists in this repo
  [Source: inputs/codebase-constraints-brief.md#1-stack--deployment-reality-non-negotiable].
  Verify the API against seeded `data_requests` rows spanning overdue, due-soon and comfortably-due
  cases; verify the UI by keyboard-only walkthrough of filters and pagination.
- **Key scenarios:** sort order is exactly overdue → due-ascending → kind priority; stat tiles never
  reflect the active filter; an expired/missing/malformed token is rejected before any query runs;
  the empty state renders for a filter with zero matches while tiles still show real numbers.
- **Per-AC verification:** AC #1 → seed rows spanning all three kinds with matching due dates and
  confirm the exact row order; AC #2 → three separate `curl` calls (no header, garbage token,
  token for a since-deleted user) each return `401` with an empty body; AC #3 → apply each filter
  and confirm the tile numbers are unchanged while the list changes; AC #4 → seed a row with a
  past `deadline_on` and confirm both the pill's rendered text and its position; AC #5 → diff
  `AdminLayout.jsx`'s `sidebarLinks` array before/after, confirming only one entry was added;
  AC #6 → filter to a combination with zero rows and confirm the specified copy, not an empty
  `<ul>`.
- **Fixtures / mocks:** seeded `data_requests` rows in `open`, `completed` and `cancelled` status,
  spanning `unlist`, `unsubscribe` and `erase`, with `deadline_on` values both in the past and
  several days out.
- **Edge cases to cover:** a request whose member has since been erased by another admin between
  page loads (the queue should still render the row using whatever `data_requests` retains, not
  crash on a missing member join — confirm the join is a `left join`/optional read, not one that
  drops the row); exactly 25 vs. exactly 26 open requests, to confirm the "Show 25 more" boundary.
