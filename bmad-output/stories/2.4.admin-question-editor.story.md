# 2.4: Admin question editor

**Story ID:** 2.4
**Epic:** 2 — Form configuration
**Slug:** admin-question-editor
**Status:** ready-for-dev

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As **Ash, a GPC admin**,
I want **to edit a question's wording and help text, toggle whether it's required, and add,
rename, reorder or retire its options**,
so that **I can fix a typo or keep the choice lists current without asking a developer for a
deploy, while every historical answer keeps reading correctly forever.**

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. Given an admin edits a question's label or help text and saves, when the draft is
   inspected, then the change is stored as **draft** content only — `GET /api/join/config`
   (2.2, which reads the published snapshot) continues returning the previously published
   text until 2.5's publish step runs.
2. Given the branch-key question (`group_choice`), when the admin opens its editor, then its
   "required" toggle is visibly present but disabled (`aria-disabled="true"`, still focusable,
   never hidden) with a permanently visible reason — this story's editor never lets an admin
   make the group choice optional, because every downstream branch depends on it.
3. Given an admin adds, renames or reorders an option on a choice question and saves, when the
   draft is inspected, then the change is present in the draft's option list with the correct
   `sort_order` — new options are appended live to the draft, never requiring a publish to
   become editable further.
4. Given an admin retires an option, then it is excluded from the draft's (and, once
   published, the public form's) live option list, but **every already-stored
   `member_submissions.answers` entry that used it keeps displaying its stored `{key, label}`
   snapshot unchanged** — retiring never rewrites a stored answer, per ADR-009. Restoring a
   retired option reverses only its own `retired_at` timestamp and never alters any snapshot.
5. Given the last remaining live (non-retired) option on a question, when the admin attempts to
   retire it, then the action is blocked with a permanently visible reason ("this question has
   to offer members something to choose. Add another option first.") rather than being
   silently unavailable with no explanation.
6. Given `listing_category`, when the admin opens its editor, then its options render as
   plain, non-editable text with a full-strength `[Manage categories →]` link to Epic 5's
   `/admin/directory/categories` — this editor never inserts, updates or retires a
   `directory_categories` row.

## Dev Notes

<!-- LOCKED. Concrete guidance compiled from the planning docs WITH SOURCE CITATIONS.
     Cite every fact: [Source: prd.md#anchor] / [Source: architecture.md#anchor] /
     [Source: ux-design.md#anchor]. Label your own inferences [Inference]. -->

**The retire guarantee, precisely — this is the load-bearing fact of this story.** ADR-009:
"`member_submissions.answers` is `jsonb`, keyed by `question_key`, and every choice answer
stores **both** [a stable `key`] and [a `label` snapshot]... `label` is the snapshot of what
the member actually saw — **the member record displays `label`** — so a retired option still
reads correctly years later."
[Source: architecture.md#adr-009-answers-store-option-keys-and-a-label-snapshot]. FR-008
states the acceptance criterion directly: "Given an option is retired, when existing
submissions are viewed, then their historical answers still display that option's label —
retiring never rewrites stored answers." [Source: prd.md#FR-008]. **Mechanically, this means
retiring/restoring an option is a `form_options.retired_at` write only** — it must never touch
`member_submissions.answers` in any way, and this story's `PUT` handler must not join against
that table for anything other than the read-only usage count. The UX draft's own framing:
"Retiring hides an option from the form. It never changes an answer anyone has already
given... Retiring is reversible; nothing here can be deleted."
[Source: EXPERIENCE.md#4-configuring-the-form — Screen S2 wireframe, "THE GUARANTEE"].

**Where an option can disagree with its stored snapshot.** "Where they disagree (an option
renamed since submission), the admin UI shows the current label and notes the change; it never
silently merges" [Source: architecture.md#adr-009-answers-store-option-keys-and-a-label-snapshot].
That admin-UI behaviour belongs to the **member record** view (Epic 7), not this editor — this
story only needs to guarantee the underlying data stays intact so Epic 7 can build that
comparison later; it does not render any stored-answer comparison itself.

**Vocabulary and tone, verbatim.** "Options are content and behave like content... *'Options
are just words on a list — add, rename, reorder and retire them as much as you like.'* —
while questions are structure and behave like structure."
[Source: EXPERIENCE.md#4-configuring-the-form]. Use *retire*, never *delete*; *question*,
never *field* or *block*. The permanent, non-dismissible explanation for why questions
themselves cannot be added/removed lives on 2.3's S1 screen, not repeated here in full, but
this screen's provenance strip must make clear the label/type/branch are read-only facts, not
controls [Source: EXPERIENCE.md#4-configuring-the-form — Screen S2 wireframe].

**The disabled-vs-absent rule (apply exactly).** "A capability that never exists for anyone
(add/delete/move a question, rewire branching, change a question's type) renders **no control
at all**... A capability that exists but is unavailable *for this specific thing right now*
(retire the last remaining option; make the branch-key question optional) renders **visible,
dimmed, `aria-disabled="true"` so it stays focusable, with a permanently visible reason beside
it**." [Source: EXPERIENCE.md#4-configuring-the-form — "The editing boundary, and what is
drafted vs live"]. AC #2 and #5 are both the *disabled-with-reason* case, not the *absent*
case — the toggle/button is always rendered.

**Required-toggle lock is narrower than it might look.** Only `group_choice` (the branch key)
is locked by **this** story, because it is the only registry (2.1) question whose
required-ness is structurally load-bearing — every branch depends on it having an answer
[Source: architecture.md#adr-008-form-configuration--code-defined-registry-database-overlay-and-versioned-publish].
`EXPERIENCE.md` also locks the *consent* question's required toggle with similar copy
[Source: EXPERIENCE.md#4-configuring-the-form — Screen S2 "Variants"], but consent is not a
registry entry (2.1's Dev Notes state this explicitly) and has no editor row here at all — do
not build a lock for a question that does not exist in this screen.

**Enter/⌘Enter option-input conventions** (Ash expects a spreadsheet-like flow): Enter in an
option input commits and moves to the next option; `⌘Enter` adds a new option; drag-to-reorder
is `@media (pointer: fine)`-only, with `▲ ▼` buttons as the guaranteed keyboard path at every
size [Source: EXPERIENCE.md#4-configuring-the-form — Screen S2 accessibility notes].

**Draft persistence is autosave, not a Save button** — 800ms after the last keystroke,
immediately on blur, immediately on any discrete action (retire/restore/reorder/add/toggle).
"Publish is the only button that means 'done'." [Source: EXPERIENCE.md#4-configuring-the-form
— "Cross-screen behaviour"]. The actual Publish button and its wiring belong to 2.5; this
story implements the autosave-on-change calls into `useFormConfigDraft.saveDraft()`.

**Admin-plane auth pattern** — identical bearer-token block to every other `/api/admin/*`
route, copied from `api/admin/subscribers.js:64-73`
[Source: architecture.md#adr-003-authn-via-supabase-auth-authz-is-binary-with-attribution-instead-of-tiers].
Every write records `actioned_by`/`actioned_at`.

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. NEVER run tests or quote coverage here. -->

- **Approach:** manual verification against a preview deployment seeded with at least one
  question that has stored answers referencing one of its options (so the retire guarantee is
  actually exercised, not merely asserted); no automated test runner exists in this repo (see
  2.1's Testing note).
- **Key scenarios:** retire an option with existing stored answers → draft/published option
  list excludes it, a direct read of the affected `member_submissions.answers` row is
  byte-for-byte unchanged; restore it → reappears in the option list, same unchanged
  guarantee; attempt to retire the last live option → blocked with the reason text, not a
  silent no-op; edit `group_choice`'s required toggle → confirm it cannot be turned off via
  either the UI or a direct `PUT` to the endpoint; open `listing_category` → confirm no
  add/rename/retire control renders and the manage-categories link is present.
- **Per-AC verification:** AC #1 → draft write does not appear in 2.2's published response
  until a publish (simulate by calling `GET /api/join/config` before and after the draft
  edit). AC #2 → toggle state and `aria-disabled`. AC #3 → option array order/content in the
  draft response. AC #4 → the byte-for-byte stored-answer check above, both directions
  (retire and restore). AC #5 → the last-option guard, both client attempt and a direct
  malicious `PUT` bypass attempt against the server. AC #6 → `listing_category`'s render mode
  and link target.
- **Fixtures/mocks:** at least one question with ≥2 options and ≥1 stored submission
  referencing one of them (for the retire guarantee); a question with exactly one live option
  (for the last-option guard); the `listing_category` registry entry.
- **Edge cases:** retiring an option that is currently mid-edit in the draft (renamed in the
  same session before being retired) — the retired row must carry the **new** draft label at
  retirement time, not the originally-published one, since retirement is itself a draft
  operation until published; two admins editing the same question concurrently is out of
  scope for this story (2.5 owns the publish-conflict message).
