# 1.1: Directory core migration — members, submissions, listings, categories

**Story ID:** 1.1
**Epic:** 1 — Data foundation
**Slug:** directory-core-migration
**Status:** ready-for-dev

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As **the system** (no code depends on it yet, but every later epic will),
I want **the core schema — `members`, `member_submissions`, `directory_listings`, `directory_categories` — to exist in Postgres with the public/private boundary enforced at the RLS and column-grant level**,
so that **no later story can accidentally write member data from the browser or read private fields with the anon key, because the boundary is structural, not a convention someone might forget**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. Given migration `028_directory_core.sql` is applied, when the schema is inspected (`\d members`, `\d member_submissions`, `\d directory_listings`, `\d directory_categories`), then all four tables exist with the exact columns, types and constraints specified in Dev Notes — `uuid` primary keys via `gen_random_uuid()`, `timestamptz` columns, and `status` as `text` + `CHECK`, never a Postgres ENUM.
2. Given an unauthenticated client queries `directory_listings` with the anon key using `select=*`, when the query executes, then only the nine granted columns (`id, slug, business_name, category_id, description, website_url, instagram_url, enquiry_email, published_at`) are returned; explicitly requesting `member_id`, `status`, `reject_reason`, any `submitted_*` column, `actioned_by` or `actioned_at` is rejected by Postgres with a permission error, not silently omitted.
3. Given an unauthenticated client queries `directory_listings` for a row whose `status` is not `'published'`, when the query executes, then zero rows are returned for it, regardless of which columns are requested.
4. Given an unauthenticated client queries `members` or `member_submissions` directly with the anon key, when the query executes, then zero rows are returned and no policy grants any access — RLS is enabled with no `anon` policy on either table.
5. Given an unauthenticated client queries `directory_categories`, when the query executes, then every category (including retired ones) is readable in full, because the table holds no personal data.
6. Given migration `028_directory_core.sql` is applied a second time against a database where it has already run, when `supabase db push` executes, then it completes with no error and no duplicate objects (every statement is idempotent).

### Why the split, and why column grants on top of it

`directory_listings` is the **only** public-readable table this feature adds. Its column list must contain no column capable of holding personal data — that is the entire guarantee ADR-001 buys, and it must be verifiable by reading one `create table` statement [Source: architecture.md#adr-001-split-public-and-private-data-across-separate-tables-and-revoke-column-access-on-the-public-one]. RLS alone cannot express "public columns, private columns" on one table — Postgres RLS is row-level, and PostgREST honours `select=*`, so a caller can always ask for every column a table grants [Source: architecture.md#adr-001-split-public-and-private-data-across-separate-tables-and-revoke-column-access-on-the-public-one]. This codebase has already shipped the "view over a private table" failure mode once, in production (`018_secure_ingest_batch_status.sql`) [Source: inputs/codebase-constraints-brief.md#3-the-publicprivate-boundary--how-it-is-actually-enforced]. **No view is ever used as a public projection here.**

The column-grant pair is the second, defence-in-depth layer, quoted verbatim from the architecture doc:

```sql
revoke select on directory_listings from anon;
grant select (id, slug, business_name, category_id, description,
              website_url, instagram_url, enquiry_email, published_at)
  on directory_listings to anon;
```
[Source: architecture.md#adr-001-split-public-and-private-data-across-separate-tables-and-revoke-column-access-on-the-public-one]

Row visibility is still separately gated by RLS:
```sql
create policy "Public can view published listings" on directory_listings
  for select using (status = 'published');
```
[Source: architecture.md#adr-001-split-public-and-private-data-across-separate-tables-and-revoke-column-access-on-the-public-one]

`members` and `member_submissions` are **private**: RLS enabled, no `anon` policy at all [Source: architecture.md#adr-001-split-public-and-private-data-across-separate-tables-and-revoke-column-access-on-the-public-one]. This story goes one step further than "no anon policy" and adds **no `authenticated` policy either** — every component that reads these tables (`GET /api/admin/members`, `GET /api/admin/members/:id`, the submission service) does so through a service-role client inside a bearer-token-verified `/api/admin/*` route, never a direct browser Supabase call [Source: architecture.md#4-component-design]. Since `service_role` bypasses RLS entirely, zero policies is sufficient and is the tightest posture available — nothing needs to reason about what an `authenticated` session could see if it queried these tables directly, because there is nothing granted to see. [Inference — architecture.md's own phrase is "no anon policy at all"; omitting an authenticated policy too is a stricter reading that costs nothing given every private read goes through service-role, and matches "any new database object defaults closed".]

**`directory_categories` is publicly readable, resolved deliberately.** ADR-001's one-line framing ("`directory_listings` is the ONLY public-readable table") and §5's Data Model entity description ("Publicly readable — the directory filter needs it") appear to be in tension. This is resolved in favour of §5: `directory_categories` holds **no personal data at all** (`key`, `label`, `sort_order`, `retired_at`), the public directory index component is explicitly documented as having "No API route" for its reads [Source: architecture.md#component-directory-public], and Epic 6 (`6.1 directory-index`) is blocked only by `1.1` and `5.3`, not by `1.3` or any admin API — meaning the category filter must be able to read this table directly with the anon key. The unconditional-read shape matches the existing `term_dates` precedent (`for select using (true)`) [Source: inputs/codebase-constraints-brief.md#3-the-publicprivate-boundary--how-it-is-actually-enforced]. [Inference — flagging this resolution explicitly since it reads against the compressed one-line ADR-001 summary; surfaced to the orchestrator.]

### `members` — private

```sql
create extension if not exists citext;

create table if not exists members (
  id           uuid primary key default gen_random_uuid(),
  first_name   text not null,
  email        citext not null unique,
  postcode     text,
  heard_about  text,
  group_choice text not null check (group_choice in ('business_mums','career_mums','both')),
  erased_at    timestamptz,
  created_at   timestamptz not null default now(),
  updated_at   timestamptz not null default now()
);

create trigger members_set_updated_at
  before update on members
  for each row execute function update_updated_at();

alter table members enable row level security;
-- No anon policy, no authenticated policy: every read/write of this table happens
-- via a service-role client behind a bearer-token-verified /api/admin/* route or
-- POST /api/join/submit. Nothing is granted, deliberately.
```
Column set, uniqueness on `email`, and `group_choice` vocabulary are from the Data Model [Source: architecture.md#entity-members--private]. Unique `email` is what makes FR-007 resubmission an upsert rather than a duplicate row [Source: architecture.md#entity-members--private]. `citext` is not used anywhere else in this schema yet; enabling the extension idempotently is this story's addition. [Inference]

### `member_submissions` — private

```sql
create table if not exists member_submissions (
  id                 uuid primary key default gen_random_uuid(),
  member_id          uuid not null references members(id) on delete cascade,
  answers            jsonb not null default '{}'::jsonb,
  form_config_version text not null,
  idempotency_key    text not null unique,
  submitted_at       timestamptz not null default now()
);

alter table member_submissions enable row level security;
-- No anon policy, no authenticated policy — same posture as members.
```
One row per submission event, so a resubmission is an additional row and history is intact [Source: architecture.md#entity-member_submissions--private]. `answers` is `jsonb` keyed by `question_key`; every choice answer is `{key, label}` — enforced at the one write path in Epic 4, not by a DB constraint here [Source: architecture.md#adr-009-answers-store-option-keys-and-a-label-snapshot]. `idempotency_key` unique is what makes a client retry after a timeout safe rather than a second member [Source: architecture.md#component-join-form-public].

### `directory_categories`

```sql
create table if not exists directory_categories (
  id         uuid primary key default gen_random_uuid(),
  key        text not null unique,
  label      text not null,
  sort_order integer not null default 0,
  retired_at timestamptz,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

create trigger directory_categories_set_updated_at
  before update on directory_categories
  for each row execute function update_updated_at();

alter table directory_categories enable row level security;

create policy "Public can view categories" on directory_categories
  for select using (true);

create policy "Authenticated can manage categories" on directory_categories
  for all to authenticated using (true) with check (true);
```
Retire, never delete, while listings reference it; delete permitted only at zero references — that constraint is enforced by Epic 5's category-management story (`5.4`), not by DB-level `ON DELETE RESTRICT` in this migration, since deletion itself is an admin API concern [Source: prd.md#FR-017]. [Inference — this migration only creates the table and its RLS/read shape; the "cannot delete while referenced" business rule is application logic for 5.4 to implement, most simply by checking references before issuing a delete.]

### `directory_listings` — the only public-readable table

```sql
create table if not exists directory_listings (
  id                        uuid primary key default gen_random_uuid(),
  member_id                 uuid not null references members(id) on delete cascade,
  slug                      text unique,
  business_name             text not null,
  category_id               uuid references directory_categories(id),
  description               text not null,
  website_url               text,
  instagram_url             text,
  enquiry_email             text not null,
  status                    text not null default 'pending'
                              check (status in ('pending','published','held','rejected','unpublished')),
  reject_reason             text,
  submitted_business_name   text,
  submitted_category_id     uuid references directory_categories(id),
  submitted_description     text,
  submitted_website_url     text,
  submitted_instagram_url   text,
  submitted_enquiry_email   text,
  published_at              timestamptz,
  actioned_by               uuid,
  actioned_at               timestamptz,
  created_at                timestamptz not null default now(),
  updated_at                timestamptz not null default now()
);

create unique index if not exists directory_listings_slug_uidx on directory_listings (slug);
create index if not exists directory_listings_status_published_idx
  on directory_listings (status, published_at desc);
create index if not exists directory_listings_member_id_idx on directory_listings (member_id);

create trigger directory_listings_set_updated_at
  before update on directory_listings
  for each row execute function update_updated_at();

alter table directory_listings enable row level security;

create policy "Public can view published listings" on directory_listings
  for select using (status = 'published');

create policy "Authenticated can manage listings" on directory_listings
  for all to authenticated using (true) with check (true);

revoke select on directory_listings from anon;
grant select (id, slug, business_name, category_id, description,
              website_url, instagram_url, enquiry_email, published_at)
  on directory_listings to anon;
```

Column list and cascade behaviour are from the Data Model table verbatim: `member_id` cascades so erasure removes the listing and it "cannot outlive the erasure" [Source: architecture.md#entity-directory_listings--the-only-public-readable-table]. `slug` is nullable and generated **once, at first publication**, never regenerated — this migration only reserves the column and its uniqueness; slug generation logic is Epic 5's / Epic 4's concern, reusing the pattern in `src/hooks/useEventMutations.js` [Source: architecture.md#adr-013-listing-slugs-are-generated-once-and-never-regenerate]. The `submitted_*` shadow columns serve two purposes: preserving the member's original values distinct from admin edits (FR-016), and holding a pending resubmission's new answers without touching what is currently published (FR-007) — both documented as "populates `submitted_*` columns alongside the published ones" [Source: architecture.md#adr-012-moderation-is-a-text-status-vocabulary-with-a-reason-not-a-boolean]. The full six-field shadow set (`submitted_business_name`, `submitted_category_id`, `submitted_description`, `submitted_website_url`, `submitted_instagram_url`, `submitted_enquiry_email`) mirrors every editable public field one-for-one; the source abbreviates this as `submitted_*` [Inference — filling in the concrete field list from the abbreviation]. `status` uses the ADR-012 vocabulary exactly; `reject_reason` is left as plain `text` with no CHECK — the source names "a key vocabulary plus free text" but does not enumerate the keys, and defining that vocabulary is Epic 5's (`5.3`) job; a follow-on migration (032+) can add a constrained key column later if needed [Inference]. `"Authenticated can manage listings"` copies the `activities`/`008_discovery_platform.sql:298-311` precedent [Source: inputs/codebase-constraints-brief.md#3-the-publicprivate-boundary--how-it-is-actually-enforced].
