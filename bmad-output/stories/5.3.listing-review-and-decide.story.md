# 5.3: Listing review & edit — submitted-vs-published, attribution, and decide-from-here

**Story ID:** 5.3
**Epic:** 5 — Moderation and shared admin
**Slug:** listing-review-and-decide
**Status:** ready-for-dev

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As **Ash (GPC admin)**,
I want **to open one listing, see her submitted values next to what's about to go public, correct the public fields, and decide — or take a live listing down — from the same screen**,
so that **I can fix a small mistake without rejecting a good listing, and editing never accidentally re-opens moderation on something already live**.

## Acceptance Criteria

<!-- LOCKED. External dev tools must not edit Acceptance Criteria. -->

1. Given an admin opens `/admin/directory/:id`, when it loads, then the six public fields (business name, category, description, website, Instagram, enquiry contact) render pre-filled with their current values, each paired with the member's originally submitted value shown separately and distinguishably — an "unchanged" line when they match, an edited-diff panel with **"Use her version"** when they differ.
2. Given an admin edits one or more public fields and clicks **"Save only"** (pending) or **"Save changes"** (already published), when the save succeeds, then the listing's `status` is unchanged — a published listing stays published — and the edit is attributed (`actioned_by`/`actioned_at` updated) without touching moderation state.
3. Given an admin edits fields on a pending listing and clicks **"Save and publish"**, when it succeeds, then the public-field edit is saved and the listing is published in the same user action.
4. Given the private "Member details" panel, when it renders, then it is visually distinct (dashed border, "Private — never published. This is the admin panel, so you can see it here." as its first line), and no control anywhere on the screen writes a private value into a public field.
5. Given a published listing, when the admin clicks **"Take it down"**, then the Decision Dialog reused from 5.2b opens with take-down reasons, and confirming unpublishes it with a recorded, attributed reason while the member record is left untouched.
6. Given the admin has unsaved edits, when they attempt to navigate away, then a confirmation dialog offers **"Leave without saving"** / **"Stay here"**, and pressing Enter inside a text field never triggers Publish — the form's default submit is **"Save only"**.

## Dev Notes

<!-- LOCKED. Concrete guidance compiled from the planning docs WITH SOURCE CITATIONS.

- FR-016 acceptance criteria, verbatim: edited public fields render on the public directory; the member's originally submitted values stay visible and distinguishable on the member record; editing a published listing keeps it published ("editing is not a re-approval"); edits are attributed to an admin and dated. [Source: prd.md#FR-016]
- "Admin edits do not re-open moderation." The member's originally submitted values are retained in `submitted_business_name`, `submitted_description` etc. so both remain visible and distinguishable — this screen is where that retention becomes visible. [Source: architecture.md#adr-012-moderation-is-a-text-status-vocabulary-with-a-reason-not-a-boolean]
- **Renaming does not change the slug.** `slug` is generated once at first publication and never regenerated; renaming changes `business_name` only. A regenerating slug would break every previously shared link and every link in every already-sent email. On-screen copy for this: "Renaming changes the display name only — the web address stays the same, so links already shared still work." with a **"Use her version"** recovery. [Source: architecture.md#adr-013-listing-slugs-are-generated-once-and-never-regenerate]; copy at [Source: EXPERIENCE.md#screen-m-s2--listing-review--edit]
- Attribution (NFR-013): "100% of publish, reject, unpublish, edit and erasure actions record the acting admin and a UTC timestamp, retrievable per listing." [Source: prd.md#NFR-013] Displayed as "Published by Ash Nolan · 18 Aug 2026, 14:07" — actor from `user_metadata.full_name`, falling back to the account email (in `title`, so two Ashes stay distinct); `<time datetime>` rendered local; member-originated entries read "the member, via /join"; history is append-only, no edit/delete control. [Source: EXPERIENCE.md#3-moderating-the-directory] "Attribution" bullet.
- The six editable public fields: `business_name`, `category_id`, `description` (≤300 chars, server-enforced), `website_url`, `instagram_url`, `enquiry_email`. [Source: architecture.md#5-data-model] entity `directory_listings`; screen layout at [Source: EXPERIENCE.md#screen-m-s2--listing-review--edit]
- Private-data boundary, three testable rules restated for this screen: private values never render inside the public-fields region; no control copies a private value into a public field; no copy/export affordance on this screen emits anything but public fields. [Source: EXPERIENCE.md#3-moderating-the-directory] "The private-data boundary" bullet.
- "Save and publish" is implemented as two calls (`PUT` then `POST .../:id/action`), not a combined endpoint — this keeps 5.2a's action endpoint single-purpose (status transitions only) and this story's edit endpoint single-purpose (content only). [Inference]
- Take-down reuses 5.2b's `DecisionDialog` + 5.2a's unpublish reason vocabulary (`member_request`/`complaint`/`closed`/`details_wrong`/`policy`/`other`; email default on except `member_request`, since she asked — telling her again is noise). [Source: EXPERIENCE.md#screen-m-s3--decision-dialog]
- Unsaved-changes guard, verbatim copy: "Leave without saving? Your edits to 2 fields will be lost." — confirm **"Leave without saving"**, cancel **"Stay here"**. Escape inside a dialog cancels; Escape outside a dialog does nothing, because it must never discard edits. [Source: EXPERIENCE.md#screen-m-s2--listing-review--edit] accessibility paragraph.
- The `<form>`'s default submit is **Save only**, never Publish, so pressing Enter in a text field cannot publish. `aria-describedby` chains label → helper → counter → original-value panel. [Source: EXPERIENCE.md#screen-m-s2--listing-review--edit] accessibility paragraph.
- Bidirectional member↔listing links (A17): this screen links to `/admin/members/:id`; the member record (Epic 7, story 7.2) links back here. `/admin/members/:id` does not exist yet at the time this story ships — render the link, but expect it to 404 until 7.2 lands; do not block this story on Epic 7. [Source: EXPERIENCE.md#screen-m-s2--listing-review--edit] "View full member record →"; scope boundary [Inference]
- Resubmission variant: the same screen holds the *proposed* values as the public fields and the *currently published* values as the "originals" gutter, so a resubmission is a diff on this same screen, not a new one. The resubmission-detection/upsert logic itself is Epic 4's (story 4.4), not this story's — this story only needs to render whichever `submitted_*` vs published diff the data already contains. [Source: EXPERIENCE.md#3-moderating-the-directory] "Re-submitted against a published listing" table row; scope boundary [Inference]
- Column-shape gap (carried from 5.2a): architecture's data model names `submitted_business_name` and `submitted_description` explicitly and says "submitted_*" for the rest; this story assumes one `submitted_` shadow column per public field. Confirm against the actual 1.1 migration once written. [Inference]

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. NEVER run tests or quote coverage here. -->

- **Approach:** manual/functional verification per AC; no automated test runner exists in this repo. [Inference]
- **Key scenarios:** open a listing where nothing has been edited (every field shows "unchanged"); edit two fields and "Save only" (status unchanged, attribution updated, dirty-count clears on save); edit + "Save and publish" on a pending listing (both writes land, in order); "Take it down" on a published listing (unpublish + reason + member record untouched); navigate away with dirty fields (guard fires; both recovery paths behave as specified); press Enter in a text field (never publishes).
- **Per-AC verification:** AC#1 → seed a listing with two `submitted_*` values differing from the published values, assert both render side-by-side with correct "unchanged"/"edited" presentation; AC#2 → `PUT` an edit, assert `status` untouched in the DB and `actioned_by`/`actioned_at` updated; AC#3 → `PUT` then `POST .../:id/action` publish, assert `published_at` set and the edited fields are what a public (anon-key) read now returns; AC#4 → assert the private panel's DOM subtree never contains a public-field `<input>`, and no button handler writes a private value into a public field; AC#5 → unpublish, assert an anon-key read no longer returns the row while `members`/`member_submissions` rows are untouched; AC#6 → attempt navigation with a dirty form and confirm the guard fires with both recovery paths working.
- **Fixtures/mocks:** one pending listing with `submitted_*` equal to its current values; one pending listing with a diff; one published listing; a resubmission fixture (published listing + a pending `submitted_*` diff) to exercise the diff-variant rendering; a mock authenticated session.
- **Edge cases:** a bad/removed `id` (404 "We can't find that listing. It may have been removed. [ Back to the queue ]"); save failing mid-edit (fields stay populated, banner "That didn't save. Your changes are still on screen — try again."); a concurrent-edit conflict (two admins editing the same row — banner with "See what changed" / "Reload and lose my edits"); Publish blocked when publish-consent is absent (Publish stays visible, disabled with a reachable reason via `aria-describedby`).
