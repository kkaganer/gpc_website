## Story

As **the admin panel, on Ash's behalf**,
I want **one bounded list endpoint over every directory-listing status and one endpoint that records a publish/hold/reject/unpublish decision with attribution and a queued notification**,
so that **the queue screen (5.2b) and the listing review screen (5.3) build against a single, tested contract instead of each inventing its own moderation write path**.

## Acceptance Criteria

<!-- LOCKED. External dev tools must not edit Acceptance Criteria. -->

1. Given a caller with no bearer token, an invalid token, or an expired token, when `GET /api/admin/directory` or `POST /api/admin/directory/:id/action` is called, then it returns `401` with no data body.
2. Given an authenticated `GET /api/admin/directory?status=pending&offset=0`, when it resolves, then it returns at most `PAGE_SIZE = 25` listings for that status ordered oldest-first, plus a separate exact count per status for the tab badges — never an unbounded result set.
3. Given an authenticated `POST /api/admin/directory/:id/action` with `{ action: 'publish' }`, when it resolves, then the listing's `status` becomes `published`, `published_at`/`actioned_by`/`actioned_at` are recorded, and a `queued` `outbound_emails` row is inserted with `template_key: 'published'` — publishing never requires a reason.
4. Given the same endpoint with `{ action: 'hold' | 'reject' | 'unpublish', reasonKey, reason? }`, when it resolves, then the listing's `status` becomes `held` / `rejected` / `unpublished` respectively, the reason is recorded, `actioned_by`/`actioned_at` are set, and — for `reject` and `unpublish` (except the `member_request` take-down reason, which is silent by design) — a `queued` `outbound_emails` row is inserted with the matching `template_key` and reason in its payload.
5. Given any action targeting a listing that does not exist, or an `action` value outside `publish | hold | reject | unpublish`, when the request is made, then the endpoint returns a clear `{ error }` with an appropriate status (`404` / `400`) rather than a silent no-op or an unhandled `500`.

## Tasks / Subtasks

- [ ] `GET /api/admin/directory`: verbatim auth block, `status`/`offset`/`limit` query params, ranged query oldest-first, one `count: 'exact', head: true` query per status for tab badges (AC: #1, #2)
- [ ] `POST /api/admin/directory/:id/action`: verbatim auth block, validate `action` against the fixed enum, `404` on a missing listing (AC: #1, #5)
- [ ] Status-transition write: update `directory_listings.status` + `actioned_by` + `actioned_at`, plus `published_at` on publish, plus the reason on hold/reject/unpublish (AC: #3, #4)
- [ ] `outbound_emails` insert (`status: 'queued'`, `template_key`, `payload: { listing_id, slug, reason_key }`, `to_member_id`) for publish/reject/unpublish per the template map; no row for hold (admin-internal) or a `spam` reject (no email by design) (AC: #3, #4)
- [ ] Build `api/_lib/moderationReasons.js`: module-scope maps of reason key → chip label → member-email sentence for hold/reject/unpublish, shared with 5.2b's Decision Dialog and 5.5a's templates (AC: #4)
- [ ] Wrap the whole handler in try/catch, `{ error }` + status on every failure path (AC: #5)

- Route contract: `GET /api/admin/directory` (list); `POST /api/admin/directory/:id/action` with `{ action: 'publish'|'hold'|'reject'|'unpublish', reason?, reasonKey? }`, writing the status transition, `actioned_by`, `actioned_at`, and an `outbound_emails` row "in one transaction" — send failure never rolls it back. [Source: architecture.md#6-api-specifications]
- Auth block, verbatim, to open every handler: `const token = req.headers.authorization?.replace('Bearer ', '')`, `401` if absent, then `supabase.auth.getUser(token)`, `401` on error/no user. Existing precedent to copy: `api/admin/subscribers.js:65-73`. [Source: architecture.md#adr-003-authn-via-supabase-auth-authz-is-binary-with-attribution-instead-of-tiers]; [Source: inputs/codebase-constraints-brief.md#3-the-publicprivate-boundary]
- Status vocabulary is `text` + `CHECK (status in ('pending','published','held','rejected','unpublished'))`, never a boolean; only `published` is public; every transition writes `actioned_by`/`actioned_at`, and — for `reject` — `reject_reason`. Admin edits (5.3) never re-open moderation; this endpoint only changes `status`, never the public content fields. [Source: architecture.md#adr-012-moderation-is-a-text-status-vocabulary-with-a-reason-not-a-boolean]
- `directory_listings` columns relevant here: `status`, `reject_reason`, `published_at`, `actioned_by`, `actioned_at`. [Source: architecture.md#5-data-model] **Column-shape gap:** the data model names only `reject_reason`; there is no documented separate column for a hold- or unpublish-reason. This story reuses `reject_reason` as the generic decision-reason column for hold/reject/unpublish alike, pending confirmation against the actual migration `028_directory_core.sql` (owned by story 1.1). [Inference — flagged]
- `outbound_emails` shape: `status text check (queued|sent|failed|given_up|not_applicable)`, `to_member_id`, `template_key`, `payload jsonb`, `attempts int`, `last_error text`, `last_attempt_at`, `sent_at`; `payload` holds only what a template needs (listing id, slug, reason key) — no personal data beyond the recipient reference. The moderation decision commits regardless of send outcome; the *send* is not part of this write, and is out of this story's scope (owned by 5.5a). [Source: architecture.md#adr-014-outbound-email-is-a-queue-table-drained-by-a-pluggable-sender]
- **No `SECURITY DEFINER` function exists yet for a combined status-update + queue-insert write.** Epic 1's reserved migrations (`028`-`031`) do not include one, and no migration number is reserved for Epic 5. [Source: sharding-context.md#locked-cross-cutting-decisions--every-story-inherits-these] item 2 ("Migrations 028–031 are reserved — do not invent new numbers"). This story therefore performs the status update and the `outbound_emails` insert as two sequential service-role writes inside one handler — not a formal Postgres transaction. This is a genuine atomicity gap versus ADR-014's "same transaction" language; flagged for the orchestrator/architecture owner rather than solved here by inventing a new migration outside this story's scope. [Inference]
- `PAGE_SIZE = 25`, ranged (`range(0, n*25 - 1)`), oldest-first; tab counts via a separate `count: 'exact', head: true` query "so a badge never costs a page of rows." [Source: architecture.md#component-moderation-admin]; [Source: EXPERIENCE.md#3-moderating-the-directory] "Bounded fetch" bullet.
- Reason vocabularies (chip label + member-email sentence), module-scope, exact keys: **Reject** — `incomplete` "Not enough detail to publish" · `contact_unsafe` "The public contact is a personal address" · `not_a_business` "This isn't a business listing" · `duplicate` "Duplicate of a listing we already have" · `not_appropriate` "Not a fit for the GPC directory" · `spam` (no email) · `other` (verbatim free text). **Hold** — `awaiting_member` · `second_opinion` · `needs_editing` · `other`; email defaults **off**. **Take down (unpublish)** — `member_request` · `complaint` · `closed` · `details_wrong` · `policy` · `other`; email defaults **on** except `member_request`. [Source: EXPERIENCE.md#screen-m-s3--decision-dialog]
- Error/response convention: every response JSON, `{ error: string }` + status on failure, every handler try/catch, status codes `400/401/404/409/429/500` as appropriate. [Source: architecture.md#adr-005-error-and-response-convention]
- No personal data in server logs — log the listing/member `id` only, never name/email. [Source: architecture.md#adr-004-one-trusted-server-write-path-the-browser-never-writes-member-data] (logging rule, applied here by extension since this is also a service-role admin path) [Inference]

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. NEVER run tests or quote coverage here. -->

- **Approach:** integration-style checks against the two routes directly (request/response, not through the UI), since this story has no UI of its own; no automated test runner exists in this repo, so verification is manual/scripted `fetch` calls plus a code-review pass. [Inference]
- **Key scenarios:** each of the four actions against a `pending` fixture; publish requiring no reason; reject/hold/unpublish each with a canned `reasonKey` and with `other` + free text; a `spam` reject producing no `outbound_emails` row; a `member_request` unpublish producing no `outbound_emails` row; every other reject/unpublish reason producing exactly one `queued` row with the right `template_key`; pagination across a >25-row status; tab counts matching the true total regardless of the page fetched; missing/invalid/expired bearer token on both routes.
- **Per-AC verification:** AC#1 → call both routes with no header, a garbage token, and a stale token, assert `401` + empty body each time; AC#2 → seed 30 pending rows, assert the first page returns exactly 25 oldest-first and the status counts equal 30; AC#3 → publish a fixture, assert `status/published_at/actioned_by/actioned_at` and exactly one queued `outbound_emails` row with `template_key: 'published'`; AC#4 → run each of hold/reject/unpublish with each reason key, assert `status`/`reject_reason` and the presence/absence of an `outbound_emails` row per the silent-reason rules; AC#5 → call with a random uuid (404) and with `action: 'archive'` (400).
- **Fixtures/mocks:** seeded `directory_listings` rows in `pending` and `published` states; a valid/invalid/expired Supabase session token for the auth checks; a member row for `to_member_id`.
- **Edge cases:** publishing a listing that has already been unpublished by another admin in the interim (stale-UI double-action — decide whether this is idempotent or a conflict, and document the chosen behaviour in the Dev Agent Record); a reject with `reasonKey: 'other'` and an empty free-text field (should this route reject with `400`, or is empty-note validation a UI-only concern owned by 5.2b's Decision Dialog — record the decision made); the sequential-write gap above under a mid-request crash (status updates but the `outbound_emails` insert fails) — confirm the decision still stands and note the send-status implication for 5.5a.
