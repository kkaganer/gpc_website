# 7.4: Insights view

**Story ID:** 7.4
**Epic:** 7 — Member records and insights
**Slug:** insights-view
**Status:** ready-for-dev

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As **Ash, a GPC admin**,
I want **one screen that turns member answers into a plain-English answer card, a readable day/time
grid, and a paste-able summary**,
so that **I can pick the next event's day, slot and cadence from evidence in under three minutes,
without exporting anything or interpreting a chart**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. Given `/admin/insights` loads with data available, then a response-base banner stating the total
   member count renders before any filter or block, and it states plainly that not every member
   answered every question.
2. Given the page has rendered, then the "When to run it" answer card names the single best
   day/time slot (or every tied slot, if more than one ties for first) as both an absolute count
   and a percentage of the response base — never an arbitrary tiebreak.
3. Given the viewport is `≥768px`, when the day/time data renders, then it appears as a 7×3 grid
   (days × morning/afternoon/evening) where every cell shows its count and share as visible text
   and the highest cell is marked "Best" in text as well as visually — colour is never the only
   carrier of that information.
4. Given the viewport is `<768px`, when the same data renders, then it appears as a ranked list of
   all 21 slots, highest first; the same ranked list remains reachable at every width behind a
   closed-by-default "Show all 21 slots as a list" disclosure.
5. Given the admin sets the group filter or the "Interested in" cross-filter, when the aggregation
   recalculates, then every block updates to the filtered response base and restates its own base
   line — no block ever renders without a base line.
6. Given the filtered response base is between 1 and 9 members, then the answer card is replaced by
   a small-base caution message while other blocks still render with their own bases; given the
   filtered base is 0, then blocks are suppressed in favour of a "no members match this filter" state
   with a "Clear filters" control, and the banner still states the unfiltered total.
7. Given the admin presses "Copy summary", when it completes, then a plain-text, counts-only summary
   (no names, no emails) is written to the clipboard and an inline confirmation appears beside the
   button — never a toast.

## Dev Notes

<!-- LOCKED. Concrete guidance compiled from the planning docs WITH SOURCE CITATIONS.
     Cite every fact: [Source: prd.md#anchor] / [Source: architecture.md#anchor] /
     [Source: ux-design.md#anchor]. Label your own inferences [Inference]. -->

**Why this screen exists at all.** "This journey is the entire payback for the length of the form —
if it fails, every survey question on `/join` is unjustified collection under NFR-006... The answer
card is the requirement, not decoration — if it is cut for scope, FR-014 has not been delivered
whatever else ships" [Source: EXPERIENCE.md#5-member-records-and-demand-insights]. Do not treat the
answer card (AC #2) as optional polish relative to the grid.

**Data contract.** This story consumes `GET /api/admin/insights` built in 7.3 and performs **no
aggregation client-side** — every count this page displays is read directly from that endpoint's
response, per ADR-007's "raw member rows never reach the browser for aggregation"
[Source: architecture.md#adr-007-client-state--hand-rolled-hooks-fetch-once-filter-client-side].

**The 7×3 grid — owned entirely by this story.** "The 21 ranked bars are **replaced by the 7×3
day/time heat grid** — the one visualisation this section keeps, because it is what makes the
form's 21-option question worth having asked" at `≥768px`
[Source: EXPERIENCE.md#5-member-records-and-demand-insights]. At `320px` "seven columns leave ~40px
each, which cannot carry a readable number, so mobile gets the ranked bar list — strictly better
for 'which slot wins?' and the same data. The ranked list stays available at every width behind a
disclosure, so nobody has to read colour to get the answer"
[Source: EXPERIENCE.md#5-member-records-and-demand-insights].

**Heat ramp — exact values, do not invent alternatives.** Six steps banded on each cell's share of
the maximum cell, every step's printed number clearing AA against its own background:
L0 (0 responses) `#6b7280` on `#ffffff` 4.83:1 · L1 (1–20%) `#1a1a2e` on `#f4effa` 15.09:1 · L2
(21–40%) `#1a1a2e` on `#e9def7` 13.20:1 · L3 (41–60%) `#1a1a2e` on `#cbb6e8` 9.26:1 · L4 (61–80%)
`#ffffff` on `#6d5296` 6.37:1 · L5 (81–100%) `#ffffff` on `#2d1b4e` 15.24:1. Text colour flips
between L3 and L4, and no step may sit in the luminance band between them
[Source: EXPERIENCE.md#5-member-records-and-demand-insights]. The best-cell outline is `#fc16a0`
drawn **only** on the L5 background `#2d1b4e` (≈4.0:1, clearing the 3:1 non-text WCAG 1.4.11
threshold) — this pairing never renders on white, so DESIGN.md §3.1's 3.64:1 figure for `#fc16a0`
on white does not apply here and must not be used as the justification
[Source: EXPERIENCE.md#5-member-records-and-demand-insights],
[Source: DESIGN.md#3-wcag-21-aa-contract]. Bars use `#fc16a0` fill on `#f4effa` track (3.22:1,
non-text) and carry no text inside them; every cell's count and share is printed as real text
regardless [Source: EXPERIENCE.md#5-member-records-and-demand-insights].

**Labels are never hard-coded.** "Insights reads every question label, option label and the three
slot names from the currently *published* form config... There is no `SLOT_LABELS` constant
anywhere in this feature; if the published config has not yet named the three slots, the block
renders the config's raw option labels rather than inventing 'Morning / Afternoon / Evening'"
[Source: EXPERIENCE.md#5-member-records-and-demand-insights]. This story reads whatever label
strings 7.3's endpoint returns — it must not define its own label constants.

**Tie handling, small-base caution, and multi-select caveats are specified copy, not paraphrase:**
- Two slots tie: **"Best slots: Tuesday morning and Thursday morning — 81 of 132 (61%) each."**
- Filtered base 1–9: **"Only 7 members match this filter. That's too few to plan from — widen the
  filter, or treat this as a hint rather than evidence."**
- Filtered base 0: **"No members match this filter yet."** + **"Clear filters"**; blocks suppressed,
  not rendered as rows of zeros; the banner still states the unfiltered total.
- Group = "Career Mums": the business-demand panel renders **"No business-branch members in this
  view"** rather than vanishing.
- Multi-select blocks: **"Members could pick more than one, so these add up to more than 100%."**
  Single-choice blocks: **"One answer each, so these add up to 100%."**
[Source: EXPERIENCE.md#5-member-records-and-demand-insights]. Reproduce this copy; it is the
recovery path for the "average-of-everyone" and "small-base overconfidence" failure modes the UX
plan calls out by name [Source: EXPERIENCE.md#5-member-records-and-demand-insights].

**Copy summary — exact shape.** Plain text, counts only: `"GPC insights, 18 Aug 2026. Filter:
everyone who wants networking breakfasts (132 of 216 members). Best slot: Tuesday morning, 81 of
132 (61%). Then Thursday morning 74 (56%), Friday morning 69 (52%). Preferred frequency: monthly,
68 of 132 (52%). Top asks: networking (98, 74%), new clients (81, 61%)."`
[Source: EXPERIENCE.md#5-member-records-and-demand-insights]. The button's success confirmation is
**"Summary copied. It contains counts only — no names or emails."**, inline beside the button, no
toast (adjudication A6) [Source: EXPERIENCE.md#5-member-records-and-demand-insights].

**"See these members" navigation.** Each block header carries "See these members", opening
`/admin/members` with the equivalent filter pre-applied **in state, not the URL**
[Source: EXPERIENCE.md#5-member-records-and-demand-insights] — consistent with the epic-wide rule
that filter state never lives in the query string for these admin screens.

**Components.** `InsightsPage`; `ResponseBaseBanner`; `InsightsFilters`; `AnswerCard`;
`SlotHeatGrid`; `RankedBarList` (reused four times: slots, event types, frequency, both branch
panels); `InsightBlock`; `BaseLine`; `SmallBaseCaution`; `CopySummaryButton`; shared `Spinner`
[Source: EXPERIENCE.md#5-member-records-and-demand-insights].

**Accessibility.** The heat grid is a real data table, navigable cell by cell with headers
announced: "Tuesday, Morning, 81, 61 percent, best." Bars are `aria-hidden`; the count/share text
beside them is the content. Base lines and the multi-select caveat are real text, never a `title`
attribute and never a footnote elsewhere. Filter changes announce once, debounced, through the
page's single `aria-live="polite"` region (adjudication A13); filters never steal focus. Heat cells
are `≥48px` tall at `md:` and form a single tab stop in browse mode
[Source: EXPERIENCE.md#5-member-records-and-demand-insights]. The "Caution" state uses `role="status"`,
**not** `alert` — information, not a failure
[Source: EXPERIENCE.md#5-member-records-and-demand-insights].

**Error-message bounding.** A server message is appended on a second muted line only when it
belongs to the app's own known error set, truncated to 120 characters, rendered as plain text —
never markup, never a raw stack or database string
[Source: EXPERIENCE.md#5-member-records-and-demand-insights].

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. NEVER run tests or quote coverage here. -->

- **Approach:** component tests for `InsightsPage.jsx` against a mocked `useInsights` hook covering
  every named state; a small set of pure-function unit tests for the tie-detection, share-formatting
  and summary-string-building logic, isolated from rendering.
- **Key scenarios:** default load with a clear winner; a two-way tie for best slot; filtered base of
  exactly 1, exactly 9, and 0; group filter narrowing to zero business-branch members; viewport
  resize crossing the `768px` breakpoint (grid ↔ ranked list swap); "Show all 21 slots as a list"
  disclosure toggled at `≥768px`; copy summary pressed at a normal base and while loading/at base 0
  (disabled).
- **Per-AC verification:** AC #1 → assert the banner renders before filters/blocks and states the
  "not everyone answered every question" caveat; AC #2 → seed a clear winner and a tie fixture,
  assert the correct singular/plural copy; AC #3 → snapshot the grid at a `≥768px` viewport, assert
  every cell has visible count+share text and the best cell carries the word "Best"; AC #4 → snapshot
  at `<768px`, assert the ranked-list ordering matches count descending, and assert the disclosure is
  present at `≥768px` too; AC #5 → change each filter, assert every block's base line value changes
  and none renders without one; AC #6 → seed bases of 5 and 0, assert the caution copy and the
  suppressed-blocks state respectively; AC #7 → mock `navigator.clipboard.writeText`, assert the
  exact summary string and the inline (non-toast) confirmation.
- **Fixtures / mocks:** a mocked `GET /api/admin/insights` response covering a clear winner, a tie,
  a small base (1–9), a zero base, at least one retired-option entry, and one wording-change entry
  (from 7.3's response shape) so this story's rendering of that case can be verified without
  duplicating 7.3's aggregation logic.
- **Edge cases to cover:** all 21 slots at zero (extreme small-base); a question with more distinct
  option keys than fit on one screen without scrolling; `prefers-reduced-motion` honoured on any
  loading skeleton.
