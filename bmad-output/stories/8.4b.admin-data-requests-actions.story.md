# 8.4b: The request detail screen and the erasure workflow

**Story ID:** 8.4b
**Epic:** 8 — Data rights and privacy
**Slug:** admin-data-requests-actions
**Status:** ready-for-dev
> **Split note:** second half of the orchestrator-assigned `8.4 admin-data-requests` — see 8.4a's
> header for the split rationale. This story is where `erase_member()` is actually called.

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As **Ash (an admin)**,
I want **to complete an unlist, unsubscribe or erasure request from one screen, with erasure
requiring a typed confirmation and never running ahead of the email that tells the member it's
done**,
so that **the 20-working-day commitment is kept without a database console, and a member can
never end up erased with a listing still live**.

## Acceptance Criteria

<!-- LOCKED. External dev tools must not edit Acceptance Criteria. -->

1. Given an admin opens an open **unlist** request and confirms "Unpublish the listing" (no typed
   confirmation — this action is reversible), then in one workflow: the listing's `status`
   becomes `unpublished`, a `publish_listing:false` consent row is appended, the `data_requests`
   row becomes `completed` with `actioned_by`/`actioned_at`, and the "your listing is down" email
   is queued.
2. Given an admin opens an open **unsubscribe** request and confirms, then `unsubscribed_at` is
   set, the `data_requests` row becomes `completed` with attribution, and a member who is already
   unsubscribed is never re-subscribed by this action.
3. Given an admin opens an open **erase** request, then the destructive "Erase this member" button
   stays disabled until the admin types the member's own email address into a
   `type="text" autocomplete="off"` field that matches it case-insensitively and trimmed — and
   pressing Enter inside that field never submits the action.
4. Given the typed confirmation matches and the admin presses "Erase this member", then the
   workflow (a) sends the erasure-complete email first, (b) **calls `erase_member(p_member_id)`
   only if that send succeeds** — its cascade on `directory_listings.member_id` is what removes
   any published listing in the same operation, so the public page cannot outlive the erasure —
   and (c) marks the `data_requests` row `completed` with attribution; if the email send fails,
   **nothing is deleted**, the request stays open, and the admin sees a blocking error offering
   retry or a typed-reason "erase without emailing" override.
5. Given a request whose member has already been erased (or which is already `completed` or
   `cancelled`), then the destructive erase control is **absent from the DOM**, not merely
   disabled, and the screen shows the already-actioned state with its acting admin and timestamp.
6. Given the `DeletionManifest`, then it shows counts by default (member record, survey answers,
   consent records, directory listing, newsletter subscription) with the actual field values
   available only behind a collapsed `<details>` disclosure, never expanded by default.

## Dev Notes

<!-- LOCKED. Concrete guidance compiled from the planning docs WITH SOURCE CITATIONS.
     Cite every fact: [Source: prd.md#anchor] / [Source: architecture.md#anchor] /
     [Source: ux-design.md#anchor]. Label your own inferences [Inference]. -->

- **This is NFR-005's entire claim.** "the whole of NFR-005's 'single workflow, no database
  access' claim" [Source: EXPERIENCE.md#7-data-rights-errors-and-edge-cases — Screen D-7]; "an
  admin can complete it in a single workflow without database access"
  [Source: prd.md#NFR-005].
- **`erase_member()` — the exact contract, LOCKED.** "**One function, `erase_member(p_member_id
  uuid)`**, `SECURITY DEFINER`, grantable to `service_role` only: 1. disables the
  `member_consents` immutability trigger for the transaction..., 2. deletes the member —
  `directory_listings.member_id … on delete cascade` removes the listing, so **the public page
  cannot outlive the erasure**, 3. writes a minimal non-identifying tombstone (`erased_at`,
  `request_id`) proving the request was honoured..., 4. re-enables the trigger."
  [Source: architecture.md#adr-015-erasure-and-withdrawal-run-through-one-security-definer-function]
  — "**Consequences — LOCKED:** no story deletes member rows ad hoc. Cascade is the mechanism that
  makes 'unpublish on erasure' impossible to forget." This story calls the function; it never
  performs its own `delete from members` or `delete from directory_listings`.
- **Function signature gap — flagged, not resolved here.** The quoted signature is
  `erase_member(p_member_id uuid)`, but step 3 references a `request_id` for the tombstone that
  the signature does not list as a parameter. `[Inference]` This story's action handler should
  pass whatever the actual migration (owned by story 1.4) exposes — if it takes a second
  `p_request_id` argument, pass this request's id; if the function resolves the open request
  itself internally, pass only `p_member_id`. Do not invent a different function or bypass it with
  direct deletes to work around a signature mismatch — raise it against 1.4 instead.
- **The email-then-delete ordering is deliberate and inverted from the usual failure-safety
  rule.** "NFR-011 says a partial failure must not lose the record; here the equivalent hazard is
  **deleting the address you need in order to say you deleted it**. So: (1) send Email 3b — on
  failure **STOP**... (2) write the tombstone; (3) delete listing → answers → consent detail →
  newsletter row → member record in one transaction; (4) mark Completed, attribute, stamp UTC."
  [Source: EXPERIENCE.md#7-data-rights-errors-and-edge-cases — Screen D-7]. The failure copy is
  specified: "We couldn't email Carla, so we haven't deleted anything yet. Try again, or use
  'Erase without emailing' and tell us why." "Erase without emailing" appears **only** after a send
  failure, requires a typed reason, and records that reason on the tombstone.
- **Unlist and unsubscribe variants, exact.** Unlist: "the manifest becomes 'What will change'
  ('The listing Bea's Baby Massage comes off the public directory. Her member record, survey
  answers and newsletter stay exactly as they are.') and the action is a single `Unpublish the
  listing` with **no typed confirmation** — it is reversible, so the ceremony would be theatre."
  Unsubscribe: "`unsubscribed_at` is the contract and the Brevo backfill must not re-subscribe
  (the behaviour fixed in commit c50bbf6)."
  [Source: EXPERIENCE.md#7-data-rights-errors-and-edge-cases — Screen D-7]. The
  never-re-subscribe guard already has a precedent in this codebase: `api/admin/subscribers.js`'s
  retry path filters `.is('unsubscribed_at', null)` specifically so a withdrawn contact is never
  pushed back to Brevo — mirror that discipline here rather than re-deriving it.
- **Typed confirmation, exact mechanics.** "`type="text"` with `autocomplete="off"` and
  `spellcheck="false"` — never `type="email"`, which lets a browser autofill defeat the
  confirmation. **Enter inside that field does not submit**; only the button activates the
  workflow, because an accidental Enter must not erase a member."
  [Source: EXPERIENCE.md#7-data-rights-errors-and-edge-cases — Screen D-7 accessibility notes]
  Validate the match **server-side too** — a disabled client button is UX, never the security
  control (mirrors ADR-003's "client-side `ProtectedRoute` is UX, never a security control"
  discipline) [Source: architecture.md#adr-003-authn-via-supabase-auth-authz-is-binary-with-attribution-instead-of-tiers].
- **Why a typed word here but a checkbox on the member side.** "The admin side (D-7) *does* use a
  typed confirmation, because there the risk inverts: Ash is acting on someone else's data, on a
  laptop, and the mistake is unrecoverable for a third party."
  [Source: EXPERIENCE.md#7-data-rights-errors-and-edge-cases — Screen D-4]. Do not soften this to
  a checkbox to match story 8.3a's member-side dialog — the two are deliberately different.
- **Absent, not disabled, once already actioned.** "Already erased, or no record | *'There's
  nothing left to delete.'*; action card replaced by `Mark this request complete`... The
  destructive control is **absent from the DOM**, not merely disabled."
  [Source: EXPERIENCE.md#7-data-rights-errors-and-edge-cases — Screen D-7 states table]
- **Attribution (NFR-013).** Every transition writes `actioned_by`/`actioned_at`
  [Source: architecture.md#adr-003-authn-via-supabase-auth-authz-is-binary-with-attribution-instead-of-tiers],
  and this route is the *only* legitimate window that writes to `member_consents` outside the
  submission path and to `directory_listings`/`members` outside moderation — reuse the verbatim
  auth block from `api/admin/subscribers.js`
  [Source: inputs/codebase-constraints-brief.md#4-admin-ui-building-blocks].
- **Auth grant for `erase_member`.** "`erase_member` is **never** granted to `authenticated` — it
  is reachable only through the admin API route, so it cannot be invoked with a stolen anon key or
  directly from a browser session."
  [Source: architecture.md#adr-015-erasure-and-withdrawal-run-through-one-security-definer-function]
  This story's endpoint must call it with the **service-role** client, never expose it via a
  browser-callable RPC.
- **`DeletionManifest` counts-first is deliberate.** "Counts-first in the manifest is deliberate:
  Ash should not have to read a member's answers in order to delete them."
  [Source: EXPERIENCE.md#7-data-rights-errors-and-edge-cases — Screen D-7 accessibility notes]
- **`DeadlinePill` reuse, not reimplementation.** Owned by story 8.4a — "the queue, the detail
  view and the dashboard tile must not be able to disagree"
  [Source: EXPERIENCE.md#7-data-rights-errors-and-edge-cases — "New components this section
  adds"].
- **Success feedback holds before navigating.** "The action card is replaced by a green completed
  panel that **holds 800ms** so the change is perceivable, then routes to D-6 with its inline
  banner." [Source: EXPERIENCE.md#7-data-rights-errors-and-edge-cases — Screen D-7 states table]

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. NEVER run tests or quote coverage here. -->

- **Approach:** No automated test runner exists in this repo
  [Source: inputs/codebase-constraints-brief.md#1-stack--deployment-reality-non-negotiable]. This
  is the highest-risk story in the epic (irreversible deletion) — verify every branch against a
  disposable seeded member in a non-production Supabase project, never against a real record.
- **Key scenarios:** unlist and unsubscribe complete in one click with correct attribution; erase
  is blocked until the typed email matches, server-side as well as client-side; a forced email-send
  failure prevents `erase_member()` from ever being called and leaves every row untouched; a
  successful erase actually removes the listing (proving the cascade) and leaves only a tombstone;
  an already-completed request never shows a live destructive control.
- **Per-AC verification:** AC #1 → seed an open unlist request, confirm, then check
  `directory_listings.status`, the new consent row, the request's `completed` status and
  `actioned_by`, and the queued email row; AC #2 → same for unsubscribe, plus a second attempt on
  an already-unsubscribed member confirming no duplicate write; AC #3 → attempt the erase POST
  directly (bypassing the UI) with a mismatched email and confirm the server itself rejects it, not
  just the disabled button; AC #4 → inject an email-send failure (e.g. point the sender at an
  invalid recipient in a test environment) and confirm zero rows changed anywhere, then retry
  successfully and confirm the listing, answers, consents and member row are all gone and exactly
  one tombstone-shaped row remains; AC #5 → open a request for an already-erased member and confirm
  the destructive button is not present in the rendered markup (not just `disabled`); AC #6 →
  confirm the manifest's default render shows numbers only, and the `<details>` disclosure is
  collapsed on load.
- **Fixtures / mocks:** at least one fully-seeded disposable member (listing, consents, newsletter
  subscription, join-form answers) per erase test run, since AC #4's success path is destructive
  and not reusable; a way to force the outbound send to fail deterministically for AC #4's failure
  branch (e.g. a test template key the sender is configured to reject, or a stubbed sender in a
  non-production environment).
- **Edge cases to cover:** two admins opening the same request in two tabs and both pressing
  confirm — the second call should see the request already `completed` and fail gracefully rather
  than double-processing; an erase request for a member with **no** listing (manifest shows `0` for
  that line, and the workflow still completes); the typed-email match must not accept a
  substring or a case-sensitive mismatch as a false positive.
