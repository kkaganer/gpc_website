## Story

As **the system**, on behalf of the org,
when **a moderation decision queues a notification**,
I want **to attempt sending it immediately through a pluggable, template-driven sender that can never block or reverse the decision it's reporting on**,
so that **FR-021 works automatically once Brevo is configured, and fails safely to a visible "queued/failed" state when it isn't — with no code change required either way**.

## Acceptance Criteria

<!-- LOCKED. External dev tools must not edit Acceptance Criteria. -->

1. Given 5.2a's action endpoint has just inserted a `queued` `outbound_emails` row, when that same request completes, then this story's sender is invoked, and its outcome (`sent`/`failed`) never changes the HTTP status or body already determined by the moderation decision — a send failure cannot turn a successful decision response into an error.
2. Given the sender renders a queued row with `template_key` `'published'`, `'rejected'`, or `'taken_down'`, when it composes the email, then the body matches the specified copy exactly — interpolated with the member's first name, business name and slug (published) or the matching reason sentence (rejected/taken-down) — and every email ends with the same controller-identity + `/privacy` + manage-data footer.
3. Given Brevo transactional is not configured (missing key) or rejects the call (`401`/`403`), when the sender attempts a send, then the row is marked `failed`, `attempts` is incremented, `last_error` is set to a mapped, non-raw string, and `last_attempt_at` is recorded — never the provider's raw message or status code.
4. Given a row reaches its third failed attempt, when that attempt resolves, then its status becomes `given_up` rather than `failed` again.
5. Given the sender logs an attempt, when it writes to server logs, then it logs the `outbound_emails` row id and the mapped error class only — never the recipient's email address or name.

- [ ] Build `api/_lib/emailSender.js`: `attemptSend(outboundEmailId)` — load the row + member + listing, render the template, call Brevo, map errors, update `status`/`attempts`/`last_error`/`last_attempt_at`/`sent_at` (AC: #1, #3, #4, #5)
- [ ] Wire `attemptSend()` into 5.2a's `api/admin/directory/[id]/action.js`, called after the `outbound_emails` insert and wrapped so a throw there does not change the already-determined decision response (AC: #1)
- [ ] Error-class mapping: address-rejected / auth-config / rate-limited / provider-5xx-or-timeout / network-drop / anything-else, each to its fixed friendly string (AC: #3)
- [ ] Given-up transition after the third failed attempt (AC: #4)
- [ ] `id`-and-class-only logging on every send attempt (AC: #5)

- ADR-014 full contract: `outbound_emails` written in the same transaction as the decision; `status` `queued|sent|failed|given_up|not_applicable`; columns `to_member_id`, `template_key`, `payload jsonb`, `attempts int`, `last_error text`, `last_attempt_at`, `sent_at`; the decision commits regardless of send outcome; the sender is pluggable and **degrades to manual with no code change** if Brevo transactional is unavailable; `payload` holds only what the template needs (listing id, slug, reason key) — no personal data beyond the recipient reference; every email carries controller identity + `/privacy` link + manage-data/unsubscribe link. [Source: architecture.md#adr-014-outbound-email-is-a-queue-table-drained-by-a-pluggable-sender]
- FR-021 acceptance criteria: publish → member emailed with a link to the live listing; reject → courteous explanation + how to resubmit; send failure visible and retryable, decision not rolled back; every email includes controller identity + a `/privacy` link. [Source: prd.md#FR-021]
- NFR-011: "Partial failures (e.g. notification email fails) still persist the submission and surface the failure to admins," measured by failure-injection on the notification path. [Source: prd.md#NFR-011]

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. NEVER run tests or quote coverage here. -->

- **Approach:** manual/functional verification per AC, with explicit failure-injection since NFR-011's own measurement method is "failure-injection on the notification path during acceptance, verifying the record persists and the error is visible" [Source: prd.md#NFR-011]; no automated test runner exists in this repo. [Inference]
- **Key scenarios:** publish with Brevo configured and healthy (row ends `sent`); publish with no Brevo key configured (row ends `failed` with the "turned us away" copy, and the listing is still published); three consecutive failures on one row (ends `given_up`); render each of the four templates and diff the output against the verbatim copy above, including the footer; confirm a decision's HTTP response is identical whether the send inside it succeeds or throws.
- **Per-AC verification:** AC#1 → stub the sender to succeed and, separately, to throw, and assert the decision endpoint's response status/body is unchanged in both cases; AC#2 → render each `template_key` against a fixture payload and assert exact string equality (subject + body + footer) against the specified copy; AC#3 → stub Brevo to return `401`, assert `status: 'failed'`, `attempts` incremented, `last_error` equals the mapped string (not the raw provider text); AC#4 → stub three consecutive failures on the same row, assert the third resolves to `given_up`, not `failed`; AC#5 → inspect whatever the send path logs and assert it contains only the row id and an error-class label, never an email address or name.
- **Fixtures/mocks:** a stubbable/mockable Brevo transactional client covering success, `401`, `429`, `5xx`, timeout, and network-drop responses; `outbound_emails` rows for each `template_key`; a member + listing pair for interpolation.
- **Edge cases:** a payload missing a field the template needs (render a safe fallback, never throw into the decision response); `admin_batch` rendered with a minimal payload (no listing-specific fields expected); retrying a row already at `given_up` (covered by 5.5b, but this story's `attemptSend()` should not itself increment past what 5.5b explicitly asks it to do); a listing whose member record has since been erased (per ADR-015, `directory_listings` cascades on member deletion — confirm the queued row, if any, fails gracefully rather than throwing on a missing member join).
