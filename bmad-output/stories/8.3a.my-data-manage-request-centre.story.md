# 8.3a: The verified request centre — unlist, unsubscribe and request erasure

**Story ID:** 8.3a
**Epic:** 8 — Data rights and privacy
**Slug:** my-data-manage-request-centre
**Status:** ready-for-dev

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.
> **Split note:** the orchestrator-assigned story `8.3 my-data-manage` was too large for one
> dev-day once the erasure confirmation dialog, the outcome page and the cancel-link flow were all
> counted — see the summary for the full split rationale. This story is the request-creation half;
> 8.3b (`my-data-outcome`) is the outcome/cancel half.

## Story

As **a member holding a valid 60-minute request link**,
I want **one screen where I can take my listing down, stop the newsletter, or ask to have
everything deleted — each on its own, without the others changing**,
so that **I can exercise exactly the right I mean to, without emailing anyone and without an
all-or-nothing "unsubscribe from everything" trap**.

## Acceptance Criteria

<!-- LOCKED. External dev tools must not edit Acceptance Criteria. -->

1. Given `GET /my-data/manage?t=<token>` with a valid, unexpired token, then the page loads and
   renders three cards — "Your directory listing", "The GPC newsletter", "Delete everything" —
   reflecting **only that token's own member's** current listing status and newsletter state.
2. Given the token is missing, malformed or expired, then the page renders no card content and
   instead shows the same expired-link state `/my-data` shows, with the address pre-filled from
   the token's claim where the token could still be parsed.
3. Given the member activates "Take my listing down" or "Stop the newsletter", then
   `POST /api/my-data/manage` writes exactly one `data_requests` row (`kind = 'unlist'` or
   `'unsubscribe'` respectively, `status` open) and queues one confirmation email — the **other
   two cards remain untouched and independently actionable** in the same page load.
4. Given the member activates "Delete everything you hold", then a confirmation `Dialog` opens
   (built on the shared `Dialog` primitive) whose destructive confirm button stays disabled until
   the "I understand this can't be undone" checkbox is ticked; confirming writes one
   `data_requests` row (`kind = 'erase'`) and queues the erasure-requested email. **No member,
   listing, answer or consent row is deleted by this story** — only the request is recorded.
5. Given any one of the three actions has just succeeded, then that card collapses in place to
   "Requested — we've emailed you the details" while the remaining cards stay live and clickable
   for the rest of the token's validity window (no navigation away, no page reload).
6. Given the member has no listing (never opted in, or it was withdrawn already), then the listing
   card renders its empty variant with no action button, while the newsletter and erase cards
   behave normally.

## Tasks / Subtasks

- [ ] Build `api/my-data/manage.js` — `GET` verifies the token (`verifyDataRightsToken`,
  `expectedPurpose: 'manage'`) and returns a snapshot `{ listing, newsletter }` for that member
  only (AC: #1, #2)
- [ ] `POST` branch: validate `{ token, kind }` where `kind` is one of `unlist | unsubscribe |
  erase`; on a valid token, insert one `data_requests` row for that `kind` and queue the matching
  confirmation email; reject a second identical in-flight request idempotently rather than
  duplicating rows (AC: #3, #4)
- [ ] Mint a `purpose: 'cancel'` token (via `src/lib/dataRights/tokens.js`, `claims: { requestId }`)
  for the queued confirmation email so story 8.3b's cancel link can act on this specific request
  (AC: #3, #4)
- [ ] Build `src/pages/MyDataManage.jsx` at `/my-data/manage` — token verification on mount,
  expired-state redirect, three-card layout in a single DOM column (AC: #1, #2, #6)
- [ ] Build `src/components/data-rights/ConsentCard.jsx` — one card per purpose, owns its own
  request state (`idle | requesting | requested | error`), renders the empty/normal/collapsed
  variants (AC: #3, #5, #6)
- [ ] Wire the erasure card's button to open the shared `Dialog` primitive (from story 5.1) with
  the itemised "we'll delete" / "we'll keep" lists, the required checkbox, and a disabled-until-
  ticked destructive confirm button (AC: #4)
- [ ] Add `/my-data/manage` to `src/App.jsx`'s public `Layout` route group (AC: #1)
- [ ] Wire "I'm done for now" to `navigate('/my-data/done', { state: { kind, deadlineOn } })` for
  the most recently requested action, so story 8.3b's outcome page can render its success variant
  from the **request payload** already held in memory, without a second authenticated fetch
  (AC: #5)

## Dev Notes

<!-- LOCKED. Concrete guidance compiled from the planning docs WITH SOURCE CITATIONS.
     Cite every fact: [Source: prd.md#anchor] / [Source: architecture.md#anchor] /
     [Source: ux-design.md#anchor]. Label your own inferences [Inference]. -->

- **This is where FR-023 is exercised member-side.** "The one screen where FR-023 is exercised...
  a direct visit without a valid token redirects to D-1 with the expired notice."
  [Source: EXPERIENCE.md#7-data-rights-errors-and-edge-cases — Screen D-3]
- **The independence guarantee is the point of the story.** "Withdrawing consent for one purpose
  does not withdraw it for the others." [Source: prd.md#FR-023] "Each control acts on exactly one
  purpose: no 'unsubscribe from everything' shortcut, no cascade."
  [Source: EXPERIENCE.md#7-data-rights-errors-and-edge-cases — §7.1]
- **Member-side action creates a request; it does not itself change state.** The actual
  unpublish, `unsubscribed_at` write and `erase_member()` call all happen from the **admin** side
  (story 8.4a/8.4b), driven by the `data_requests` row this story creates — confirmed by the
  admin queue screen showing open "Unlist"/"Unsubscribe"/"Erasure" cards each needing an admin
  action before anything changes [Source: EXPERIENCE.md#7-data-rights-errors-and-edge-cases —
  Screens D-6, D-7]. `[Inference]` — architecture.md's ADR-015 describes unlist/unsubscribe's
  *end effect* ("unlist sets the listing to unpublished and appends a `publish_listing:false`
  consent row") without stating which actor triggers it; the EXPERIENCE.md admin-queue journey is
  the disambiguating source, and NFR-005's requirement that "an admin can complete it in a single
  workflow" only makes sense if the admin is the one completing it
  [Source: prd.md#NFR-005].
- **Erasure request ≠ erasure.** "Erasure is never a same-session irreversible act: a second
  confirm step, a 'This wasn't me — cancel it' email that works until the erase runs, and an
  admin action." [Source: EXPERIENCE.md#7-data-rights-errors-and-edge-cases — §7.1, rule 4] The
  actual `erase_member()` `SECURITY DEFINER` call is **never** reachable from this route — it is
  granted only to `service_role` and invoked only from the admin action endpoint
  [Source: architecture.md#adr-015-erasure-and-withdrawal-run-through-one-security-definer-function].
- **`deadline_on` computation is not this story's job.** ADR-015 states `deadline_on` "is computed
  as 20 **working** days from `requested_at`"
  [Source: architecture.md#adr-015-erasure-and-withdrawal-run-through-one-security-definer-function],
  and migration `031` (owned by story 1.4) is where `data_requests` and its supporting functions
  are defined [Source: architecture.md#3-architecture-decision-records — ADR-002 migration table].
  `[Inference]` This story's insert should supply `member_id` and `kind` only and rely on a
  database default/trigger for `deadline_on`, matching the codebase's existing convention of
  trigger-maintained columns rather than application-computed ones
  [Source: inputs/codebase-constraints-brief.md#2-data-layer-conventions-a-new-migration-must-follow-these-exactly].
  If 1.4 does not provide this, flag it back to the orchestrator rather than duplicating a
  working-day calendar calculation here.
- **The Dialog primitive is not built here.** "One `Dialog` primitive; `ConfirmModal` rebuilt on
  it" is owned by story 5.1 [Source: bmad-output/context/sharding-context.md#ux-rulings-that-override-the-long-form-drafts].
  This story only consumes it, with `confirmTone: 'destructive'` and a required checkbox
  [Source: DESIGN.md#2-component-specifications — §2.9 Modal / Dialog].
- **Dialog content, exact.** Itemised "We'll delete" (membership record, join-form answers,
  listing if any, newsletter subscription) and "We'll keep one thing" (a dated, non-identifying
  tombstone note); checkbox before the destructive button enables; **why a checkbox, not a typed
  word**: "typing `DELETE` on a phone at night is a motor and cognitive tax on someone exercising a
  legal right" — the admin side uses a typed confirmation instead, because there the risk inverts
  [Source: EXPERIENCE.md#7-data-rights-errors-and-edge-cases — Screen D-4].
- **No friction beyond what's specified.** "There is deliberately **no retention interstitial, no
  'are you sure you want to leave?', no pause-instead-of-leave** — friction applied specifically to
  a withdrawal is a dark pattern and would undermine the compliance claim this feature exists to
  make." [Source: EXPERIENCE.md#7-data-rights-errors-and-edge-cases — §7.1 Drop-off] Do not add an
  extra confirmation step to the unlist/unsubscribe cards beyond the one specified.
- **DOM order matters, not just visual order.** "The destructive card is last in **DOM order** as
  well as visually." [Source: EXPERIENCE.md#7-data-rights-errors-and-edge-cases — Screen D-3
  accessibility notes] Cards stay a single column at every width — a three-across layout would
  make the destructive card look like a peer of the other two.
- **Hand-off to 8.3b.** "I'm done for now" is this story's only exit that leaves the page; it
  passes `{ kind, deadlineOn }` as router state to `/my-data/done`, echoing the same "render from
  the request payload, never a server echo" discipline used elsewhere in this codebase for
  confirmation screens (adjudication A2)
  [Source: bmad-output/context/sharding-context.md#ux-rulings-that-override-the-long-form-drafts].
  Story 8.3b's outcome page must not need a second authenticated fetch to show what was just
  requested. `[Inference — the exact state shape is this story's design, not sourced verbatim]`.
- **Token module reuse.** `verifyDataRightsToken`/`mintDataRightsToken` are owned by story 8.2
  (`src/lib/dataRights/tokens.js`) — this story imports and calls them, it does not modify the
  module. `[Inference — see 8.2's Dev Notes]`.
- **Accessibility floor (NFR-008)** applies in full — heading order (`<h1>` page, `<h2>` per card,
  `<h3>` for the erasure card's title beneath its own "Or leave completely" `<h2>`, no level
  skipped), `aria-describedby` on the disabled destructive button explaining why
  [Source: EXPERIENCE.md#7-data-rights-errors-and-edge-cases — Screen D-3 accessibility notes];
  [Source: bmad-output/context/sharding-context.md#accessibility-floor-nfr-008--applies-to-every-ui-story].

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. NEVER run tests or quote coverage here. -->

- **Approach:** No automated test runner exists in this repo
  [Source: inputs/codebase-constraints-brief.md#1-stack--deployment-reality-non-negotiable].
  Verify the API by scripted requests against a seeded non-production member with a known-valid
  token; verify the UI by keyboard-only walkthrough and by inspecting `data_requests` rows
  directly after each action.
- **Key scenarios:** valid token loads the right member's own state; expired/malformed token never
  renders card content; each of the three actions writes exactly one `data_requests` row of the
  right `kind` and leaves the other two purposes' state completely unchanged; the erasure dialog
  cannot be confirmed unticked; an empty-listing member sees no listing action button.
- **Per-AC verification:** AC #1 → mint a token for member A, confirm the response never contains
  member B's data even under a crafted `claims` payload; AC #2 → an expired token (or one signed
  with a stale/incorrect secret) is treated identically to a missing one; AC #3 → after an unlist
  request, re-fetch the snapshot and confirm the newsletter and erase cards are unaffected; AC #4 →
  attempt to submit the dialog with the checkbox unticked and confirm the API is never called;
  AC #5 → after a successful action, confirm the DOM node for that card changes in place with no
  route change (`history.length` unchanged); AC #6 → a member with `listing: null` in the snapshot
  renders no button in that card.
- **Fixtures / mocks:** a seeded member with a published listing and an active newsletter
  subscription; a seeded member with neither; a valid token and a deliberately expired one for the
  same member, both mintable via the shared token helper's test-only export if one is added.
- **Edge cases to cover:** a member requests both unlist and erase in the same 60-minute window —
  confirm this does not error and results in two independent `data_requests` rows (an admin will
  reconcile them at action time, out of this story's scope); a double-click on the same action
  button does not create two rows for the same purpose within the same page load (client-side
  in-flight guard, not a server-side uniqueness constraint this story is responsible for
  inventing).
