# 3.7: Validation and the error summary

**Story ID:** 3.7
**Epic:** 3 — The public form
**Slug:** validation-and-error-summary
**Status:** ready-for-dev

## Story

As a **member who has missed or mistyped a required answer**,
I want **one clear list of everything that needs fixing, positioned where I'll actually see it,
that takes me straight to each problem field**,
so that **I can correct my submission in one pass instead of hunting through 25 fields for what's
wrong**.

## Acceptance Criteria

<!-- LOCKED. External dev tools must not edit Acceptance Criteria. -->

1. Given a required, currently-rendered field is unanswered or invalid, when the member blurs it,
   then it shows its own inline error tied to it via `aria-describedby` and `aria-invalid="true"`
   — validation runs on blur, never on every keystroke.
2. Given the member submits with one or more invalid or unanswered required fields, when the
   submit attempt is blocked client-side, then a single `ErrorSummary` banner renders **directly
   above the Submit button** (never at the top of the form), lists every current error as a link
   to its field, and reads `"There are «n» things to fix before we can send this"` (or the
   singular form for exactly one).
3. Given the error summary appears, when it renders, then focus moves to it **always**, regardless
   of how many errors there are — there is no branch that skips this for a single error.
4. Given the member follows a link in the summary to a specific field, when focus lands there,
   then she can immediately correct it, and once corrected on blur (or on change once a field was
   already in error) its inline error and its summary entry both clear without a page reload.
5. Given a question belongs to a branch that is not currently mounted (FR-002), then it is never
   evaluated by validation and never appears in the summary, however it was previously answered.
6. The `ErrorSummary` is the page's **only** `role="alert"` region; every per-field error message
   is `aria-describedby` text with `aria-invalid`, never its own alert region.

## Tasks / Subtasks

- [ ] Create `src/lib/join/validateAnswers.js` — a pure function that walks the **currently
      mounted** question set (from `useJoinForm`'s branch/opt-in state) and returns
      `{ fieldKey: errorMessage }`, sourcing per-field messages from the registry/config and the
      verbatim strings already specified in 3.4's/3.5's/3.6's Dev Notes (AC: #1, #5)
- [ ] Wire on-blur validation into every field consumer (`FormField`, `RadioGroup`,
      `ChoiceChipGroup`, `Checkbox`, `DayTimeMatrix`) via a shared `useFieldValidation`-style
      pattern in `useJoinForm.js`, with re-validation on change once a field is already in error
      (AC: #1, #4)
- [ ] Create `src/components/join/ErrorSummary.jsx` — `role="alert"`, singular/plural heading,
      `<ul>` of links in DOM order, `tabindex="-1"`, focused on the next animation frame after
      every failed submit attempt (AC: #2, #3, #6)
- [ ] Wire each summary link's `href`/`onClick` to focus the corresponding field, matching the
      field's own label text plus the fix in the link text (AC: #4)
- [ ] Mount `ErrorSummary` in `src/pages/Join.jsx` immediately above the Submit button, remove any
      previous summary at the *start* of every new submit attempt so a stale error never sits
      beside a live spinner (AC: #2)

## Dev Notes

<!-- LOCKED. Concrete guidance compiled from the planning docs WITH SOURCE CITATIONS. -->

- **Adjudication A1 is the exact ruling this story implements — apply it verbatim:** *"The
  summary renders above the submit button, not at the top of the form. `role="alert"`. On failed
  submit, focus always moves to the summary, regardless of the error count. Each listed error is
  a link to its field."* The rationale recorded: on a 320px screen a member who scrolled down to
  press Submit must see the result without hunting; and one unconditional focus rule beats a
  count-dependent one — "a conditional ('field if 1, summary if 2+') is a bug factory for a solo
  maintainer and the summary announces the single error anyway."
  [Source: ux-drafts/ADJUDICATIONS.md#a1-error-summary-three-specs--one]
  [Source: DESIGN.md#2.10-inline-banner — "Form-level error summary"]
- **D6, the same rule restated for this feature's specific fields:** *"One `ErrorSummary` banner,
  `role="alert"`, rendered immediately above the Submit button. Focus always moves to the summary,
  whatever the error count. Each listed error is a link to its field. Per-field messages are
  `aria-describedby` text with `aria-invalid="true"` — they are not their own alert regions
  (A13). Only rendered questions are validated; hidden-branch questions are never required and
  never appear in the summary."* [Source: EXPERIENCE.md#1-joining--the-public-form — "D6"]
- **Exact wireframe and copy (Screen S6):**
  ```
  ⚠ There are 3 things to fix before we can send this
  • Your email address — enter an email address so we can reply
  • Which group would you like to join? — choose the group you'd like to join
  • Which days and times work? — pick at least one slot, or tick "I'm flexible"
  ```
  Singular reads *"There's 1 thing to fix…"*. Placement is directly above `[ Send my answers ]`.
  ≥768px: banner caps at `max-w-2xl` with the form column; summary links go to two columns past
  six entries. **Never a floating toast at any breakpoint** (A6) — a toast can be missed, cannot
  be re-read, and is the wrong shape for an error requiring action on specific fields elsewhere
  on the page. [Source: EXPERIENCE.md#1-joining--the-public-form — Screen S6 wireframe and prose]
  [Source: ux-drafts/ADJUDICATIONS.md#a6-no-global-toaster]
- **Server-side validation errors (400) render through the same component and copy shape:**
  server field keys map to the same client messages this story already defines; an unmapped key
  falls back to *"Something in this answer isn't accepted. Please shorten or simplify it."* This
  story builds the client-side validation and the summary component; wiring the 400 response into
  it is 3.8's job, but this story's `ErrorSummary` must accept an externally-supplied error map
  (not only its own client-computed one) so 3.8 can reuse it without a second component.
  [Source: EXPERIENCE.md#1-joining--the-public-form — Screen S6, "validation (server, 400)" row]
- **Only rendered questions are validated — this is the FR-002 boundary this story must not
  violate:** a hidden-branch question is never required and never blocks submission, however it
  was answered before a branch change. `validateAnswers.js` must derive its field set from
  `useJoinForm`'s *currently mounted* keys (branch + opt-in state), never from a static list of
  every possible key. [Source: prd.md#FR-002 — "Hidden-branch questions are never validated as
  required and never blocked submission."] [Source: EXPERIENCE.md#1-joining--the-public-form —
  "D6"]
- **Validation timing, exact:** runs **on blur**, not on every keystroke; re-validation after an
  error **may** run on change, so the error clears as soon as the member fixes it. This applies
  uniformly to every field type built in 3.2–3.6 (text, textarea, select, radio, chip group,
  checkbox, the day/time matrix). [Source: DESIGN.md#2.4-text-input-textarea-select — "Validation
  runs on blur"] [Source: EXPERIENCE.md#dev-handoff-notes — "Non-negotiables"]
- **One `role="alert"` region, full stop.** Per-field errors are `aria-describedby` text with
  `aria-invalid="true"` and must **not** carry `role="alert"` — this directly overrides
  DESIGN.md §2.4's "Error message containers carry `role="alert"`" line, which A13's ruling
  supersedes: *"One `aria-live="polite"` region per page... plus one `role="alert"` region for
  errors. ... Four simultaneous regions on `/join` would produce interleaved, unintelligible
  speech."* [Source: ux-drafts/ADJUDICATIONS.md#a13-one-live-region-per-page]
  [Source: EXPERIENCE.md#1-joining--the-public-form — "D7"]
- **Default (no-error) state renders nothing, not an empty container.** *"The summary is not
  rendered at all — not rendered-empty. A permanently-present alert container has a habit of
  announcing stale content on re-render."* On a new submit attempt, remove any previous summary
  at the **start** of the request so a stale error never sits next to a live spinner.
  [Source: EXPERIENCE.md#1-joining--the-public-form — Screen S6 states table]
- **Focus choreography, exact:** `role="alert"`; focus moves to the summary "on the next animation
  frame, always, whatever the count." **Focus is never moved to the Submit/retry button** — that
  would let a member re-submit by reflex before reading why the last attempt failed. From the
  summary's last link, Tab continues **into the form**, never trapping.
  [Source: EXPERIENCE.md#1-joining--the-public-form — Screen S6 states table, accessibility
  notes]
- **Link text is the field's own label plus the fix, in DOM order** — matching the form so the
  summary reads as a sentence, e.g. "Your email address — enter an email address so we can
  reply." Do not invent a generic "Fix this field" link text.
  [Source: EXPERIENCE.md#1-joining--the-public-form — Screen S6 wireframe]
- **This story does not implement server-error wiring, network/429/closed states, or the double-
  submit spinner** — those belong to 3.8. This story's boundary is client-side validation and the
  summary component's presentation/focus contract, built so 3.8 can drop server-originated errors
  into the same `ErrorSummary` and reuse the same focus rule.
  [Inference — drawn from the epics.md split between 3.7 ("validation-and-error-summary") and 3.8
  ("confirmation-and-errors"), and DESIGN.md's single error-summary component serving both.]

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify per AC, test types, fixtures, edge cases. -->

- **Approach:** unit tests for `validateAnswers.js` against every field type and branch
  combination built by 3.2–3.6, component tests for `ErrorSummary`'s focus and rendering
  contract, and a manual screen-reader pass confirming exactly one assertive announcement fires
  per failed submit.
- **Key scenarios:** blur-triggered validation on each field type; a submit attempt with zero
  errors renders no summary at all; a submit attempt with N errors renders exactly N links in DOM
  order with correct link text; focus lands on the summary on every failed attempt regardless of
  N (test N=1 explicitly, since that's the case the old count-dependent designs got wrong); a
  hidden-branch field with a stale error never appears in the summary after a branch change (this
  overlaps 3.3's discard logic — verify the two integrate); correcting a field and blurring
  removes both its inline error and its summary entry live.
- **Per-AC verification:** AC #1 → blur an empty required field and assert `aria-invalid="true"`
  and a matching `aria-describedby` id appear, and assert no error appears mid-keystroke before
  blur; AC #2 → submit with 3 known-invalid fields and assert the summary heading reads "There
  are 3 things to fix before we can send this" with 3 links, and that the summary's DOM position
  is a sibling immediately preceding the Submit button, not the top of the form; AC #3 → repeat
  with exactly 1 invalid field and assert focus still moves to the summary (not to the single
  field); AC #4 → click a summary link, assert focus lands on the target field, fix it, blur, and
  assert both the inline error and the summary's corresponding `<li>` are gone; AC #5 → set a
  branch field's answer, discard the branch (3.3's mechanism), submit, and assert
  `validateAnswers.js`'s output never mentions the discarded key; AC #6 → assert
  `document.querySelectorAll('[role="alert"]').length` is at most 1 at any time, including while
  individual fields are in error.
- **Fixtures / mocks:** a fully-populated stub `useJoinForm` state covering every section built by
  3.2–3.6 (identity, branch, events/community, listing, consent), so this story can be tested
  without depending on Epic 2's live config endpoint.
- **Edge cases to cover:** a member who fixes all errors and re-submits before the summary's
  removal-at-start-of-request timing settles (no flash of stale content); a field whose error
  message changes because its branch's registry-driven required flag changed mid-session (form
  config publish is out of scope for `/join`'s runtime, so this is a low-probability edge case,
  but the validator must not cache a stale message); very long field-label link text wrapping at
  320px without breaking the list's tap targets.

## Learnings from Previous Stories

- 3.1a's Dev Notes already establish that DESIGN.md §2.4's per-field `role="alert"` line is
  overridden by A13 — every field-level component built in 3.2–3.6 should already be compliant;
  this story's job is the summary and the orchestration, not retrofitting field-level ARIA.
  (from 3.1a)
- 3.3 established the delete-not-blank discard rule and its own recompute-on-change flow — this
  story's validator must read `useJoinForm`'s live mounted-field set rather than a snapshot, so a
  branch discard immediately removes that branch's entries from any pending error summary. (from
  3.3)
- 3.5's escape-hatch pattern (a `Button size="sm"` link out of a stuck state) is the same
  `size="sm"` variant this story's summary links can reuse for visual consistency, though the
  summary's own links are plain text links, not buttons. (from 3.5)
