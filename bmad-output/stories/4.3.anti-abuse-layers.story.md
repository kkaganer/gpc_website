# 4.3: Anti-abuse layers

**Story ID:** 4.3
**Epic:** 4 — Submission pipeline
**Slug:** anti-abuse-layers
**Status:** ready-for-dev

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As **GPC's community admin team**,
I want **`POST /api/join/submit` protected by an origin check, a honeypot, and a Postgres-backed rate limit, applied in that fixed order in front of validation**,
so that **automated abuse never reaches the moderation queue or the database, and a real member on shared wi-fi is never falsely accused**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. Given a request to `POST /api/join/submit` arrives with a missing or non-matching `Origin`/`Referer` header, when the pipeline runs, then it is rejected with `403 { error }` as the very first check — before the honeypot field is read, before any rate-limit query runs, and before any row is written — and an `abuse_events` row is written with `reason = 'origin'`.
2. Given the origin check passes and the hidden honeypot field is non-empty, when the pipeline runs, then an `abuse_events` row is written with `reason = 'honeypot'`, no `members`/`member_submissions`/`directory_listings` row is created, and the response is the **ordinary `200 { ok: true }` success shape** — returned before the rate-limit check or field validation runs.
3. Given the origin and honeypot checks pass, when the caller's salted IP hash has already recorded 3 submissions in the trailing hour or 20 in the trailing 24 hours, then the request is rejected with `429 { error }`, an `abuse_events` row is written with `reason = 'rate_limit'`, and no member/submission/listing row is written — checked before field validation runs.
4. Given field validation (built in 4.2) rejects a submission because a free-text answer exceeds its registry `maxLength`, when the request is rejected, then an `abuse_events` row is **also** written with `reason = 'length'`, in addition to the `400` response — so the FR-006 admin-visible counter reflects every rejection reason, not only honeypot and rate-limit.
5. Given any `abuse_events` row is written by this pipeline (any reason), when it is inspected, then it stores only a salted SHA-256 hash of the caller's IP — the raw IP is never stored, logged, or passed to any function that is not the hashing step itself — and it remains eligible for the existing 48-hour sweep delivered by `1.4`.
6. Given a full request lifecycle, when the pipeline runs end to end, then the order is exactly **origin → honeypot → rate limit → validate (4.2) → `submit_membership()` (4.1)**, and whichever layer rejects first short-circuits everything after it — no later layer's side effects (a DB write, a validation error) ever occur once an earlier layer has rejected.

## Tasks / Subtasks

- [ ] Create `api/_lib/abuse.js`: `hashIp(ip, salt)` (salted SHA-256), `recordAbuseEvent(reason)`, `checkRateLimit(ipHash)` querying `abuse_events` for the 1h/24h windows (AC: #3, #5)
- [ ] In `api/join/submit.js` (4.2's handler), insert the origin/referer check as the **first** statement after method/body parsing, before the honeypot read; on mismatch, write `abuse_events(reason='origin')` and return `403` (AC: #1, #6)
- [ ] Add the honeypot field read immediately after the origin check and before the rate-limit check; on a non-empty value, write `abuse_events(reason='honeypot')` and return the identical `200 { ok: true }` shape 4.2 already produces for a genuine success, without calling `submit_membership()` (AC: #2, #6)
- [ ] Add the rate-limit check immediately after the honeypot check and before field validation; on threshold breach, write `abuse_events(reason='rate_limit')` and return `429` (AC: #3, #6)
- [ ] Wrap 4.2's existing field-validation failure path so an over-length rejection also calls `recordAbuseEvent('length')` before returning its existing `400` (AC: #4)
- [ ] Compute the IP hash once per request from `req.headers['x-forwarded-for']` (Vercel's client-IP header) using a server-only salt env var; pass the hash, never the raw value, into every downstream call (AC: #5)
- [ ] Confirm no sweep logic is built here — `abuse_events`' 48-hour sweep function already exists from `1.4`; this story only writes rows and reads them for the rate-limit window (AC: #5)

## Dev Notes

<!-- LOCKED. Concrete guidance compiled from the planning docs WITH SOURCE CITATIONS.
     Cite every fact: [Source: prd.md#anchor] / [Source: architecture.md#anchor]. Own inferences: [Inference]. -->

- **The load-bearing order, verbatim from the architecture.** *"Order of operations is load-bearing: origin → honeypot → rate limit → validate → transaction. The honeypot returns the ordinary success shape before any row is written."* [Source: architecture.md#component-submission-service-post-apijoinsubmit]. This is restated at the ADR level: *"Four layers, all inside the existing stack, applied in `POST /api/join/submit` in this order: 1. Origin check … 2. Honeypot … 3. Postgres-backed rate limit … 4. Server-side length limits …"* [Source: architecture.md#adr-011-anti-abuse-in-postgres-and-the-request-handler-no-new-third-party-processor]. This story does **not** re-implement the length-limit rejection logic itself (that is 4.2's field-by-field validation loop) — it only ensures that path also feeds the shared `abuse_events` counter, so all four ADR-011 layers are represented in the FR-006 criterion-5 counter.
- **Origin check, mechanics.** Reject when `Origin`/`Referer` is absent or not the site's own origin; free, stops naive scripted posting; `403` [Source: architecture.md#adr-011-anti-abuse-in-postgres-and-the-request-handler-no-new-third-party-processor]. No route in this codebase currently reads `origin`, `referer`, or `x-forwarded-for` at all — this is genuinely new [Source: inputs/codebase-constraints-brief.md#6-what-does-not-exist-and-must-be-built-or-decided].
- **Honeypot, mechanics.** "a visually hidden, `aria-hidden`, `tabindex="-1"` field with an innocuous name. If completed: discard silently, record an `abuse_event`, return the ordinary success shape (ADR-005 non-disclosure). No member row, no listing, no moderation task." [Source: architecture.md#adr-011-anti-abuse-in-postgres-and-the-request-handler-no-new-third-party-processor]. The field itself is built into the `/join` form by Epic 3; this story only handles the server-side branch on it.
- **Rate limit, mechanics and thresholds.** "an `abuse_events` table storing a salted SHA-256 hash of the client IP, never the IP … 3 submissions per IP-hash per hour, 20 per IP-hash per 24h. The salt is a server-only env var; rows are swept after 48 hours. Exceeding the limit returns 429 and writes no member row." [Source: architecture.md#adr-011-anti-abuse-in-postgres-and-the-request-handler-no-new-third-party-processor]. "Why hashed IPs. An IP is personal data. Hashing with a server-side salt keeps the rate-limit function … while making the stored value useless to anyone reading the table" [Source: architecture.md#adr-011-anti-abuse-in-postgres-and-the-request-handler-no-new-third-party-processor].
- **`abuse_events` schema**, from `1.4`'s migration: `id · ip_hash text (salted SHA-256) · reason (text + CHECK honeypot|rate_limit|origin|length) · created_at`, swept after 48 hours [Source: architecture.md#5-data-model]. This story writes rows against a table it does not own or migrate — `1.4` already created it; do not add a second migration for it.
- **Why the counter matters.** *"FR-006 criterion 5 — the visible counter. `abuse_events` is the source for the 'Abuse blocked' tile on Form Settings … counts for 7 and 30 days, split honeypot vs rate-limit vs origin, plus a warning banner … Without a screen this requirement is unbuilt, which is why the table carries a `reason` column rather than being a bare counter."* [Source: architecture.md#adr-011-anti-abuse-in-postgres-and-the-request-handler-no-new-third-party-processor]. That screen is Epic 2's `2.7`, out of scope here — this story's job is only to make sure every rejection path feeds the table with the right `reason`.
- **No third-party processor.** ADR-011 is explicit that no CAPTCHA/Turnstile/hCaptcha is added without a controller decision and a privacy-page revision [Source: architecture.md#adr-011-anti-abuse-in-postgres-and-the-request-handler-no-new-third-party-processor]. This story adds zero runtime dependencies.
- **FR/NFR coverage:** FR-006 (all five ACs — threshold rejection, honeypot silent success, origin rejection, length rejection never truncated, visible counter) [Source: prd.md#FR-006]; NFR-003 (burst-test threshold: 100 submissions in one minute results in no more than the configured allowance stored) [Source: prd.md#NFR-003]; NFR-006 data minimisation (hashed IP, 48h sweep) [Source: prd.md#non-functional-requirements].
- **This story owns sequencing, not 4.2's internals.** It wraps and reorders around the handler 4.2 built; it must not change 4.2's allowlist-mapping logic, only insert three new early-return branches ahead of it and one additional side-effect (`abuse_events` write) inside the existing length-limit branch.

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. NEVER run tests or quote coverage here. -->

- **Approach:** integration verification against a preview deployment, matching how NFR-003 is specified to be measured: *"Scripted burst test against a non-production deployment before launch"* [Source: prd.md#NFR-003] and *"a real constraint … the pre-launch burst test (NFR-003) must run against a preview deployment with a distinct IP salt, and its `abuse_events` rows must be swept afterwards"* [Source: architecture.md#10-deployment-architecture]. No unit-test framework exists in this repo to substitute for this.
- **Key scenarios:** (a) a request with no `Origin` header → `403`, `abuse_events(reason='origin')`, zero other writes; (b) a request with the honeypot field filled → `200 { ok: true }`, `abuse_events(reason='honeypot')`, zero member/submission/listing rows; (c) a 4th request within an hour from the same IP → `429`, `abuse_events(reason='rate_limit')`; (d) a 21st request within 24h from the same IP → `429`; (e) an over-length free-text field → `400` **and** `abuse_events(reason='length')`; (f) a scripted burst of 100 requests in one minute from one IP → no more than the configured allowance persisted, the remainder rejected, matching NFR-003's threshold.
- **Per-AC verification:** AC #1 → assert order by checking no honeypot/rate-limit query fires when origin fails (e.g. via a mocked/instrumented rate-limit call that must not be invoked); AC #2 → assert response body is identical to a genuine success and no DB row exists besides the `abuse_events` one; AC #3 → assert threshold counts exactly at 3/hr and 20/24h boundaries (3rd allowed, 4th rejected); AC #4 → assert the `abuse_events` row exists alongside the existing `400`; AC #5 → inspect `abuse_events.ip_hash` and confirm it is not the literal IP, and confirm rows older than 48h are absent after the existing sweep runs; AC #6 → assemble a table of {which layer fails} × {which later layers must not have run} and check each combination.
- **Fixtures/mocks:** requests with no `Origin`, a foreign `Origin`, and the site's own `Origin`; a payload with the honeypot field set; a scripted loop from one source IP (or a forced `x-forwarded-for` header on a preview deployment) to exercise the rate limit without a real burst; a distinct IP salt for any pre-launch burst test so it can be swept independently of production data.
- **Edge cases:** the rate-limit check running exactly at the boundary count (3rd/4th, 20th/21st); a request whose `Origin` header is present but empty string; a honeypot field present but explicitly `null` vs an empty string vs whitespace-only (all three should count as "not completed" unless the field spec says otherwise — confirm against Epic 3's honeypot markup once built); `x-forwarded-for` carrying multiple comma-separated IPs (Vercel convention — hash only the client-facing first entry).
