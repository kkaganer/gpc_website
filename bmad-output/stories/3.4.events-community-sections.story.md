# 3.4: Events and community sections — the day/time matrix

**Story ID:** 3.4
**Epic:** 3 — The public form
**Slug:** events-community-sections
**Status:** ready-for-dev

## Story

As a **member filling in the Events section**,
I want **to say which kinds of events I'd love, which days and times usually work, and how often
I'd like events, in a control that doesn't cost me a thousand pixels of scrolling to answer one
question**,
so that **the "which day should we run the next event?" question the survey exists to answer
gets a real, usable answer instead of a wall of 21 checkboxes I give up on**.

## Acceptance Criteria

<!-- LOCKED. External dev tools must not edit Acceptance Criteria. -->

1. Given the Events section renders, when a member wants to answer the day/time question, then
   she can express "any day or time works" with one tap on a leading "I'm flexible" checkbox, and
   this single tap satisfies the question's required rule.
2. Given the day/time question, when a member wants to select a specific pattern (e.g. "Tuesday
   and Thursday mornings"), then she can do so as a 7×3 grid of real, individually-named
   checkboxes ("Tuesday morning", etc.), each with a ≥44px touch target, with row (day) and
   column (time-of-day) toggle controls that select/deselect a whole row or column in one tap,
   and the whole control fits within 320px width with no horizontal scroll.
2a. Given the "I'm flexible" checkbox is ticked, when the grid is present, then the 21 cells and
   the 3 column toggles become `disabled` (native, out of tab order) while remaining **visible**,
   any prior selections are retained in component state and restored on unticking, and while
   flexible is ticked those prior selections are excluded from the submitted payload.
3. Given "How often would you like events?" renders, then it is a single-select `RadioGroup`
   (Weekly / Fortnightly / Monthly / Quarterly) — never a checkbox group that could record
   mutually exclusive answers like "Weekly + Quarterly" simultaneously.
4. Given the two Community questions render, then both are optional, carry no asterisk, and each
   section shows a `Done` badge from first paint (having no required fields).
5. Given a screen reader announces the day/time question, then the matrix itself carries no
   heading (its `<legend>` is the question text) and errors attach to the fieldset via
   `aria-describedby`, never to any of the 21 individual cells.

## Dev Notes

<!-- LOCKED. Concrete guidance compiled from the planning docs WITH SOURCE CITATIONS. -->

- **This is the epic's explicitly named replacement for a real usability defect.** The source
  form asks "which days work best?" as one flat 21-option multi-select — ~1,000px of continuous
  scroll at 320px against a whole-form height of ~2,800px, so a member sizing the form up
  overestimates its length threefold. Splitting into "which days" + "which times" was
  **rejected** because it destroys the cross product FR-014 needs (a member choosing {Tue, Sat} ×
  {morning, evening} would wrongly record as free for all four combinations when she meant two).
  An inner scroll box was also rejected — a scroll trap inside a scrolling page, invisible to
  `Ctrl+F`. [Source: EXPERIENCE.md#1-joining--the-public-form — "The 21-checkbox problem"]
- **The fix: a 2D grid of real checkboxes with row/column toggles**, costing **zero** extra tab
  stops beyond the label column and header row that existed anyway. Vertical cost is **~440px
  against ~1,000px**, and the same information is answerable in 1 tap (flexible), 2 (two whole
  days via row toggles) or 4 (all mornings via a column toggle) — while remaining exactly as
  expressible at 21 individual taps as the source form. Tab order: `I'm flexible` → three column
  toggles → `Mon` (row toggle) → Mon's three cells → `Tue` → … .
  [Source: EXPERIENCE.md#1-joining--the-public-form — Screen S3 wireframe and prose]
- **Wireframe reference (320px):**
  ```
  [ ☐ I'm flexible — any day or time works ]   ← FIRST tab stop, 48px, one tap satisfies AC #1
          Morn    Aft     Eve
         [ all ] [ all ] [ all ]                ← column toggles, aria-pressed
   Mon ⇢ [     ] [     ] [     ]                ← day label = row toggle
   Tue ⇢ [  ✓  ] [     ] [     ]
   ...
  Morn = before 12 · Aft = 12–5 · Eve = after 5           3 selected
  ```
  Cells are 63px wide × 44px tall with visually-hidden accessible names ("Tuesday morning"); the
  day-label column is 56px and doubles as the row toggle.
  [Source: EXPERIENCE.md#1-joining--the-public-form — Screen S3 wireframe]
- **≥768px, differences only:** cells widen to ~96px, headers show full words, the abbreviation
  legend drops, and a `Weekdays / Weekend / Clear all` shortcut row appears — **deliberately not
  at 320px**, where three more targets would undo the whole saving. Business name/website/
  Instagram (a different section) pair into two columns at this breakpoint too, but that is
  3.3's concern, not this story's. [Source: EXPERIENCE.md#1-joining--the-public-form — Screen S3]
- **Required rule and its error text:** the matrix stays `required` because "I'm flexible" makes
  satisfying it cost exactly one tap, and the error names the escape hatch: *"Pick at least one
  slot, or tick 'I'm flexible'."* Event-type chips error: *"Pick at least one kind of event."*
  Frequency error: *"Choose how often you'd like events."* Summary badge on the section heading
  while unanswered: *"2 to fix"* (or the current count).
  [Source: EXPERIENCE.md#1-joining--the-public-form — Screen S3 states table]
- **Disabled-while-flexible is a deliberate, cited divergence from `EventFilters.jsx`'s
  dim-and-disable idiom** for dependent controls — used correctly here because the grid stays a
  dependent control of "I'm flexible": grid stays **visible** (not hidden) so a member can see
  what she opted out of and untick to get it back, native `disabled` removes cells from the tab
  order, and a wrapper `aria-describedby` carries a hidden note: *"Day and time choices are
  turned off because you said you're flexible."* Prior selections are **retained in state and
  restored** on unticking but **excluded from the payload** while flexible is on. This is the one
  place in `/join` where dimming a section (rather than unmounting it, as branches are) is
  correct, because the grid is a dependent control of a sibling checkbox, not a branch of the
  form. [Source: EXPERIENCE.md#1-joining--the-public-form — Screen S3 "Disabled" state row]
  [Source: inputs/codebase-constraints-brief.md#5 — `EventFilters.jsx` dimmed+disabled idiom]
- **Not a `role="grid"`, deliberately.** 21 fully-named plain checkboxes need no spatial model; an
  ARIA grid would ask the member to hold a two-dimensional coordinate space announced as row/
  column headers, which is the wrong cognitive load here. Roving `tabindex` for the matrix is
  **explicitly deferred** — plain Tab is fully conformant and the row/column toggles mean no
  keyboard user is forced through all 21 stops; revisit only if manual testing says otherwise.
  [Source: EXPERIENCE.md#1-joining--the-public-form — Screen S3 accessibility notes, "Notes for
  architecture"]
- **Legend carries the question and its hint together**, re-announced on entry rather than relying
  on memory after 18 preceding checkboxes elsewhere on the page; the selected-slot count is
  debounced 500ms into the one shared live region (`useLiveRegion` from 3.1a). Header labels and
  the abbreviation legend are permitted at 14px — the 16px-input rule governs `input`/`textarea`/
  `select`, not static labels, and applying it here would push the matrix past 320px.
  [Source: EXPERIENCE.md#1-joining--the-public-form — Screen S3 accessibility notes]
- **Event types (10 chips) and frequency (single-select, the source form's defect 4 fixed):** the
  source form's "How often would you like events?" is currently a checkbox group that wrongly
  permits "Weekly + Quarterly" together; it renders here as a `RadioGroup` from 3.1b, sourced from
  the corrected question type in the registry (Epic 2, story 2.1 — this story does not itself fix
  the registry, it renders whatever `type` the registry declares, which must be `single_choice`
  for this key). [Source: EXPERIENCE.md#1-joining--the-public-form — Screen S3 wireframe,
  "DEFECT 4 FIXED" annotation]
- **Community section (2 questions, both optional):** neither carries a required flag; the
  section shows `Done` from first paint — itself a length signal, per D2. No specific field
  copy is given in EXPERIENCE.md beyond "2 optional questions" — render generically off the
  registry/config exactly as with 3.3's branch sections. [Source: EXPERIENCE.md#1-joining--the-
  public-form — Journey J2 wireframe, "Community: 2 optional questions skipped → section reads
  Done"] [Inference — exact community question wording is registry/config content owned by
  Epic 2, not specified verbatim in EXPERIENCE.md; this story renders whatever the config
  resolves.]
- **Render generically off the registry (ADR-008), same pattern as 3.3** — event types, frequency
  and the 2 community questions all come from `src/lib/join/questions.js` (read-only here) plus
  the published config. [Source: architecture.md#adr-008-form-configuration-code-defined-
  registry-database-overlay-and-versioned-publish]
- **This section is `always`-branch, not `business`/`career`-gated** — Events and Community render
  regardless of `groupChoice`, unlike 3.3's branch sections. Confirm the registry marks these
  question keys `branch: 'always'`. [Inference — consistent with EXPERIENCE.md's journey diagrams,
  which show Events/Community rendering identically for both Bea (Business) and Carla (Career).]

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify per AC, test types, fixtures, edge cases. -->

- **Approach:** component tests for `DayTimeMatrix` in isolation (the highest-risk component in
  this story) covering row/column toggle logic and the flexible-disables-and-excludes rule, plus
  a manual 320px keyboard pass and a manual screen-reader pass confirming each cell's accessible
  name (e.g. "Tuesday morning") and that the matrix has no extraneous heading.
- **Key scenarios:** ticking "I'm flexible" satisfies the required rule with zero cells selected;
  selecting individual cells without flexible also satisfies it; a row-toggle selects/deselects
  all 3 cells in that row and updates the row toggle's `aria-pressed`; a column-toggle does the
  same for all 7 cells in that column; ticking flexible after cells are already selected disables
  the cells but does not clear them, and unticking restores the exact prior selection; frequency
  cannot hold more than one selected value even if the underlying state is mishandled (single-
  select by construction via `RadioGroup`).
- **Per-AC verification:** AC #1 → tick "I'm flexible" alone and assert the section's required
  check passes; AC #2 → select 2 cells via direct taps and via one row toggle, assert equivalent
  resulting state, and assert computed width at a 320px viewport does not overflow; AC #2a →
  tick flexible with 3 pre-selected cells, assert the 21 cells and 3 column toggles gain
  `disabled`, assert internal state still holds the 3 selections, untick and assert they
  reappear checked; assert the serialized payload while flexible is ticked contains no day/time
  keys; AC #3 → assert the frequency control renders as radio inputs, not checkboxes, and that
  selecting a second option deselects the first; AC #4 → assert both community fields render
  without `aria-required`/`*` and the section heading shows `Done` before any input; AC #5 →
  assert no `<h*>` exists inside the matrix's DOM subtree and that an injected error id appears
  only in the fieldset's `aria-describedby`.
- **Fixtures / mocks:** a stub registry/config for the Events (3) and Community (2) question keys,
  matching Epic 2's contract shape, so this story is not blocked on 2.1/2.2 shipping.
- **Edge cases to cover:** ticking and immediately unticking "I'm flexible" with no prior
  selections (no-op); toggling a row/column that is already fully selected (should deselect,
  matching the "all"-toggle's `aria-pressed` semantics); rapid tapping across the grid to confirm
  no dropped state updates.

## Learnings from Previous Stories

- 3.1b's `ChoiceChipGroup` reports selection count to its caller rather than announcing directly
  — this story's `EventsSection` (event types) is the first real consumer of that contract; apply
  the same pattern for the matrix's own count via the shared `useLiveRegion`, debounced 500ms.
  (from 3.1b)
- 3.3 established the generic registry-driven rendering pattern (switch over `type`, no per-
  question hand-built component) — this story's `EventsSection`/`CommunitySection` should follow
  the same shape rather than reinvent field-by-field components. (from 3.3)
- 3.2/3.3 confirmed `Join.jsx` and `useJoinForm.js` are inherently serialized across Epic 3
  stories; this story is the third to extend both. (from 3.2, 3.3)
