# 2.7: Abuse blocked tile

**Story ID:** 2.7
**Epic:** 2 — Form configuration
**Slug:** abuse-blocked-tile
**Status:** ready-for-dev

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As **Ash, a GPC admin**,
I want **to see how many submissions were blocked as spam over the last week and month, split
by why, right on the form settings screen**,
so that **a live attack becomes visible to a human instead of silently piling up behind the
scenes, and I have evidence, not just a hunch, when I decide whether to close the form.**

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. Given the tile loads, when its data resolves, then it shows rejected-submission counts for
   rolling **7-day** and **30-day** windows, broken down by reason (`honeypot`, `rate_limit`,
   and any other value present in `abuse_events.reason`'s vocabulary — `origin`, `length`) —
   computed **server-side** from `abuse_events`; the browser never receives a raw
   `abuse_events` row.
2. Given zero rejections occurred in the last 30 days, then the tile shows "Nothing blocked in
   the last 30 days." rather than a bare `0`.
3. Given the tile's own fetch fails, then it shows "Couldn't load the blocked count" and
   `[Try again]` **without** affecting the rest of the Form Settings page — a failure here
   never blocks the open/close toggle, the question list, or the intro/closed-message fields
   (2.3) from working.
4. Given the response payload, then it contains only counts and reason keys — no IP address
   (raw or hashed), no per-event timestamp, no request payload, and no free text of any kind.
5. Given blocked submissions in the trailing 24 hours exceed **20 and** are at least **3× the
   trailing 7-day daily average** (both conditions, together), then a warning banner appears
   above the status card naming the 24-hour count and the usual average, and its one action
   moves focus to the open/close toggle — it never closes the form automatically.
6. Given a 2.6 preview submission is made, when the tile is subsequently refreshed, then its
   counts are unchanged — preview never reaches a real endpoint, so no abuse-related counter
   can move because of it.

## Dev Notes

<!-- LOCKED. Concrete guidance compiled from the planning docs WITH SOURCE CITATIONS.
     Cite every fact: [Source: prd.md#anchor] / [Source: architecture.md#anchor] /
     [Source: ux-design.md#anchor]. Label your own inferences [Inference]. -->

**Why this story exists and what it is worth.** "FR-006 criterion 5 — the admin-visible
rejected-submission counter, and with it the **only UX surface of NFR-003**"
[Source: epics.md#epic-2-form-configuration]. FR-006's own text: "Rejected submissions
increment a counter an admin can see, so a live attack is visible."
[Source: prd.md#FR-006]. NFR-003's acceptance/threshold ("a scripted burst of 100 submissions
... results in no more than the configured allowance being stored, with the remainder
rejected") [Source: prd.md#NFR-003] is enforced entirely server-side by Epic 4's anti-abuse
layers — this story does not enforce anything; it is the **only place a human ever sees that
enforcement happened.** Without this screen, NFR-003 can be fully implemented and still be
functionally invisible — the sharding context is explicit that this story is not optional
polish: "2.7 is the ONLY UX surface of NFR-003 — without it FR-006 criterion 5 is unbuilt."
[Source: sharding-context.md — epic-specific direction].

**Data source, exactly.** `abuse_events`: `id · ip_hash (salted SHA-256, never the raw IP) ·
reason (text + CHECK 'honeypot' | 'rate_limit' | 'origin' | 'length') · created_at`, swept
after 48 hours [Source: architecture.md#5-data-model — Entity: `abuse_events`]. The four
layers that can write a row, in the order they run: origin check → honeypot → Postgres rate
limit → server-side length limit
[Source: architecture.md#adr-011-anti-abuse-in-postgres-and-the-request-handler--no-new-third-party-processor].
**Consequence for this story's aggregation:** because rows are swept after 48 hours, a
30-day count is only meaningful if the sweep does not also delete the count evidence —
confirm with whoever builds Epic 1 story 1.4 (the sweep function) that the sweep runs against
a *retained* aggregate or that 48h is long enough that 7-/30-day windows are actually
achievable from live rows. **This is a real tension to flag, not silently resolve**: ADR-011
says rows are "swept after 48 hours"
[Source: architecture.md#adr-011-anti-abuse-in-postgres-and-the-request-handler--no-new-third-party-processor],
but this story's own AC #1 requires a 30-day window. [Inference — likely resolution: the sweep
removes the `ip_hash` for privacy/retention but a lighter daily/weekly rollup count survives,
or the 48h sweep figure in ADR-011 needs revisiting for this requirement; **flagged for the
orchestrator and for 1.4's author**, not decided here.]

**Tile copy and placement, verbatim.** "It sits directly under the status card because the
evidence and the only control that answers it belong together. Counts are of *rejected*
submissions over rolling windows — last 7 and last 30 days — split honeypot vs rate-limit,
because the two mean different things (a bot script vs a flood). It shows **no personal
data**: no IPs, no addresses, no payloads. Preview never increments any of these counters.
Zero state: 'Nothing blocked in the last 30 days.' The tile fetches independently of the
config and fails independently: on error it shows 'Couldn't load the blocked count' and
`[Try again]` without touching the rest of the page."
[Source: EXPERIENCE.md#4-configuring-the-form — "'Abuse blocked' tile (FR-006 criterion 5)"].
The wireframe example figures: "3 last 7 days · 11 last 30 days · Honeypot 9 · Rate limit 2"
[Source: EXPERIENCE.md#4-configuring-the-form — Screen S1 wireframe].

**Warning-banner threshold and copy, verbatim.** "A **warning banner** (`DESIGN.md` §2.10
warning, `role='status'`) appears above the status card when blocked submissions in the
rolling 24 hours exceed **20 and are at least 3× the trailing 7-day daily average** — both
conditions, so a steady low hum never cries wolf... The banner's action moves focus to the
toggle rather than closing anything — closing is offered, never automatic."
[Source: EXPERIENCE.md#4-configuring-the-form — "A warning banner"]. Copy: *"Unusual number of
blocked sign-ups — 47 in the last 24 hours, against a usual 2 a day. None of them reached your
queue and members can still join normally. If it keeps rising you can close the form for a
while." `[Close the form to new members]`* [Source: EXPERIENCE.md#4-configuring-the-form].
`[Close the form to new members]` moves focus to (and does not itself activate) 2.3's toggle —
this story never calls `PUT /api/admin/form-settings` directly.

**Aggregation is server-side, matching the rest of the admin plane.** "Insights aggregate
server-side — raw member rows never reach a browser." [Source: architecture.md#adr-007-client-state--hand-rolled-hooks-fetch-once-filter-client-side].
Although `abuse_events` carries no personal data itself (the IP is hashed, not stored raw),
the counting still happens in the API route, not by shipping raw rows to the client — keeping
one consistent pattern across the admin plane [Inference, consistent with ADR-007's stated
principle].

**Bearer-token auth pattern**, identical to every `/api/admin/*` route
[Source: architecture.md#adr-003-authn-via-supabase-auth-authz-is-binary-with-attribution-instead-of-tiers],
copied from `api/admin/subscribers.js:64-73`.

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. NEVER run tests or quote coverage here. -->

- **Approach:** manual verification against a preview deployment seeded with `abuse_events`
  rows across both reasons and both windows; no automated test runner exists in this repo (see
  2.1's Testing note).
- **Key scenarios:** seed 3 honeypot + 2 rate-limit rows inside the last 7 days, 6 more
  outside 7 days but inside 30 → tile shows 5/11 with the correct reason split; seed zero rows
  → zero-state copy; force the endpoint to error → independent error banner, rest of page
  unaffected; seed 47 events inside the last 24h against a 2/day trailing average → warning
  banner appears with those exact figures and its action focuses the toggle without opening
  the close dialog; seed 21 events inside 24h against a 15/day trailing average (exceeds the
  count but not the 3× multiple) → banner does **not** appear, proving the AND condition.
- **Per-AC verification:** AC #1 → count/breakdown accuracy against seeded rows. AC #2 → zero
  state copy exactly. AC #3 → independent failure, verified by breaking only the abuse-summary
  endpoint and confirming the rest of `/admin/join-form` still functions. AC #4 → inspect the
  raw HTTP response body for the absence of any IP-shaped string or timestamp finer than a
  day. AC #5 → the two-condition threshold test above, both the true and the near-miss case.
  AC #6 → run a 2.6 preview submission, refetch the tile, confirm no count moved.
- **Fixtures/mocks:** a set of `abuse_events` rows spanning both reasons and both the 24h and
  7d/30d windows, including the near-miss threshold case above.
- **Edge cases:** the 48-hour sweep vs 30-day-window tension flagged in Dev Notes — if 1.4's
  sweep genuinely deletes rows at 48h, the 30-day count as specified cannot be produced from
  `abuse_events` alone; this must be resolved (a rollup table, or a revised sweep window)
  before this story's AC #1 can be verified end-to-end, and is called out here as a
  cross-story testing blocker, not something this story's own code can paper over.
