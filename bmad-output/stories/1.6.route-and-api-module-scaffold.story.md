# 1.6: Route and API module scaffold

**Story ID:** 1.6
**Epic:** 1 — Data foundation
**Slug:** route-and-api-module-scaffold
**Status:** ready-for-dev

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As the **maintainer of this backlog**,
I want **each feature to own its own route module and API client file**,
so that **40+ stories can be built in parallel instead of queueing on two shared files**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. `src/routes/` exists and contains one route module per feature area, each default-exporting an
   array of `<Route>` elements: `joinRoutes.jsx`, `directoryRoutes.jsx`, `adminDirectoryRoutes.jsx`,
   `adminFormRoutes.jsx`, `adminMembersRoutes.jsx`, `dataRightsRoutes.jsx`, `adminDataRequestsRoutes.jsx`.
   Each is created as an **empty array with the file's intended contents documented in a comment**;
   the owning story fills it in.
2. `src/App.jsx` imports each route module and spreads it into the correct `<Route>` parent (public
   modules inside the `<Layout />` route; admin modules inside the `ProtectedRoute`/`AdminLayout`
   route). After this story **no other story modifies `src/App.jsx`**.
3. Every route that existed in `src/App.jsx` before this story still resolves to the same component
   at the same path, and lazy loading is preserved — this is a pure refactor with no behaviour change.
4. `src/lib/api/` exists containing `directory.js`, `members.js`, `formConfig.js`, `dataRequests.js`,
   each importing `authHeaders()` and `parseResponse()` from `src/lib/adminApi.js` and exporting
   nothing else initially.
5. `src/lib/adminApi.js` retains its existing exported functions unchanged (nothing else may break)
   plus `authHeaders()` and `parseResponse()` exported for the new domain modules. After this story
   **no other story modifies `src/lib/adminApi.js`**.
6. A short comment at the top of `src/App.jsx` and `src/lib/adminApi.js` states that both files are
   owned by story 1.6 and that new routes/clients belong in their feature module, citing ADR-016.

## Dev Notes

<!-- LOCKED. -->

- **Why this story exists.** Running the Owned-Scope conflict checker across the compiled backlog
  found `src/App.jsx` in **170 of 274** conflicting story pairs and `src/lib/adminApi.js` in a
  further **39** — 76% of all contention, on two files whose only shared property is that everyone
  appends to them. [Source: architecture.md#adr-016-per-feature-route-modules-and-per-domain-api-clients]
- **This is a pure refactor.** No route path changes, no component changes, no behaviour change.
  If a route resolves differently after this story, that is a defect, not an improvement. [Inference]
- **Current structure to preserve:** `src/App.jsx` declares every page with `lazy()` at module
  scope and wraps the whole tree in one `<Suspense fallback={<Spinner />}>`. Public routes sit
  inside `<Route element={<Layout />}>`; admin routes sit inside
  `<Route path="/admin" element={<ProtectedRoute><AdminLayout /></ProtectedRoute>}>`.
  [Source: inputs/codebase-constraints-brief.md#4-admin-ui-building-blocks]
- **Route modules export arrays, not components.** `export default [ <Route ... />, … ]` spread into
  the parent with `{...joinRoutes}`. This keeps `App.jsx`'s nesting visible in one place while
  giving each feature its own file. [Inference]
- **`adminApi.js` has no generic `request()` helper today** — each endpoint duplicates ~9 lines of
  `authHeaders()` + `fetch` + `parseResponse()`. Do **not** introduce one in this story; that is a
  behaviour-affecting refactor and this story must stay mechanical.
  [Source: inputs/codebase-constraints-brief.md#4-admin-ui-building-blocks]
- **Naming follows ADR-006:** route modules are `camelCaseRoutes.jsx`, API modules are
  `camelCase.js` under `src/lib/api/`. [Source: architecture.md#adr-006-naming-conventions]
- **No new runtime dependency.** [Source: architecture.md#adr-007-client-state--hand-rolled-hooks-fetch-once-filter-client-side]
- This story blocks a large share of the backlog, so it should be scheduled in the first wave
  alongside the migrations. [Source: epics.md#epic-1-data-foundation]

## Testing

<!-- LOCKED. STRATEGY ONLY. -->

- **Approach:** manual route-parity verification plus a lightweight smoke test; no unit tests are
  meaningful for a pure re-export refactor.
- **Key scenarios:** every pre-existing public and admin path still renders its original component;
  lazy chunks still split; `ProtectedRoute` still gates every `/admin` path.
- **Per-AC verification:** AC #1 → the seven files exist and export arrays · AC #2 → `App.jsx`
  contains no inline `<Route>` for a new feature · AC #3 → walk the full route list from the
  pre-refactor `App.jsx` and confirm each resolves identically · AC #4/#5 → the domain modules
  import the helpers and existing `adminApi.js` consumers still compile · AC #6 → comments present.
- **Fixtures / mocks:** none. An authenticated session is needed to verify the admin paths.
- **Edge cases to cover:** an unauthenticated visit to an `/admin` path must still redirect;
  the route order for `/events/:slug` versus `/events` must be preserved.
