# 2.5: Form config publish

**Story ID:** 2.5
**Epic:** 2 — Form configuration
**Slug:** form-config-publish
**Status:** ready-for-dev

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As **Ash, a GPC admin**,
I want **one Publish button that lands every wording/option edit on the live form at once, and
a warning if I try to leave with unpublished changes**,
so that **a multi-field edit becomes live in a single instant instead of drifting live one
field at a time, and I never accidentally leave `/join` showing something I only meant to
draft.**

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. Given an admin clicks Publish with pending draft changes, when the request succeeds, then a
   new `form_config_versions` row is written containing the fully resolved config (2.1's
   registry merged with the current draft overlay) as `jsonb`, a new `version` identifier,
   `published_at` and `published_by`, and 2.2's `GET /api/join/config` returns this new
   content from that moment on.
2. Given a publish request, when it is processed, then **every** drafted field — question
   labels, help text, required flags, every option's label/order/retired state, intro text,
   closed message — is captured together in the same version row. Publish is all-or-nothing:
   there is no partial-publish outcome.
3. Given an admin navigates away from any `/admin/join-form/*` route with unpublished draft
   changes (a route change out of the section, or a tab close), then a confirmation dialog
   offers `[Publish now]` / `[Stay here]` / `[Leave without publishing]`, and **no path in that
   dialog discards the draft** — losing it requires the separate, explicit `[Discard changes]`
   control (2.4/2.3's editors) with its own confirmation.
4. Given a publish request fails, then the draft is left completely intact on screen — never
   reverted or reloaded — an inline banner states the failure with `[Try again]`.
5. Given another admin published a different version while this admin was still editing, when
   this admin attempts to publish, then the attempt is rejected with a message naming the
   conflict plus a plain-language diff of what changed, and this admin's own draft is never
   silently overwritten or auto-merged with the intervening publish.
6. Given publish succeeds, then the sticky publish bar transforms in place into a success
   confirmation naming the outcome — never a toast (per adjudication A6) and never a navigation
   away from whichever of S1/S2/S3 the admin was on.

## Tasks / Subtasks

- [ ] Write `api/admin/form-config/publish.js` — bearer-token verified, resolves the current
  draft overlay against 2.1's registry into one `jsonb` object, inserts a new
  `form_config_versions` row, marks it current, writes `actioned_by`/`actioned_at` (AC: #1,
  #2)
- [ ] Implement optimistic concurrency: the client sends the `draft_version` (or
  `updated_at`) it last fetched; the server rejects with `409` if the draft has moved on
  since, returning enough detail for the plain-language diff (AC: #5) — "the config row
  supports optimistic concurrency (without it the publish-conflict state... cannot exist and
  the last publish silently wins)" [Inference — mechanism, cited requirement below]
- [ ] Extend `useFormConfigDraft.js` (2.3/2.4's hook) with `publish()`, `discardDraft()`, and
  a computed `changeCount` the sticky bar and 2.3's dashboard status line both read (AC: #1,
  #2, #6)
- [ ] Wire the actual Publish/Discard buttons into `JoinFormLayout.jsx`'s sticky bar shell
  (built visually by 2.3): absent when `changeCount === 0`, showing the count and both actions
  otherwise (AC: #6)
- [ ] Implement the unsaved-changes guard: a route-change listener plus a `beforeunload`
  handler scoped to `/admin/join-form/*`, firing the three-option dialog only on navigation
  **out of** the section (AC: #3)
- [ ] Implement the publish-conflict response: parse the `409`, render "Someone else published
  a change while you were editing" plus `[See what changed]` showing a plain-language diff
  line per changed field (e.g. `'Weekly Newletter' renamed to 'Weekly Newsletter' by Kristina,
  14:20`) (AC: #5)
- [ ] Implement the publish-failure banner (network/5xx) distinct from the conflict case,
  never clearing the draft (AC: #4)
- [ ] Implement the success transform: the bar's own content swaps in place, includes
  `[View the live form ↗]`, collapses after 6s or on the next edit (AC: #6)

## Dev Notes

<!-- LOCKED. Concrete guidance compiled from the planning docs WITH SOURCE CITATIONS.
     Cite every fact: [Source: prd.md#anchor] / [Source: architecture.md#anchor] /
     [Source: ux-design.md#anchor]. Label your own inferences [Inference]. -->

**The publish contract, verbatim.** "Editing writes to the overlay tables as **draft**.
Publishing snapshots the resolved config into a new version row and marks it current. This
makes FR-004's requirement to publish a *consent version* the same act as publishing the form
(ADR-010)." [Source: architecture.md#adr-008-form-configuration--code-defined-registry-database-overlay-and-versioned-publish].
`GET|PUT /api/admin/form-config` writes draft; `POST /api/admin/form-config/publish`
snapshots a new version [Source: architecture.md#6-api-specifications]. This story owns only
the `publish` sub-route — `GET`/`PUT` on the base `form-config` resource belong to 2.3/2.4,
which this story must not alter beyond calling them.

**All-or-nothing is explicit UX language, not an implementation detail.** "Labels, help text,
required flags, options, intro text and closed message are drafted, previewed and published
as one atomic set; publish is all-or-nothing, which is what makes a multi-step edit land in a
single instant." [Source: EXPERIENCE.md#4-configuring-the-form — "Draft → publish (A4)"]. The
**one exception is `is_open`**, which 2.3 already applies immediately and which this story's
publish action never touches — publishing must not accidentally flip or re-write `is_open`.

**Optimistic concurrency is a named architecture gap, not this story's invention.** "Two
backend assumptions: the configuration row is seeded from `FORM_STRUCTURE` by migration...
and the config row supports optimistic concurrency (without it the publish-conflict state
above cannot exist and the last publish silently wins)."
[Source: EXPERIENCE.md#4-configuring-the-form — "Notes for architecture"]. This is flagged in
the UX doc as unresolved by the PRD — this story is the one that must actually implement the
mechanism (a version/timestamp field compared at publish time) since it is the only place a
conflict becomes visible. No source document specifies the exact column; a `draft_updated_at`
or integer `draft_revision` on the overlay is a reasonable, minimal design. [Inference]

**Unsaved-changes guard, verbatim copy and behaviour.** "fires on navigation *out of*
`/admin/join-form/*`, never between the three screens. 'You have unpublished changes — your 3
changes are saved as a draft, so they'll still be here when you come back. Members won't see
them until you publish.' `[Publish now]` (primary) · `[Stay here]` · `[Leave without
publishing]` (text). **No path in this dialog discards anything**; discarding needs the
explicit `[Discard changes]`, which has its own confirm."
[Source: EXPERIENCE.md#4-configuring-the-form — "Cross-screen behaviour"]. This is the single
most consequential behavioural rule in this story: a generic "unsaved changes" dialog that
offers a bare "Leave" as a synonym for "discard" would violate this contract.

**Publish-conflict copy, verbatim.** "Someone else published a change while you were editing.
Review what changed, then publish again." `[See what changed]` renders a plain-language diff —
"'Weekly Newletter' renamed to 'Weekly Newsletter' by Kristina, 14:20". Ash's draft is never
overwritten." [Source: EXPERIENCE.md#4-configuring-the-form — "Cross-screen behaviour"].

**Success and failure banners, verbatim.** Success: "Published. Members see your changes
now." + `[View the live form ↗]`, no toast, no navigation, collapses after 6s or on the next
edit, focus **not** moved (Ash is mid-flow). Failure: "Couldn't publish — your 3 changes are
still saved as a draft." + `[Try again]`.
[Source: EXPERIENCE.md#4-configuring-the-form — Screen S1 states table]. `role="alert"` on
failure, nested `role="status"` on success, per the shared-region rule (adjudication A13)
[Source: sharding-context.md#ux-rulings-that-override-the-long-form-drafts].

**Dialog primitive — a cross-epic dependency, flag it.** DESIGN.md specifies one shared
`Dialog` primitive with `ConfirmModal` rebuilt on it, owned by Epic 5 story 5.1
[Source: DESIGN.md#29-modal--dialog-new-extends-confirmmodal; epics.md#epic-5-moderation-and-shared-admin
— "5.1 shared-admin-chrome: ...one `Dialog` primitive..."]. `epics.md`'s cross-epic dependency
map does **not** list Epic 2 as blocked-by Epic 5, so this story cannot assume 5.1 has landed.
Build the unsaved-changes dialog against `DESIGN.md` §2.9's contract directly (`role="dialog"`
+ `aria-modal` + focus trap + Escape + focus return) using a local implementation if 5.1 does
not yet exist, and swap to the shared primitive once it does — this divergence is flagged for
the orchestrator, not silently resolved. [Inference]

**Attribution.** `published_by` is the caller's `auth.uid()`, matching every other
state-changing admin action in this feature
[Source: architecture.md#adr-003-authn-via-supabase-auth-authz-is-binary-with-attribution-instead-of-tiers].

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. NEVER run tests or quote coverage here. -->

- **Approach:** manual verification against a preview deployment with two authenticated admin
  sessions available (to exercise the publish-conflict path), plus a keyboard-only pass on the
  unsaved-changes dialog; no automated test runner exists in this repo (see 2.1's Testing
  note).
- **Key scenarios:** publish with 3 pending changes across label/option/intro-text → single
  new `form_config_versions` row, all 3 reflected in 2.2's response; navigate away with a
  pending draft → three-option dialog, each option's actual effect verified (Publish now
  actually publishes before leaving; Stay here cancels navigation; Leave without publishing
  actually leaves and the draft is still there on return); trigger a conflict by publishing
  from a second session mid-edit → 409 handled, diff shown, first session's draft untouched;
  force a network failure on publish → draft intact, retry banner, retry succeeds.
- **Per-AC verification:** AC #1 → new version row content matches the draft exactly. AC #2 →
  a multi-field edit lands as one version, not several. AC #3 → each of the three dialog
  outcomes, and confirm no route change *within* `/admin/join-form/*` (e.g. S1→S2) ever
  triggers it. AC #4 → draft persists across a simulated 500. AC #5 → the two-session conflict
  scenario. AC #6 → in-place bar transform, no `navigate()` call, 6s auto-collapse.
- **Fixtures/mocks:** two admin sessions/tokens for the conflict scenario; a draft with
  changes spanning all four editable surfaces (label, option, required flag, intro text) to
  prove all-or-nothing publish.
- **Edge cases:** publishing with **zero** pending changes — the bar should be absent per
  2.3's "Default" state, so this scenario should be unreachable through the UI; verify the
  server-side `publish` endpoint still behaves sanely (a no-op version, or a `400`) if called
  directly with no draft delta, so a stray API call cannot create meaningless version rows.
  [Inference]

## Learnings from Previous Stories

<!-- Carried forward from completed sibling stories: chosen patterns, gotchas, helpers
     created, naming conventions. Only what is actionable for THIS story. -->

- 2.3 built `JoinFormLayout.jsx`'s publish-bar **shell** as visual-only, deliberately leaving
  the button behaviour for this story — do not rebuild the shell, extend it (from 2.3).
- 2.3 flagged that `is_open` is the one field that bypasses draft/publish entirely; this
  story's publish action must never read or write `form_settings.is_open` (from 2.3).
- 2.4 built option-level draft operations (`addOption`/`retireOption`/etc.) on
  `useFormConfigDraft.js` — this story's `changeCount` must count those operations too, not
  just label/help/required edits (from 2.4).
- 2.3 and 2.4 both flagged the `Dialog` primitive as a cross-epic dependency on 5.1 with no
  formal blocked-by relationship in `epics.md` — this story inherits the same fallback
  approach rather than inventing a third local dialog implementation (from 2.3, 2.4).
