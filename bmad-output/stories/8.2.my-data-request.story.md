# 8.2: Start a data-rights request without becoming an enumeration oracle

**Story ID:** 8.2
**Epic:** 8 — Data rights and privacy
**Slug:** my-data-request
**Status:** ready-for-dev

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As **a member (with no account or login)**,
I want **to type my email address at `/my-data` and be sent a link that proves it's me**,
so that **I can manage my own data without emailing an admin and waiting — and without that page
ever revealing to anyone whether an address belongs to a GPC member**.

## Acceptance Criteria

<!-- LOCKED. External dev tools must not edit Acceptance Criteria. -->

1. Given `POST /api/my-data/request` receives a request, then it **always** returns
   `200 { ok: true }` — identically whether the submitted email matches a member, matches no
   member, or the honeypot field is completed — never a different status code or body shape that
   would let a caller distinguish these cases.
2. Given the submitted email matches an existing member, when the request is processed, then
   exactly one signed, expiring (60-minute), single-purpose request token is minted for that
   member and one `outbound_emails` row is queued carrying only the token and the recipient
   reference — no other personal data in `payload jsonb`.
3. Given the submitted email matches no member, when the request is processed, then no token is
   minted and no `outbound_emails` row is written, while the response remains identical to AC1.
4. Given the honeypot field is completed, when the request is processed, then it is discarded
   before any member lookup runs, one `abuse_events` row is written with `reason = 'honeypot'`,
   and the response remains identical to AC1.
5. Given `/my-data` loads with no token in the URL, then it presents one labelled email field
   (`id` + `<label htmlFor>`, `autocomplete="email"`, `inputmode="email"`) and the off-screen
   honeypot field; submitting moves the page to the "Check your inbox" state, which echoes back
   the exact string the member typed — never a value read from any lookup.
6. Given the "Check your inbox" state, then its "Send another link" control is disabled for 60
   seconds after each successful send and its accessible name updates only at the 60/30/10/0-second
   marks, never on every tick.
7. Given the "Check your inbox" copy in any of its states (first send, resend success, resend
   network failure), then none of the visible or accessible text states or implies whether the
   address is registered.

## Tasks / Subtasks

<!-- Every task maps to one or more ACs via (AC: #N). A task with no AC mapping is a smell. -->

- [ ] Create `src/lib/dataRights/tokens.js` — `mintDataRightsToken({ memberId, purpose, ttlMinutes,
  claims })` (`claims` optional, e.g. `{ requestId }` for a future cancel-purpose token) and
  `verifyDataRightsToken(token, { expectedPurpose })` using Node's built-in `crypto` HMAC
  (AC: #2). Design the claims bag generically now — story 8.3a mints a `purpose: 'cancel'` token
  scoped to one `data_requests` row using this same module and must not need to modify it.
- [ ] Create `api/my-data/request.js` — parse body defensively, honeypot check first, member
  lookup by lower-cased email against `members`, mint token + queue email only on a match, always
  respond `200 { ok: true }` (AC: #1, #2, #3, #4)
- [ ] Write one `abuse_events` row (`reason = 'honeypot'`) on a honeypot trip, mirroring the
  existing abuse vocabulary (AC: #4)
- [ ] Queue the `outbound_emails` row (`template_key = 'my_data_manage_link'`,
  `payload = { token }`) in the same request as the mint, never sent inline (AC: #2)
- [ ] Build `src/pages/MyData.jsx` — D-1 (email field + honeypot + submit) and D-2 (check-your-inbox)
  as two states of one route, `/my-data`, added to `src/App.jsx` inside the public `Layout` route
  group (AC: #5)
- [ ] Build `src/components/data-rights/CooldownButton.jsx` — 60s disabled window, accessible-name
  updates only at 60/30/10/0s (AC: #6)
- [ ] Write D-1/D-2 copy exactly per the specified strings, with no conditional branching on
  registration state anywhere in the client or server response (AC: #7)
- [ ] Pad the request handler's response time to a fixed floor (~600ms) so a match vs. no-match
  branch cannot be timing-distinguished (AC: #1)

## Dev Notes

<!-- LOCKED. Concrete guidance compiled from the planning docs WITH SOURCE CITATIONS.
     Cite every fact: [Source: prd.md#anchor] / [Source: architecture.md#anchor] /
     [Source: ux-design.md#anchor]. Label your own inferences [Inference]. -->

- **Component contract.** "`POST /api/my-data/request` (emails a signed, expiring token — no
  member login exists)... **Security note.** The request form takes an email address and must
  not become an oracle: it returns the same response whether or not the address is registered,
  and the actionable link arrives only in the mailbox. The token is single-purpose, expiring, and
  grants access to *that member's* data only."
  [Source: architecture.md#component-data-rights-public--admin]
- **API contract, exact.** "Takes an email; **always** returns `200 { ok: true }` whether or not
  it is registered. Queues a signed, expiring, single-purpose token email (ADR-014, ADR-015)."
  [Source: architecture.md#6-api-specifications]
- **FR this satisfies.** "Given a member follows the withdrawal link from any email or the
  privacy page, when they confirm, then a removal request is recorded..."
  [Source: prd.md#FR-023] — this story delivers the entry point that leads there, not the request
  itself (that is story 8.3a).
- **Token mechanism is not specified in architecture.md beyond "signed, expiring,
  single-purpose"** [Source: architecture.md#component-data-rights-public--admin]. No token table
  exists or may be added — migrations `028`–`031` are reserved and `031` (owned by story 1.4)
  already lists everything Epic 8 gets: `abuse_events`, `outbound_emails`, `data_requests`, sweep
  functions, `erase_member()` [Source: architecture.md#3-architecture-decision-records — ADR-002
  migration table]. **[Inference]** Implement the token as a stateless, self-verifying HMAC-SHA256
  signature over `{ memberId, purpose, exp }` using Node's built-in `crypto` module — already
  available in a Vercel Node serverless function, so this adds no new runtime dependency, which
  the PRD constrains against without a logged decision [Source: prd.md#constraints]. This
  satisfies "expiring" and "single-purpose" (a `purpose` claim scoped to one use-family) exactly
  as specified. EXPERIENCE.md's UX also describes a "second time" reuse warning implying true
  single-*use* consumption tracking [Source: EXPERIENCE.md#7-data-rights-errors-and-edge-cases],
  which would require persisted "used" state with no home in the reserved migrations — **treat
  this as a deferred nicety, not an AC**, since architecture.md's own wording is "single-purpose",
  not "single-use". Flag to the orchestrator if this reading is wrong.
- **Honeypot pattern to copy exactly.** "a visually hidden, `aria-hidden`, `tabindex="-1"` field
  with an innocuous name. If completed: discard silently, record an `abuse_event`, return the
  ordinary success shape" — this is ADR-011's layer 2, written for `/join` but the same UX
  wireframe shows an identical honeypot on `/my-data`'s D-1
  [Source: architecture.md#adr-011-anti-abuse-in-postgres-and-the-request-handler--no-new-third-party-processor];
  [Source: EXPERIENCE.md#7-data-rights-errors-and-edge-cases — Screen D-1 wireframe, "[ honeypot
  'Company' — off-screen ]"]. **[Inference]** ADR-011's Postgres rate-limit layer (3/hr, 20/24h)
  is scoped explicitly to `POST /api/join/submit` and is not extended to this endpoint by any
  source document — do not invent a threshold for it here; the honeypot plus the non-oracle
  response plus the client-side 60s cooldown are this story's abuse controls. If probing in
  production shows this insufficient, that is a decision for architecture, not this story.
- **The `outbound_emails` payload rule.** "`payload jsonb` holds only what the template needs...
  **No personal data beyond the recipient reference.**"
  [Source: architecture.md#adr-014-outbound-email-is-a-queue-table-drained-by-a-pluggable-sender]
  — the recipient is already `to_member_id`, so `payload` here needs only `{ token }`.
- **D-1 / D-2 screen contracts, exact copy and states** (masked-address display, honeypot
  placement, `autocomplete`/`inputmode`, the "Sending…" loading label, the 60s `CooldownButton`,
  and the identical-response rule across known/unknown/rate-limited/honeypot-caught) are specified
  in full, including the accessible-name timing rule for the countdown ("updates only at
  60/30/10/0s, never every second")
  [Source: EXPERIENCE.md#7-data-rights-errors-and-edge-cases — Screens D-1 and D-2].
- **Constant-time response.** "D-1's response is constant — same copy, same screen, same status,
  **padded to a fixed time floor (≈600ms)**" [Source: EXPERIENCE.md#7-data-rights-errors-and-edge-cases].
- **Member lookup.** `members.email` is `citext, unique`
  [Source: architecture.md#5-data-model — Entity: `members`], so a case-insensitive match is a
  direct `.eq('email', normalised)` — no application-side case folding needed beyond trimming,
  though lower-casing before comparison mirrors the existing `api/subscribe.js` convention
  [Source: inputs/codebase-constraints-brief.md#5-public-ui-building-blocks--design-tokens].
- **API route shape to copy.** Defensive body parsing, always-JSON responses via try/catch, and
  the `{ error: string }` failure shape are the established pattern in `api/subscribe.js`
  [Source: inputs/codebase-constraints-brief.md#3-the-publicprivate-boundary--how-it-is-actually-enforced]. This endpoint additionally never varies its *success* shape (ADR-005 non-disclosure)
  [Source: architecture.md#adr-005-error-and-response-convention].
- **No form library, no new dependency.** Continue the hand-rolled `useState`/`useEffect` pattern;
  `NewsletterBanner.jsx`'s five-state machine (`idle | submitting | success | partial | error`) and
  its single `role="status" aria-live="polite"` region are the closest existing precedent for a
  public form → API screen [Source: inputs/codebase-constraints-brief.md#5-public-ui-building-blocks--design-tokens].
- **Accessibility floor (NFR-008)** applies in full: `id`/`<label htmlFor>` pairing (absent
  everywhere else in the codebase today), one polite region, one alert region per page, 16px
  minimum input text, visible `:focus-visible`
  [Source: bmad-output/context/sharding-context.md#accessibility-floor-nfr-008--applies-to-every-ui-story].
- **Out of scope: the mail-token entry point.** EXPERIENCE.md describes a second, wider "mail
  token" embedded in the footer of **every** GPC email (rotates each send, pre-fills the D-1
  address as a read-only `EmailChip`) [Source: EXPERIENCE.md#7-data-rights-errors-and-edge-cases —
  "Two token types"]. That token is generated wherever outbound email templates are rendered,
  which is the outbound-email-queue's territory (story 5.5), and this story does not build it.
  `/my-data` here handles the cold, no-token arrival only (typed email). **[Inference]** If a
  `?t=` mail-token param is present when 5.5 ships, `EmailChip` and the pre-fill behaviour are a
  follow-up enhancement to this page, not a gap in this story's ACs.

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. NEVER run tests or quote coverage here. -->

- **Approach:** No automated test runner exists in this repo
  [Source: inputs/codebase-constraints-brief.md#1-stack--deployment-reality-non-negotiable]. Verify
  the API contract with manual/scripted `curl` calls against a non-production Supabase project
  (three cases: known email, unknown email, honeypot filled) and diff the three raw HTTP responses
  byte-for-byte for status, headers and body. Verify the UI by hand against each AC.
- **Key scenarios:** known-email request mints exactly one token and one queued email; unknown-email
  request mints nothing but returns the same response; honeypot request writes an `abuse_events`
  row and mints nothing; resend button re-arms only after 60s; D-2 copy is identical regardless of
  which of the three server branches ran.
- **Per-AC verification:** AC #1 → three `curl` requests (known/unknown/honeypot), diff status +
  body; AC #2 → inspect `outbound_emails` and confirm exactly one row with `payload = { token }`
  and no other member fields; AC #3 → confirm zero `outbound_emails` rows for an unknown address;
  AC #4 → confirm an `abuse_events` row with `reason = 'honeypot'` and zero member-table reads (log
  inspection, since no member row should be touched); AC #5 → keyboard-only walk-through of D-1 →
  D-2, confirming the echoed address is the typed string, not a fetched one; AC #6 → time the
  resend button's disabled state and confirm the accessible name only changes at the four
  checkpoints; AC #7 → read every string surfaced in D-2's three states aloud and confirm none
  implies registration status.
- **Fixtures / mocks:** at least one seeded `members` row with a known email; a request from an
  email guaranteed absent from `members`; the honeypot field populated programmatically (a real
  browser would never do this, so this case needs a direct `fetch`/`curl`, not a UI script).
- **Edge cases to cover:** an email with mixed case or surrounding whitespace still matches an
  existing member; a malformed email (no `@`) is rejected with a **field-level** validation error
  before the request is ever sent (this is client-side shape-checking, not a registration check,
  so it does not violate AC1 — no request reaches the server for an empty/malformed field); two
  rapid resend clicks within the 60s window are blocked client-side and, if the button is somehow
  reached anyway (e.g. a replayed request), the server-side response is still AC1-identical either
  way, since minting a second token for the same member is not itself disclosive.
