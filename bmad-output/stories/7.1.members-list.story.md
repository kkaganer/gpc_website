# 7.1: Members list

**Story ID:** 7.1
**Epic:** 7 — Member records and insights
**Slug:** members-list
**Status:** ready-for-dev

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As **Ash, a GPC admin**,
I want **to search and filter every member who has filled in the join form, with the headline
counts always visible**,
so that **I can find one person's record quickly, or see the shape of the whole membership at a
glance, without ever touching Supabase**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. Given an admin with a valid bearer token calls `GET /api/admin/members`, when it responds, then
   each row contains only the summary projection — id, first name, business name (if listed),
   joined date, group, directory status, newsletter consent state, a resubmitted flag and an
   open-data-request flag — and never a survey answer, free-text answer or consent record.
2. Given more than 1,000 member rows exist, when the endpoint runs, then no more than 1,000 rows
   are returned (`MAX_ROWS = 1000`), ordered by joined date descending.
3. Given the members list page has loaded, when the stat tiles render (Members, In the directory,
   Business branch, Career branch, Newsletter consent, Data requests open), then every tile is
   computed over the full fetched set, never the filtered or currently-visible subset, and the
   page states this explicitly.
4. Given an admin types into the search box (name, email or business name) or sets the group,
   directory-status or consent filter, when the list updates, then it narrows client-side with no
   additional network request, and a "Showing X of Y" count updates to match.
5. Given the filtered list contains more than 100 rows, when the admin reaches the end of the
   first `PAGE_SIZE = 100` rows, then a "Show 100 more" control reveals the next page in place
   without losing the active search term, filters, or scroll position.
6. Given a request to `GET /api/admin/members` is missing a bearer token, or the token is invalid
   or expired, then the response is `401 { error }` with no member data in the body.

## Dev Notes

<!-- LOCKED. Concrete guidance compiled from the planning docs WITH SOURCE CITATIONS.

**The privacy boundary — state it, do not just build to it.** This screen and its two siblings
(7.2, 7.4) are "the only screens where private member data is legitimately on screen"
[Source: EXPERIENCE.md#5-member-records-and-demand-insights]. Six boundaries apply here
specifically: every read goes through `/api/admin/*` with a server-verified bearer token, never
the anon key; **no personal data in a URL** — search and filter state live in component state,
deliberately not the query string, because `?search=hannah@example.com` writes an email into
history, referer headers and access logs (a conscious divergence from FR-019's public-directory
pattern, which is fine because a category is not personal data); no personal data in logs,
notifications, document titles or filenames — the title is exactly `"Members | GPC Admin"`; stat
tiles state counts, never people [Source: EXPERIENCE.md#5-member-records-and-demand-insights].

**FR-012 acceptance criteria this story delivers:** name/group/submission-date/directory-status/
newsletter-consent on each row; search by name, email or business name; filter by group, directory
status, consent state; "more can be loaded without losing filters"
[Source: prd.md#FR-012]. NFR-010 requires the admin members list to "remain usable at 1,000 member
records... with no view loading an unbounded result set"
[Source: prd.md#NFR-010]. NFR-002 requires every private-data endpoint to reject a missing,
malformed or expired token with a 401 and no data body [Source: prd.md#NFR-002]. NFR-006 (data
minimisation) is why the list endpoint returns a summary projection and defers survey answers and
consent text to the detail route [Source: prd.md#NFR-006].

**Auth block — copy verbatim** into `api/admin/members.js`, matching every existing `/api/admin/*`
route:
```js
const token = req.headers.authorization?.replace('Bearer ', '')
if (!token) return res.status(401).json({ error: 'Not authenticated' })
const { data: { user: caller }, error } = await supabase.auth.getUser(token)
if (error || !caller) return res.status(401).json({ error: 'Invalid or expired session' })
```
[Source: architecture.md#adr-003-authn-via-supabase-auth-authz-is-binary-with-attribution-instead-of-tiers],
same pattern in `api/admin/subscribers.js:65-73` in this repo.

**Bounds — LOCKED, do not invent different numbers:** `MAX_ROWS = 1000` server-side,
`PAGE_SIZE = 100` client-side "Show N more", matching `api/admin/subscribers.js`'s
`MAX_ROWS = 1000` and `SubscribersManager.jsx`'s `PAGE_SIZE = 100`
[Source: architecture.md#adr-007-client-state--hand-rolled-hooks-fetch-once-filter-client-side].

**Stat tiles over the FULL set — the existing convention.** `SubscribersManager.jsx` computes
`consent`/`counts` with `useMemo(() => tallyConsent(subscribers), [subscribers])` over the whole
fetched array, never the filtered list, and the filtered/`visible` slice is a separate derived
value (`SubscribersManager.jsx:227-240`). Reproduce this shape exactly: one `useMemo` over the full
set for tiles, one over the full set + filters for the list, one `.slice(0, visible)` for the page
window [Source: architecture.md#adr-007-client-state--hand-rolled-hooks-fetch-once-filter-client-side].
The wireframe's explicit tile notice — **"Every tile counts ALL 216 members. Filters below change
the list only, never the tiles."** — is required copy, not decoration
[Source: EXPERIENCE.md#5-member-records-and-demand-insights].

**Exact summary projection.** "The list endpoint returns a *summary projection only* (id, first
name, business, email, postcode, group, joined, resubmitted, directory status, newsletter state,
open-request flag) — never survey answers or consent text, which load on the detail route.
~250 bytes/row ≈ 250KB at 1,000 members... Escape hatch: above 500KB or 2,000 rows, move search and
paging server-side" [Source: EXPERIENCE.md#5-member-records-and-demand-insights]. Note the
wireframe additionally states email is shown muted beneath the name/business line at all widths,
and postcode is added as the last table column only at `≥1024px`, "being least often needed and
most sensitive to shoulder-surfing"
[Source: EXPERIENCE.md#5-member-records-and-demand-insights]. The resubmitted flag is derived from
`member_submissions` carrying "one row per submission event, so a resubmission is an additional
row" [Source: architecture.md#5-data-model] — `count(*) > 1` per member. **[Inference]** exact
boolean derivation, not stated verbatim in any source. The open-data-request flag reads
`data_requests` (columns `member_id`, `kind`, `status`, per ADR-015)
[Source: architecture.md#adr-015-erasure-and-withdrawal-run-through-one-security-definer-function];
its precise `status` vocabulary belongs to Epic 8 (stories 8.2–8.4), not yet authored — treat any
row without a completed/actioned outcome as "open" and confirm the exact check once Epic 8 lands.
**[Inference / cross-epic coordination point.]**

**Component reuse and new pieces.** `MembersManager`; `StatTile` lifted out of
`SubscribersManager` into `src/components/admin/StatTile.jsx` and used by both;
`WholeSetNotice`; `MemberFilters` (search + three `<select>`, every control `htmlFor`/`id`);
`MemberRowCard` / `MemberTable` (one data shape, two renderers); `Badge` with new `group-*`,
`dir-*`, `news-*` variants; `ShowMoreButton`; shared `Spinner`
[Source: EXPERIENCE.md#5-member-records-and-demand-insights]. **Pills reuse `SubscribersManager`'s
module-scope class-map *idiom* and NONE of its values** — that ramp is ~3.4:1/~3.1:1 and fails AA
at pill size; use `DESIGN.md` §2.7's verified values for directory status
[Source: DESIGN.md#2-component-specifications] (adjudication A15). `group-*` and `news-*` are new
variants this story adds and DESIGN.md does not enumerate — pick colours from the same DESIGN.md
§2.7 palette family (background tint + ≥4.5:1 text) and pair every pill with an icon, never colour
alone. **[Inference]** exact hex values for these two new families.

**Server-side, matching the site's existing shape.** Fetching is `useState`+`useEffect` or a
hand-rolled hook in `src/hooks/`; no React Query, SWR, Redux or Zustand
[Source: architecture.md#adr-007-client-state--hand-rolled-hooks-fetch-once-filter-client-side].
Copy `authHeaders()`/`parseResponse()` from `src/lib/adminApi.js` rather than inventing a generic
`request()` helper (none exists) [Source: inputs/codebase-constraints-brief.md#4-admin-ui-building-blocks].

**Accessibility.** Below `md:` the list is a `<ul>` of links whose accessible name composes to
"Hannah, Little Fox Photography, joined 4 March 2026, both groups, listing published, newsletter
yes" — never a bare colour or abbreviation; ≥`md:` becomes a real `<table>` with `scope="col"`
headers and a right-aligned "Open" link — **never a `<div onClick>` row**
[Source: EXPERIENCE.md#5-member-records-and-demand-insights]. This satisfies the accessibility
floor's ban on `<div onClick>` rows [Source: architecture.md#3-architecture-decision-records].

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. NEVER run tests or quote coverage here. -->

- **Approach:** integration tests against `api/admin/members.js` with a seeded Supabase instance
  (or mocked Supabase client) covering row shape, the `MAX_ROWS` cap, and auth rejection; component
  tests for `MembersManager.jsx` covering tile stability under filtering, search debounce, and
  "Show more" state preservation.
- **Key scenarios:** empty state (zero members); more than 1,000 members (cap enforced, order
  correct); a search term matching zero, one, and many rows; each filter dimension in isolation and
  combined; "Show more" pressed after a filter change (paging resets); filters cleared restores
  full list and returns focus to search.
- **Per-AC verification:** AC #1 → inspect the response shape for absence of `answers`/
  `consent_text` keys; AC #2 → seed >1000 rows, assert response length and ordering; AC #3 → assert
  tile values are unchanged before/after applying a filter that reduces the visible rows; AC #4 →
  simulate typing and filter changes, assert no additional `fetch` call fires and the count line
  updates; AC #5 → assert "Show 100 more" preserves `search`/filter state and does not reset scroll
  to top; AC #6 → call the endpoint with no/garbage/expired token, assert `401` and an empty body.
- **Fixtures / mocks:** seeded `members`/`directory_listings`/`member_consents`/`member_submissions`/
  `data_requests` rows spanning every group, directory status, and consent state; a fake bearer
  token for the 401 paths; a large (>1000-row) fixture for the cap test.
- **Edge cases to cover:** a member with no directory listing at all ("Not requested" pill, not an
  error); a member with more than one submission (resubmitted flag true); a member with an open
  data request; two members with very similar names (disambiguation via business name/email);
  zero-match search/filter combination.
