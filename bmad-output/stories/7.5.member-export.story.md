# 7.5: Member export

**Story ID:** 7.5
**Epic:** 7 — Member records and insights
**Slug:** member-export
**Status:** ready-for-dev

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As **Ash, a GPC admin**,
I want **to download the currently filtered member list, or one member's complete record, as a
file with no personal data leaking through its own filename or confirmation message**,
so that **I can do offline analysis or hand a member a portable copy of their data, safely**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. Given an admin opens the export dialog from the members list and confirms CSV format, then a
   file downloads containing one row per member currently shown in the active filtered view, one
   column per question using that question's **current published label**, identity columns, and
   per-purpose consent columns (decision, version, UTC timestamp, capture method), with a line-1
   comment row stating the export date and the filters applied.
2. Given an admin opens the export dialog from a single member's record and confirms a format, then
   the downloaded file contains that member's complete record — every answer, their full
   append-only consent history as an ordered list, and their directory listing state — in CSV or
   JSON, the JSON shape being the one handed to a member exercising a portability request.
3. Given a filename is generated for either export, then it contains no personal data — only a
   fixed prefix, the export date, and either a row count (filtered export) or the member's opaque
   uuid (single-member export); never a name, email or postcode.
4. Given an export completes, then the confirming banner beside the triggering button states only a
   count — "Downloaded 216 member records." or "Downloaded 1 member record." — and never a name or
   email, with no toast anywhere.
5. Given `POST /api/admin/members/export` is called without a valid bearer token, or with an invalid
   or expired one, then it returns `401 { error }` and no file content.
6. Given a filtered export is requested, then the request identifies members by the opaque id list
   the client already holds from its current filtered view — no free-text search term or filter
   criteria is ever sent as a URL query parameter.

## Dev Notes

<!-- LOCKED. Concrete guidance compiled from the planning docs WITH SOURCE CITATIONS.

**Nothing to build on. "There is no export helper anywhere in the codebase — no download utility,
no serialiser, no `Blob`. This is net-new and needs its own module and tests, because the failure
mode is silently emitting a broken or over-broad file of personal data"**
[Source: EXPERIENCE.md#5-member-records-and-demand-insights]. The constraints brief confirms: "CSV
export — Absent everywhere. No download helper, no serialiser, no `Blob`/`createObjectURL` in the
codebase. The only export-shaped affordance is copy-HTML-to-clipboard in
`NewsletterManager.jsx:58-66`" [Source: inputs/codebase-constraints-brief.md#6-what-does-not-exist-and-must-be-built-or-decided].
Do not look for a pattern to copy for the serialiser or the `Blob` trigger — there is none.

**FR-013 acceptance criteria this story delivers:** exporting the current filtered view produces
one row per member with all answers as columns; exporting a single member produces their complete
record in a portable format; the export respects the active filters shown on screen; exports are
available only to authenticated admins [Source: prd.md#FR-013]. NFR-002 governs the endpoint's auth
requirement identically to every other `/api/admin/*` route [Source: prd.md#NFR-002].

**Downloading is the one act that moves data outside the admin panel's protections, so it is the
one act confirmed.** "Downloading is the one act that moves data outside these protections, so it
is the one act confirmed (S3)" [Source: EXPERIENCE.md#5-member-records-and-demand-insights]. The
dialog's warning body is specified copy: **"Once it's on your computer it's outside the admin
panel's protections. Keep it somewhere safe and delete it when you're done with it."**
[Source: EXPERIENCE.md#5-member-records-and-demand-insights]. "Nothing states a retention
expectation for an exported file once it is on Ash's laptop. The dialog's 'delete it when you're
done with it' is the only control; more than an instruction would be a new requirement"
[Source: EXPERIENCE.md#5-member-records-and-demand-insights] — do not add a retention mechanism
beyond that instruction; it is out of scope.

**Filenames are a leak surface — treated as one.** "Filenames carry no personal data:
`gpc-members-2026-08-18-216-records.csv`; `gpc-member-8f2c4a1b-2026-08-18.json`. A filename appears
in the Downloads shelf, in file pickers and in screen shares"
[Source: EXPERIENCE.md#5-member-records-and-demand-insights]. Reproduce these exact filename shapes.

**Contents — exact contract.** "CSV: one row per member; one column per question using the
question's **current published label**; identity columns; per-purpose consent columns (decision,
version, UTC timestamp, capture method); multi-selects semicolon-joined in one quoted cell; retired
options export their historical label; line 1 is a comment row stating the export date and the
filters applied. JSON: the complete record with the append-only consent history as an array and
ISO-8601 `Z` timestamps — the shape to hand a member exercising portability"
[Source: EXPERIENCE.md#5-member-records-and-demand-insights].

**Retired options in an export — same rule as the member record and insights.** "Retired options
export their historical label" [Source: EXPERIENCE.md#5-member-records-and-demand-insights],
consistent with ADR-009's group-by-key/display-label contract applied everywhere else in this epic
[Source: architecture.md#adr-009-answers-store-option-keys-and-a-label-snapshot].

**No personal data in the URL — why this endpoint is a `POST`, not the literal `GET` named in
architecture.md.** Architecture's API list names `GET /api/admin/members/export`
[Source: architecture.md#6-api-specifications]. This story deliberately implements it as **`POST
/api/admin/members/export`** with the member id set (or single id) in the request body, not the
query string, because a filtered export otherwise has to encode the active search term and filters
somewhere the server can read them — and "no personal data in a URL" is the standing boundary for
every screen in this epic
[Source: EXPERIENCE.md#5-member-records-and-demand-insights]. **[Inference] — a deliberate
deviation from the literal HTTP verb in `architecture.md`, on privacy grounds; flag to the
orchestrator/architecture owner for confirmation rather than treating this as pre-approved.** The
path stays `/api/admin/members/export`, matching the file-based route.

**Confirmation copy — exact.** "Downloaded 216 member records." / "Downloaded 1 member record."
Never a name [Source: EXPERIENCE.md#5-member-records-and-demand-insights], rendered as the §2.10
inline success banner directly beneath the export button, never a toast (adjudication A6)
[Source: DESIGN.md#2-component-specifications].

**Dialog contract.** Built on the shared `Dialog` primitive (adjudication A14; `ConfirmModal`
rebuilt on it by 5.1): `role="dialog"` + `aria-modal="true"` + `aria-labelledby` the heading +
`aria-describedby` the warning paragraph so it is spoken on open; focus to heading; trapped;
Escape closes; background `inert`
[Source: DESIGN.md#2-component-specifications]. The trigger is `disabled` at zero matching rows, so
an empty export cannot be requested — there is no "empty" state to design for
[Source: EXPERIENCE.md#5-member-records-and-demand-insights]. Format is a real `<fieldset>`/
`<legend>` with two labelled radios; the JSON option's help text is tied to its radio with
`aria-describedby` [Source: EXPERIENCE.md#5-member-records-and-demand-insights].

**Auth block — copy verbatim**, identical to the rest of this epic's endpoints:
```js
const token = req.headers.authorization?.replace('Bearer ', '')
if (!token) return res.status(401).json({ error: 'Not authenticated' })
const { data: { user: caller }, error } = await supabase.auth.getUser(token)
if (error || !caller) return res.status(401).json({ error: 'Invalid or expired session' })
```
[Source: architecture.md#adr-003-authn-via-supabase-auth-authz-is-binary-with-attribution-instead-of-tiers].

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. NEVER run tests or quote coverage here. -->

- **Approach:** unit tests for the CSV/JSON serialisers and the filename builder in
  `adminExport.js`, isolated from the DOM and from network; integration tests for the export
  endpoint covering both branches and auth rejection; component tests for `ExportDialog.jsx`
  covering both variants and the loading/success/error states.
- **Key scenarios:** filtered export at 1 row, at 216 rows, at the `MAX_ROWS` boundary; a filtered
  export where the filter matches zero rows (trigger disabled, unreachable); single-member export in
  both formats; a member with a retired option in their answers; a member with a withdrawn consent
  alongside an original grant (both appear in the JSON consent array); CSV cell escaping for a
  free-text answer containing a comma, a quote, and a line break.
- **Per-AC verification:** AC #1 → parse the generated CSV, assert row count matches the filtered
  set, column headers match current published labels, and line 1 is the comment row; AC #2 → parse
  the generated JSON, assert every answer and the full consent array are present; AC #3 → assert
  the filename string against a personal-data denylist (no email, name, or postcode substring) for
  both variants; AC #4 → assert the rendered confirmation string matches the count-only template
  exactly; AC #5 → call the endpoint with no/garbage/expired token, assert `401` and no file bytes
  in the body; AC #6 → inspect the actual request made by the dialog and assert no search term or
  filter value appears in the URL, only in the POST body as an id list.
- **Fixtures / mocks:** a seeded filtered list of member ids matching 7.1's list fixture; a single
  member fixture matching 7.2's detail fixture, including a retired option and a withdrawn consent;
  a fake bearer token for the 401 case; `URL.createObjectURL`/`Blob` mocked so the download trigger
  can be asserted without a real file write.
- **Edge cases to cover:** a member whose business name or free-text answer contains characters that
  must be CSV-escaped; an export requested while a previous export for the same trigger is still
  building (both buttons and radios must be inert, not just visually dimmed).
