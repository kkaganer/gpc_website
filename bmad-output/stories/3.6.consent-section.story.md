# 3.6: Privacy and consent — three separate, un-pre-ticked permissions

**Story ID:** 3.6
**Epic:** 3 — The public form
**Slug:** consent-section
**Status:** ready-for-dev

## Story

As a **member about to submit the form**,
I want **three separate, clearly-explained permissions — none ticked for me — instead of one
undifferentiated tick**,
so that **I give exactly the consent I mean to give, and GPC can prove what I agreed to if I ever
ask**.

## Acceptance Criteria

<!-- LOCKED. External dev tools must not edit Acceptance Criteria. -->

1. Given the consent section renders, when it loads, then it shows two or three checkboxes — Hold
   my data (always, required), Publish my listing (only when the directory opt-in is "Yes",
   required in that case), Newsletter (always, optional) — and **none is pre-ticked, ever, for any
   reason, including on a resubmission**.
2. Given each checkbox, when a screen reader announces it, then its accessible name is the **full,
   exact consent sentence** defined in this story's consent artifact register — never a
   truncated summary such as "I agree to the terms".
3. Given the member opted out of the directory, when the consent section renders, then the
   Publish-my-listing consent is **absent from the DOM entirely** — not disabled, not greyed out.
4. Given the member submits with Hold-my-data unticked, then submission is blocked with an
   explanatory error on that checkbox; given she opted in and submits with Publish-my-listing
   unticked, then submission is blocked with an error offering two named ways out: ticking it, or
   following an in-page link back to the directory opt-in question.
5. Given the member does not tick the newsletter checkbox, then nothing in this story's output
   causes a newsletter subscription to be created by any path.
6. Every consent's rendered text links to `/privacy`, opening in a new tab with
   `rel="noopener"` and a visually-hidden "(opens in a new tab)".

- **FR-004 is this story's contract:** three separate consents — (a) hold submitted personal
  data, required; (b) publish nominated fields, required only if opted into the directory; (c)
  newsletter, always optional, never pre-ticked; the stored record must include the exact consent
  text shown, a version identifier, the UTC timestamp and the capture method (assigned
  server-side — this story sends only booleans, per ADR-004; it does not author the timestamp or
  version); if (c) is not ticked, no newsletter subscription is created by any path; the copy
  links to the site's own `/privacy` page; consent records are append-only.
  [Source: prd.md#FR-004]
- **⛔ BLOCKING — do not invent a retention period.** Consent A's text below contains the literal
  placeholder `«RETENTION_PERIOD»`. This is **addendum Q8**, unresolved, and blocks the first live
  submission — every day the form runs with the placeholder produces consent records citing text
  GPC cannot evidence. This story renders the placeholder as specified; it does **not** guess a
  number or a phrasing. The final string (drafted both ways below) is the controller's decision,
  not this story's, and swapping it in later is a version bump to `hold_data@1.0.0`'s deployed

### The consent artifact register — THE DELIVERABLE, stored verbatim (do not paraphrase)

**Consent A — `hold_data@1.0.0`** · always required; submission is rejected server-side without
it and no partial member record is created.

> Yes — Greenwich Parents & Carers CIC can keep the information I've given here, and use it to
> run the Mums in Business & Work community, contact me about it, and plan events. GPC won't sell
> it, and won't share it with anyone outside GPC without telling me first. I can ask to see it,
> change it or have it deleted at any time, and GPC will do that within 20 working days. GPC will
> keep it for **«RETENTION_PERIOD — addendum Q8»** unless I ask sooner. I've read the
> [privacy notice](/privacy).

Two drafted replacements exist for when Q8 resolves (this story renders the placeholder form,
not either replacement): **(a)** fixed period — "GPC will keep it for **___ years** unless I ask
sooner." **(b)** no fixed period — "GPC will keep it for **as long as I'm part of the
community**, and delete it within 20 working days of my asking." Either way the string still
ships as `hold_data@1.0.0`; **the placeholder version is never used for a live submission.**

*Helper (not stored, freely editable):* "You can't join without this one — it's how we're allowed
to hold your details at all."
[Source: EXPERIENCE.md#2-the-directory-opt-in-and-consent — "Consent A"]

**Consent B — `publish_listing@1.0.0`** · required only when the member opted into the directory;
absent from the DOM otherwise.

> Yes — GPC can publish my business name, category, description, website, Instagram and public
> enquiry contact on the public directory page of the GPC website, where anyone can see them and
> search engines can index them. My name, sign-up email, postcode and survey answers stay
> private. I can ask GPC to take my listing down at any time and they'll remove it within 20
> working days. I've read the [privacy notice](/privacy).

*Helper (not stored):* "We only need this because you asked to be listed.
[Change your directory answer](#directory) if you'd rather not."

Every clause is working, not decorative: it **names all six published fields**, because a consent
that doesn't name what's published isn't specific consent; "…and search engines can index them"
is the sentence members most underestimate, and it stays; the private-fields guarantee is inside
the consent text itself, not only in the disclosure panel, so it becomes part of the evidenced
record. [Source: EXPERIENCE.md#2-the-directory-opt-in-and-consent — "Consent B"]

**Consent C — `newsletter@1.0.0`** · never required, never pre-ticked; declining has no other
effect.

> Yes please — send me the GPC weekly newsletter with local events and news. GPC will use my
> email address only for the newsletter. I know I can unsubscribe from any email, at any time.
> I've read the [privacy notice](/privacy).

*Helper (not stored):* "Optional. Saying no here changes nothing else."

This replaces the source form's "Weekly Newletter" typo. Per addendum Q5, if she does not tick
this, the existing Brevo sync's opt-out semantics must not be overridden by this new write path —
**not this story's code to write** (that is Epic 4's submission pipeline), but this story's UI
must never suggest ticking is required. [Source: EXPERIENCE.md#2-the-directory-opt-in-and-consent
— "Consent C"]

- **Storage contract — what this component hands the (future, Epic 4) submit call per ticked
  consent:** `consent_key` (`hold_data`|`publish_listing`|`newsletter`), `consent_version` (e.g.
  `publish_listing@1.0.0`), `consent_text` (the exact rendered string, **plain text with link URLs
  expanded inline** — "…I've read the privacy notice
  (https://greenwichparentsandcarers.co.uk/privacy)."), `granted` (`true`; a later withdrawal is a
  separate append-only row the client never authors). **`granted_at` and `capture_method` are
  assigned server-side** — this story's payload contribution is booleans plus the pinned version
  string, never a client-authored timestamp (ADR-004, ADR-010). **Deliberately not stored: IP
  address, user agent, geolocation** — collecting one against a consent record is a direct
  NFR-006 violation. [Source: EXPERIENCE.md#2-the-directory-opt-in-and-consent — "Storage
  contract"] [Source: architecture.md#adr-004-one-trusted-server-write-path-the-browser-never-
  writes-member-data] [Source: architecture.md#adr-010-consent-records-are-append-only-and-
  version-bearing-enforced-by-trigger]
- **Where the strings live:** `src/lib/join/consentText.js` — a versioned code module, **not**
  the admin-editable form configuration (`form_question_config`/`form_options`, owned by 2.1/2.2).
  FR-008 scopes admin editing to labels, help text, options and required flags; consent strings
  are not questions, and an admin silently rewording one would produce a cohort of records citing
  `1.0.0` whose text differs from `1.0.0`, destroying the evidence NFR-004 exists to create. A
  future admin panel may *display* the current text and version read-only — that is Epic 2's
  concern, not this story's. [Source: EXPERIENCE.md#2-the-directory-opt-in-and-consent — "Where
  the strings live"]
- **Version bump triggers:** any change to the rendered `consent_text`, including punctuation and
  including a link-destination change, is a new version. **Not** a bump: helper text, badge
  labels, card styling, or display order. [Source: EXPERIENCE.md#2-the-directory-opt-in-and-
  consent — "Version bump triggers"]
- **Cards, not a flat list, stacked at every breakpoint — never a 3-across row.** A three-across
  layout invites treating the consents as one decision, which is the exact defect being fixed.
  Each consent is a `Card` (existing `src/components/ui/Card.jsx`, no internal padding — wrap in
  `p-6`) with a `Checkbox` (3.1b) inside; **the card as a whole is not clickable** — only the
  checkbox and its label text are, so a thumb scrolling the card cannot accidentally consent.
  [Source: EXPERIENCE.md#2-the-directory-opt-in-and-consent — Screen D-3 wireframe and
  "Differences only"]
- **Consent error strings, verbatim:** A unticked → *"We can't accept the form without this. It's
  the permission that lets us hold your details at all."* B unticked while opted in → *"You asked
  to be listed in the directory, so we need your permission to publish it. Tick this box, or
  change your directory answer."* — the last five words are an in-page link to the D-1 radio
  group (3.5). C never errors. [Source: EXPERIENCE.md#2-the-directory-opt-in-and-consent —
  "Consent error strings"]
- **`/privacy` link placement and behaviour:** the link sits **inside** each checkbox's label
  (making it part of the accessible name — a known screen-reader edge case; verify in the manual
  NFR-008 pass, and if a tested reader fails to expose it, move the link to the line immediately
  below rather than removing it) and is **duplicated** in a plain, non-nested controller footnote
  below the whole group: *"Who holds your data: Greenwich Parents & Carers CIC (company
  16387545). Read the full privacy notice."* Opens in a **new tab**, `rel="noopener"`, with a
  visually-hidden "(opens in a new tab)" — this is the one place on `/join` where that's correct,
  because there is no saved-progress feature and a member who navigates away mid-form loses
  everything typed; the new tab *is* the mitigation.
  [Source: EXPERIENCE.md#2-the-directory-opt-in-and-consent — Screen D-3 wireframe, accessibility
  notes]
- **No dark patterns, explicitly:** no "select all", no pre-fill from a previous session, no
  consent implied by proceeding, no visual emphasis making the optional one look required — the
  optional one (C) is last. [Source: EXPERIENCE.md#2-the-directory-opt-in-and-consent —
  accessibility notes]
- **Consent B's appearance is announced through the shared live region** (`useLiveRegion`, 3.1a):
  *"One more permission added: publishing your directory listing."* No focus move — it is
  inserted after Consent A in DOM order and reached naturally.
  [Source: EXPERIENCE.md#2-the-directory-opt-in-and-consent — accessibility notes]
- **Canonical domain and contact, verified facts that settle disputes in the drafts:** the
  canonical domain is `greenwichparentsandcarers.co.uk` (not `greenwichparents.co.uk`, which is
  wrong and must not appear); the contact address is `gpc.communitynews@gmail.com`.
  [Source: ux-drafts/ADJUDICATIONS.md#verified-facts-that-settle-three-disputes]

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify per AC, test types, fixtures, edge cases. -->

- **Approach:** component tests asserting the exact rendered consent strings against the register
  above (character-for-character, since this is a legal artifact), conditional-mount tests for
  Consent B, and a manual screen-reader pass confirming each checkbox's accessible name is the
  full sentence and the in-label `/privacy` link is exposed.
- **Key scenarios:** default render has zero checkboxes ticked; opting into the directory then
  back out removes and re-adds Consent B without ever pre-ticking it; submitting with A unticked
  blocks with the correct error; submitting opted-in with B unticked blocks with the two-route
  error and the in-page link correctly scrolls/focuses the D-1 fieldset; C is never required
  under any combination of the other answers.
- **Per-AC verification:** AC #1 → assert all rendered checkboxes have `checked === false` on
  mount in every combination of prior answers, including a simulated "resubmission" state if one
  is passed in; AC #2 → assert each checkbox's computed accessible name (via label association)
  equals the register string verbatim, including the trailing "I've read the privacy notice."
  clause; AC #3 → toggle the directory opt-in off and assert Consent B's DOM node is entirely
  absent, not `hidden`/`disabled`; AC #4 → submit with A unticked and assert the specific error
  string and that focus/summary linkage exists for 3.7 to consume; opt in, leave B unticked,
  submit, assert both the tick-it and the in-page-link recovery paths work; AC #5 → assert no
  code path in this story's components calls any newsletter-subscription side effect when C is
  unticked (this story has none — verify by absence, not by a stubbed call); AC #6 → assert every
  rendered `/privacy` anchor has `target="_blank" rel="noopener"` and a visually-hidden
  "(opens in a new tab)" text node.
- **Fixtures / mocks:** none beyond the directory opt-in state already produced by 3.5's
  `useJoinForm` slice — no network call in this story.
- **Edge cases to cover:** rapid opt-in/opt-out toggling before Consent B's mount/unmount settles
  (must never leave a ticked-but-hidden B state behind); a member who ticks B, opts out, opts
  back in — B must render **unticked** again, per "none pre-ticked, at any time, for any reason".
