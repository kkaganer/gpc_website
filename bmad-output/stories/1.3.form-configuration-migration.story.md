# 1.3: Form configuration migration — overlay, options, versioned publish, open/close

**Story ID:** 1.3
**Epic:** 1 — Data foundation
**Slug:** form-configuration-migration
**Status:** ready-for-dev

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As **an admin**,
I want **the database tables that will hold my edits to question wording, options and the form's open/closed state**,
so that **Epic 2's admin screens have somewhere to write drafts and publish versions, without the field set or branching structure ever living in the database**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. Given migration `030_form_configuration.sql` is applied, when the schema is inspected, then `form_config_versions`, `form_question_config`, `form_options`, and `form_settings` all exist with the columns specified in Dev Notes — `uuid` primary keys, `timestamptz` timestamps, `jsonb` for the version snapshot.
2. Given an unauthenticated client queries any of the four tables directly with the anon key, when the query executes, then zero rows are returned — all four are private; the public form reads configuration only through `GET /api/join/config` (Epic 2), never a direct table read.
3. Given `form_options` already has a row for `(question_key, option_key) = ('event_types', 'networking_breakfasts')`, when a second row with the same pair is inserted, then it is rejected by the unique constraint.
4. Given one `form_config_versions` row has `is_current = true`, when a second row is also set `is_current = true`, then the insert/update is rejected by the partial unique index — at most one version may be current at a time.
5. Given migration `030` completes, when `form_settings` is queried, then exactly one row exists with `is_open = true` by default, ready for the admin open/close toggle to update in place rather than insert a second row.
6. Given migration `030_form_configuration.sql` is applied a second time, when `supabase db push` executes, then it completes with no error.

### The three-layer model this schema supports

**Layer 1 (not this migration):** `src/lib/join/questions.js`, the code registry — the structural truth for keys, types, branch membership and validation. Not editable at runtime, and not touched by this story [Source: architecture.md#adr-008-form-configuration--code-defined-registry-database-overlay-and-versioned-publish].

**Layer 2 (this migration):** the database overlay — `form_question_config` (`label`, `help_text`, `is_required` per `question_key`) and `form_options` (`label`, `sort_order`, `retired_at` per `(question_key, option_key)`). A question key present in the code registry but absent from the overlay renders its code default, so adding a question in code never requires a data migration — which is why the overlay columns here are **nullable with no default**, not `not null default ''`: null is the signal "no override, use the code default" [Source: architecture.md#adr-008-form-configuration--code-defined-registry-database-overlay-and-versioned-publish].

**Layer 3 (this migration):** `form_config_versions` — a `jsonb` snapshot of the whole *resolved* config (registry + overlay merged), taken at publish time. Editing writes to the overlay tables as draft; publishing snapshots into a new version row and marks it current. The public form reads the current published version; admin preview resolves the draft directly from the overlay tables [Source: architecture.md#adr-008-form-configuration--code-defined-registry-database-overlay-and-versioned-publish]. This is also the version identifier FR-004's consent record cites — publishing the form and publishing a consent-text version are the same act [Source: architecture.md#adr-008-form-configuration--code-defined-registry-database-overlay-and-versioned-publish].

**Exception — `form_settings.is_open` applies immediately, bypassing draft/publish.** Closing the form is an emergency control; making it wait behind a publish step would be a defect [Source: architecture.md#adr-008-form-configuration--code-defined-registry-database-overlay-and-versioned-publish]. This directly satisfies FR-009: the form can be taken offline without removing the page or deploying, and the current state must be visible at a glance in the admin panel [Source: prd.md#FR-009].

**Categories are explicitly not here.** `directory_categories` (created in **1.1**) is owned by the directory section and takes effect immediately — one editor, one home [Source: architecture.md#adr-008-form-configuration--code-defined-registry-database-overlay-and-versioned-publish]. This migration must not create a categories table.

### `form_question_config`

```sql
create table if not exists form_question_config (
  id           uuid primary key default gen_random_uuid(),
  question_key text not null unique,
  label        text,
  help_text    text,
  is_required  boolean,
  created_at   timestamptz not null default now(),
  updated_at   timestamptz not null default now()
);

comment on column form_question_config.label is
  'Null means "no override — render the code registry default from src/lib/join/questions.js".';
comment on column form_question_config.is_required is
  'Null means "use the code registry default required flag", not "not required".';

create trigger form_question_config_set_updated_at
  before update on form_question_config
  for each row execute function update_updated_at();

alter table form_question_config enable row level security;
-- No anon policy, no authenticated policy: reads/writes go through
-- GET|PUT /api/admin/form-config and GET /api/join/config (both server routes).
```
[Source: architecture.md#adr-008-form-configuration--code-defined-registry-database-overlay-and-versioned-publish] for the shape; the `comment on column` documenting null-means-fallback follows the codebase's convention that semantics a client must obey are written into a column comment [Source: inputs/codebase-constraints-brief.md#2-data-layer-conventions-a-new-migration-must-follow-these-exactly].

### `form_options`

```sql
create table if not exists form_options (
  id           uuid primary key default gen_random_uuid(),
  question_key text not null,
  option_key   text not null,
  label        text not null,
  sort_order   integer not null default 0,
  retired_at   timestamptz,
  created_at   timestamptz not null default now(),
  updated_at   timestamptz not null default now(),
  unique (question_key, option_key)
);

create trigger form_options_set_updated_at
  before update on form_options
  for each row execute function update_updated_at();

alter table form_options enable row level security;
-- No anon policy, no authenticated policy — same as form_question_config.
```
Retiring an option never rewrites stored answers — historical submissions keep the `{key, label}` snapshot they were given at submission time (ADR-009), so retiring here only hides the option from future renders, via `retired_at` [Source: prd.md#FR-008] and [Source: architecture.md#adr-009-answers-store-option-keys-and-a-label-snapshot].

### `form_config_versions`

```sql
create table if not exists form_config_versions (
  id           uuid primary key default gen_random_uuid(),
  version      text not null unique,
  config       jsonb not null,
  is_current   boolean not null default false,
  published_at timestamptz not null default now(),
  published_by uuid,
  created_at   timestamptz not null default now()
);

create unique index if not exists form_config_versions_current_uidx
  on form_config_versions (is_current)
  where is_current;

alter table form_config_versions enable row level security;
-- No anon policy, no authenticated policy.
```
Shape (`version`, `config jsonb`, `published_at`, `published_by`) is from the Data Model [Source: architecture.md#adr-008-form-configuration--code-defined-registry-database-overlay-and-versioned-publish]. The mechanism for tracking which version is current — `is_current boolean` plus a partial unique index — is not spelled out in the source at the SQL level; this is the standard Postgres "singleton flag" pattern and is the simplest correct implementation of "marks it current" [Inference]. `published_by` is left as a bare `uuid` (the caller's `auth.uid()`), matching how `actioned_by` is described elsewhere as attribution without a foreign key to `auth.users` [Source: architecture.md#adr-003-authn-via-supabase-auth-authz-is-binary-with-attribution-instead-of-tiers].

### `form_settings` — single-row table

```sql
create table if not exists form_settings (
  id             uuid primary key default gen_random_uuid(),
  is_open        boolean not null default true,
  closed_message text,
  intro_text     text,
  updated_at     timestamptz not null default now()
);

create trigger form_settings_set_updated_at
  before update on form_settings
  for each row execute function update_updated_at();

insert into form_settings (is_open, closed_message, intro_text)
select true, null, null
where not exists (select 1 from form_settings);

alter table form_settings enable row level security;
-- No anon policy, no authenticated policy.
```
`form_settings` holds `is_open`, `closed_message`, `intro_text` [Source: architecture.md#entity-form_config_versions--form_question_config--form_options--form_settings]. There is no established singleton-table pattern anywhere in the existing 27 migrations (no boolean-PK trick, no CHECK-based row cap), so this story keeps the standard `uuid` PK convention and enforces "exactly one row" by seeding it once here and by convention thereafter (the admin API always does `update form_settings set … where id = (select id from form_settings limit 1)`, never an insert) [Inference — flagged because the source does not specify a DB-level single-row guarantee; Epic 2's `admin-form-settings` story (2.3) should read this row by `limit 1`, never assume a fixed id]. `closed_message` and `intro_text` are the admin-authored copy shown per FR-009 ("an admin-authored closed message instead of the fields") [Source: prd.md#FR-009] and FR-001's intro text [Source: prd.md#FR-001].

### No CHECK vocabularies in this migration, deliberately

Unlike `directory_listings.status` or `member_consents.purpose`/`method`, none of these four tables has a closed-vocabulary column — `is_required`, `is_open`, `is_current` are booleans, and `question_key`/`option_key` are open-ended, code-registry-defined identifiers, not a fixed list this migration can enumerate. `-- CHECK VOCAB: deliberately none — no closed-vocabulary column exists in this schema.` belongs in the header comment as the "deliberately not done" block [Source: inputs/codebase-constraints-brief.md#2-data-layer-conventions-a-new-migration-must-follow-these-exactly].

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. NEVER run tests or quote coverage here. -->

- **Approach:** manual SQL-editor verification against the shared Supabase project — no automated test runner exists in this repo [Inference]. This migration has no FK dependency on `members`/`028`, so it can be applied and verified independently of **1.1**/**1.2**, though numbering means `028`/`029` should already be applied first in practice.
- **Key scenarios:** (a) all four tables exist with the specified shape; (b) anon cannot read any of the four tables; (c) duplicate `(question_key, option_key)` is rejected; (d) two `is_current = true` rows is rejected; (e) exactly one `form_settings` row exists after migration; (f) re-running is a no-op.
- **Per-AC verification:** AC #1 → `\d+` each table against Dev Notes. AC #2 → `select * from form_question_config` (and the other three) with the anon key returns nothing. AC #3 → insert `('event_types','networking_breakfasts','Networking breakfasts',1,null)` twice into `form_options`; the second must fail on the unique constraint. AC #4 → insert two `form_config_versions` rows both with `is_current = true`; the second must fail on the partial unique index. AC #5 → `select count(*) from form_settings` immediately after migration equals 1, with `is_open = true`. AC #6 → re-apply via `supabase db push`.
- **Fixtures / mocks:** a couple of hand-inserted `form_question_config`/`form_options` rows via the SQL editor with `service_role`, removed after verification.
- **Edge cases to cover:** inserting a `form_options` row with `retired_at` already set (a pre-retired option) must succeed without error; setting `is_current = false` on the previously-current row before inserting a new current one must not violate the partial index (the transition is two statements, not one — worth noting for whoever writes the publish endpoint in Epic 2); an admin overlay row with all three overlay columns `null` must still resolve correctly to "use every code default" at the application layer (not testable at the DB layer alone, but the nullability contract must hold).
