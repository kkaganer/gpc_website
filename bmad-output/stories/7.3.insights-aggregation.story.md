# 7.3: Insights aggregation

**Story ID:** 7.3
**Epic:** 7 — Member records and insights
**Slug:** insights-aggregation
**Status:** ready-for-dev

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As **Ash, a GPC admin**,
I want **a server-side function that summarises every member's day/time, frequency, event-type and
branch-demand answers into counts and shares, optionally filtered by group and event-type
interest**,
so that **event planning is evidence-led without a single raw member row ever leaving the
database**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. Given `GET /api/admin/insights` is called with a valid bearer token and no filters, then the
   response contains: counts for all 21 day/time slots, event frequency, event types, and the
   branch-specific "what business members are looking for" / "what support career members want"
   blocks — every count expressed as both an absolute number and a share of that block's response
   base — and the response body contains no raw member row, no `member_id`, and no free-text
   answer.
2. Given a `group` query value (`business_mums` | `career_mums` | `both`) is passed, then every
   block reflects only members whose `group_choice` matches, and the response states both the
   matched count and the total unfiltered member count.
3. Given an `eventType` (interested-in) cross-filter key is passed, then every block reflects only
   members whose `event_types` answer includes that key.
4. Given a choice option was retired after being answered, when it appears in any block, then it is
   grouped by its stable `key` and displayed with the label it was actually given under, never
   dropped and never merged into a differently-labelled bucket.
5. Given a question's published label changed after some members had already answered it, when the
   block for that question is returned, then the response distinguishes the current label's count
   from any earlier-wording count(s) for the same `key`, rather than silently merging them under one
   label.
6. Given `GET /api/admin/insights` is called without a valid bearer token, or with an invalid or
   expired one, then the response is `401 { error }` with no aggregate data.

  - [ ] Aggregate over each member's **most recent** `member_submissions.answers`, joined to

        `form_options`/`form_question_config` overlay where it exists, otherwise fall back to the
        stored `label` snapshot (AC: #1, #4, #5)

  - [ ] Compute the day/time grid as 21 `(day, slot)` cells from the events section's answer,

  - [ ] Compute frequency and event-type counts (single- and multi-select respectively) with
        absolute count and share (AC: #1)
  - [ ] Compute the two branch-specific blocks, scoped to members whose `group_choice` puts them in

  - [ ] Apply the `p_event_type_key` cross-filter before computing every block, not just the grid
        (AC: #3)
  - [ ] State the response base (matched count, total count) once at the top level, not per block
        (AC: #1, #2)

## Dev Notes

<!-- LOCKED. Concrete guidance compiled from the planning docs WITH SOURCE CITATIONS.

     [Source: ux-design.md#anchor]. Label your own inferences [Inference]. -->

**This is server-side aggregation by design — not a client-side reduce.** "Insights are computed
by a SQL function over `member_submissions.answers`; raw member rows never reach the browser for
aggregation" [Source: architecture.md#component-member-records--insights-admin]. ADR-007 is
explicit: "Insights aggregate server-side... sending 1,000 member records to a browser to draw a
bar chart would move private data to the client for no reason (NFR-006)"
[Source: architecture.md#adr-007-client-state--hand-rolled-hooks-fetch-once-filter-client-side].
This is the single hardest LOCKED constraint on this story: **no code path in this feature may
select raw `member_submissions` or `members` rows into the Vercel function's response body for
counting purposes** — only the function's pre-aggregated `jsonb` result leaves the database layer.

**FR-014 acceptance criteria this story delivers:** day/time distribution across all members; event
type, frequency, and branch-split "looking for"/"support wanted" counts; a group filter that
recalculates the summary; every count as both an absolute number and a share of respondents; the
view states the response base it was computed from [Source: prd.md#FR-014]. The "interested in"
cross-filter (AC #3) is **not named by FR-014 itself** — it is flagged in `EXPERIENCE.md` as
"exceeds FR-014... what turns [insights] from a chart page into a decision. Needs PM confirmation;
if cut, the answer card must say plainly that it is the best slot for *everyone*, not for the event
being planned" [Source: EXPERIENCE.md#5-member-records-and-demand-insights]. Build it — 7.4 (the
UI) depends on this filter existing — but flag to the orchestrator if product has not confirmed it.

**Group by key, display label — the ADR-009 contract, applied to aggregation specifically.** "`key`
is the stable identifier — **insights and aggregation group by `key`** (FR-014), so a rename does
not fracture a chart... Where they disagree (an option renamed since submission), the admin UI
shows the current label and notes the change; it never silently merges"
[Source: architecture.md#adr-009-answers-store-option-keys-and-a-label-snapshot]. The retired-option
and wording-change behaviours (AC #4, #5) are specified narratively in the UX journey: "An option
was retired (FR-008) — it still appears with its historical label, a muted `retired` pill... Counts
unchanged" and "A question's *wording* changed mid-collection — Show the **current published
label**, aggregate, and print a note under the block: 'The wording of this question changed on 12
Jun 2026. 74 of these 132 answers were given to the earlier wording — [show it].' Never silently
merge two wordings under one label"
[Source: EXPERIENCE.md#5-member-records-and-demand-insights]. **[Inference]** the exact SQL
mechanism for detecting a wording change (comparing each stored `label` value against the current
overlay label per `key`, per question) is not specified in any source — this is a judgment call for
the implementer, not a cited fact.

**Labels come from the published form configuration, never a hard-coded list.** "Insights reads
every question label, option label and the three slot names from the currently *published* form
config... so an FR-008 rename propagates here without a code change and a retired option keeps the
historical label it was answered under. There is no `SLOT_LABELS` constant anywhere in this
feature" [Source: EXPERIENCE.md#5-member-records-and-demand-insights]. This means the function must
read `form_question_config`/`form_options` (or the current `form_config_versions` snapshot) for
current labels — **a functional dependency on Epic 1's story 1.3 (`form-configuration-migration`)**
beyond the epic-level dependency list, because those tables do not exist without it.

**Migration numbering — a cross-epic coordination point, not a decision this story can make alone.**
"Migrations 028–031 are reserved" for Epic 1's four stories, "one file each — nobody else may edit
a migration" [Source: context/sharding-context.md#owned-filemodule-scope--the-collision-map]. This
story's `get_member_insights()` function needs a **new** migration numbered after 031, following
every ADR-002 convention: `snake_case`, idempotent, header comment with `-- WHY.`, and the lockdown
grant pair in the same file [Source: architecture.md#adr-002-persistence-conventions]. Epics 4, 5
and 8 each also need new functions (`submit_membership()`, the moderation transition functions,
`erase_member()`) not yet assigned numbers in any source document read for this story. **Do not
hard-code a specific number** (e.g. `032`) without confirming with the orchestrator that no
sibling epic has already claimed it — flag this explicitly during cross-epic sequencing.

**Function grant.** Every function gets the lockdown pair in the same migration:
```sql
revoke execute on function get_member_insights(text, text) from public, anon;
grant  execute on function get_member_insights(text, text) to authenticated;
```
[Source: architecture.md#adr-002-persistence-conventions], matching the pattern that exists because
`010_lock_down_publish_rpcs.sql` had to fix a missed grant once
[Source: inputs/codebase-constraints-brief.md#2-data-layer-conventions-a-new-migration-must-follow-these-exactly].

**Auth block for the API route — copy verbatim**, identical to 7.1/7.2:
```js
const token = req.headers.authorization?.replace('Bearer ', '')
if (!token) return res.status(401).json({ error: 'Not authenticated' })
const { data: { user: caller }, error } = await supabase.auth.getUser(token)
if (error || !caller) return res.status(401).json({ error: 'Invalid or expired session' })
```
[Source: architecture.md#adr-003-authn-via-supabase-auth-authz-is-binary-with-attribution-instead-of-tiers].

**No UI in this story.** This story delivers the function and the endpoint only; the readable 7×3
grid, ranked bars, response-base banner and copy-summary button belong to 7.4, which consumes this
endpoint's `jsonb` shape as its data contract.

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. NEVER run tests or quote coverage here. -->

- **Approach:** SQL-level tests against a seeded local Supabase instance calling
  `select get_member_insights(...)` directly, verifying the returned `jsonb` shape and values;
  integration tests against `api/admin/insights.js` verifying auth rejection and pass-through of
  filter params.
- **Key scenarios:** no filters (whole-membership baseline); `group` filter alone; `eventType`
  filter alone; both combined; a retired option present in historical answers; a question whose
  overlay label has changed since some members answered it; zero members (empty aggregate, not an
  error); a filtered group with zero matches.
- **Per-AC verification:** AC #1 → assert every named block is present with absolute+share pairs
  and assert the response contains no `member_id`/`email`/free-text key at any depth; AC #2 →
  compare matched vs. total counts against a hand-computed value from the seed data for each group
  value; AC #3 → assert every block narrows consistently when the event-type filter is applied, not
  just the grid; AC #4 → seed an answer under a retired option key, assert it still counts and
  carries its historical label; AC #5 → seed the same question answered under two different labels
  over time, assert both counts appear distinctly, never summed silently under one label; AC #6 →
  call with no/garbage/expired token, assert `401` and no `jsonb` body.
- **Fixtures / mocks:** a seeded set of `members` + `member_submissions` spanning all three group
  values, all 21 day/time combinations, every frequency and event-type option including one
  retired option, and at least one question with two historically-distinct labels for the same
  `question_key`; the `form_question_config`/`form_options` overlay rows needed to resolve current
  labels.
- **Edge cases to cover:** a member who submitted twice (only the latest submission's answers
  count, per the "resubmission is an additional row" data model); a multi-select question where
  shares legitimately exceed 100%; a single-select question where shares sum to exactly 100% modulo
  rounding.
