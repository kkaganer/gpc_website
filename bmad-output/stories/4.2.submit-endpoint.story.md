# 4.2: Submit endpoint

**Story ID:** 4.2
**Epic:** 4 — Submission pipeline
**Slug:** submit-endpoint
**Status:** ready-for-dev

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As **the data controller**,
I want **`POST /api/join/submit` to build every database field from an explicit allowlist and assign all consent metadata itself**,
so that **a client holding only the public browser key can never write an arbitrary field, forge a consent record, or set its own moderation status**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. Given a POST to `/api/join/submit` with any payload, when the handler builds arguments for `submit_membership()`, then every value is pulled field-by-field from an explicit allowlist keyed to `src/lib/join/questions.js` and the identity fields — `req.body` is never spread into the call — so a field the server did not ask for (`status`, `id`, `published_at`, `actioned_by`, `consent_version`, etc.) is silently ignored rather than rejected.
2. Given the same request, when consent metadata is assembled, then `consent_text` and `consent_version` for each presented purpose are read from the currently **published** `form_config_versions` row, never from the request body — the client sends only the three boolean consent choices.
3. Given a required identity or answer field is missing, or a free-text answer exceeds its registry-defined `maxLength`, when the handler validates, then it returns `400 { error }` and `submit_membership()` is never called — no row of any kind is written.
4. Given the submission succeeds, when the response is returned, then it is exactly `200 { ok: true }` — no member id, listing id, or echoed record — the same shape the endpoint must also return for a duplicate email and a honeypot catch once 4.3/4.4 land.
5. Given the handler throws for any reason (a Postgres error, a JSON-parse failure, an unexpected exception), when it responds, then the whole handler body is wrapped in try/catch so it always returns `{ error: string }` with a non-2xx status, never an HTML error page.
6. Given `form_settings.is_open = false`, when a request is posted directly to the endpoint (bypassing the UI's closed-state check), then it is rejected with `409 { error }` and no row is written.
7. Given the handler logs anything about a request (success or failure), when the logs are inspected, then no personal data — name, email, phone, postcode, free-text answers — appears anywhere in a log line; only the resulting record id (or nothing, on a pre-write failure) is logged.

<!-- Keep to ~3-7. More than ~7 means the story is too big — split it. -->

## Tasks / Subtasks

- [ ] Create `api/join/submit.js`: export a default async handler, reject non-`POST` methods, and wrap the entire body in try/catch from the first line (AC: #5)
- [ ] Read `form_settings.is_open` via the service-role client before any other processing; return `409 { error: 'The form is currently closed' }` if closed (AC: #6)
- [ ] Build the allowlist mapper: iterate `src/lib/join/questions.js`'s registry, pull each question's value only from `req.body.answers[key]`, validate its `type`/`maxLength` from the registry, and assemble the ADR-009 `{key,label}` shape for choice answers — never touch any other key on `req.body.answers` (AC: #1, #3)
- [ ] Validate identity fields (`firstName`, `email`, `postcode`, `heardAbout`, `groupChoice`) against server-side required/format/length rules independent of the client; return `400 { error }` naming the first invalid field (AC: #1, #3)
- [ ] Fetch the current published `form_config_versions` row (service-role read) and extract `consent_text`/`consent_version` per purpose actually being presented (`hold_data`, `newsletter`, and `publish_listing` only if `wantsListing`) (AC: #2)
- [ ] Assemble the `submit_membership()` call arguments strictly from the values built above — no destructuring/spread of `req.body` anywhere near the call (AC: #1, #2)
- [ ] Call `submit_membership()` through the service-role client; on success return `200 { ok: true }`; on thrown error return `{ error }` + status, logging only the returned member/submission id or the string `'submit failed'` with **no** identifying field (AC: #4, #5, #7)

## Dev Notes

<!-- LOCKED. Concrete guidance compiled from the planning docs WITH SOURCE CITATIONS.
     Cite every fact: [Source: prd.md#anchor] / [Source: architecture.md#anchor]. Own inferences: [Inference]. -->

- **This is the endpoint ADR-004 and the Submission Service component describe.** *"`POST /api/join/submit` is the only public write endpoint. The handler builds the row set field by field from an allowlist. The request body is never spread into an insert. Any field the server did not ask for … is ignored, not rejected, so a probing client learns nothing."* [Source: architecture.md#adr-004-one-trusted-server-write-path-the-browser-never-writes-member-data]; component contract at [Source: architecture.md#component-submission-service-post-apijoinsubmit].
- **The allowlist mapping, explicitly — copy this shape, never this anti-pattern:**
  ```js
  // NEVER DO THIS — spreads the client's body straight into a write:
  // await supabase.rpc('submit_membership', { ...req.body })

  // DO THIS — every field is named, one at a time, from a known source:
  const answers = {}
  for (const q of questionRegistry) {
    const raw = req.body?.answers?.[q.key]
    if (raw === undefined) continue
    answers[q.key] = mapAnswerForKey(q, raw)   // validates type/maxLength; shapes {key,label} per ADR-009
  }
  const identity = {
    first_name:   requireString(req.body?.firstName, { max: 100 }),
    email:        requireEmail(req.body?.email),
    postcode:     requireString(req.body?.postcode, { max: 20 }),
    heard_about:  optionalString(req.body?.heardAbout, { max: 200 }),
    group_choice: requireOneOf(req.body?.groupChoice, ['business_mums', 'career_mums', 'both']),
  }
  ```
  Nothing else on `req.body` is ever read into a variable that reaches the database. [Inference — exact helper names; the allowlist principle itself is LOCKED per ADR-004.]
- **No auth block on this route — do not copy `api/admin/subscribers.js`'s bearer-token check here.** That pattern is for `/api/admin/*` routes verifying a Supabase session [Source: architecture.md#adr-003-authn-via-supabase-auth-authz-is-binary-with-attribution-instead-of-tiers]. `POST /api/join/submit` is deliberately the **one** public, unauthenticated write path [Source: architecture.md#adr-004-one-trusted-server-write-path-the-browser-never-writes-member-data]. Its error-shape and try/catch convention *is* copied from the same file family: `{ error: string }` + status, whole handler in try/catch, matching `api/subscribe.js`'s pattern and explicitly not `api/admin/users.js`'s (which 500s with HTML on an empty body) [Source: inputs/codebase-constraints-brief.md#3-the-publicprivate-boundary--how-it-is-actually-enforced].
- **Do not repeat `api/subscribe.js`'s logging mistake.** It currently does `console.error('[subscribe] conflict on', email, …)` — a real email address into Vercel logs [Source: architecture.md#adr-004-one-trusted-server-write-path-the-browser-never-writes-member-data]; also flagged as named risk 6 [Source: inputs/codebase-constraints-brief.md#8-named-risks-for-a-public-write-endpoint-on-this-stack]. This story's handler logs **the record id only**, never any field named in FR-005's list (name, email, phone, postcode) [Source: prd.md#FR-005].
- **Error/status codes:** `200` ok · `400` validation · `409` form closed · `429` rate-limited (4.3, not this story) · `403` bad origin (4.3, not this story) · `500` unexpected — the full status vocabulary is fixed at [Source: architecture.md#6-api-specifications].
- **Non-disclosure applies to the shape returned, from day one of this story.** *"the submit endpoint returns the same success shape for a genuine submission, a duplicate email (FR-007) and a honeypot-caught bot (FR-006)"* [Source: architecture.md#adr-005-error-and-response-convention]. This story only produces the genuine-success and validation-failure branches; 4.3 and 4.4 must slot their branches into the *same* `200 { ok: true }` shape this story establishes, not invent a second one.
- **Consent text source.** `form_config_versions` holds "a `jsonb` snapshot of the whole resolved config" [Source: architecture.md#adr-008-form-configuration-code-defined-registry-database-overlay-and-versioned-publish]; this story's handler reads the row marked current/published and extracts the purpose-keyed consent text from it, passing it into `submit_membership()`'s `p_consents` argument (see 4.1's Dev Notes for the exact parameter shape this story must match).
- **Registry dependency.** `src/lib/join/questions.js` is owned by story **2.1**; this story reads it but never edits it (per the collision map) [Source: context/sharding-context.md#owned-filemodule-scope--the-collision-map].
- **FR coverage:** FR-005 (single trusted write path, allowlist, JSON errors, no PII in logs) [Source: prd.md#FR-005]; FR-004's server half (consent text/version/timestamp/method assigned server-side) [Source: prd.md#FR-004]; FR-009's closed-form rejection [Source: prd.md#FR-009]; FR-006's server-side length rejection (the mechanics live here; 4.3 additionally logs it as an abuse event) [Source: prd.md#FR-006].

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. NEVER run tests or quote coverage here. -->

- **Approach:** integration-style verification against a preview deployment (no unit test runner exists in this repo [Source: inputs/codebase-constraints-brief.md#1-stack--deployment-reality-non-negotiable]) — scripted `fetch`/`curl` requests exercising the handler end-to-end against real (throwaway) rows, matching how NFR-001/003 are measured elsewhere [Source: architecture.md#7-fr--nfr-coverage-matrix].
- **Key scenarios:** (a) a fully valid payload → `200 { ok: true }` and the four expected rows exist; (b) a payload with extra fields (`status: 'published'`, `id: '<uuid>'`, a fabricated `consentVersion`) → those fields have zero effect on the written rows; (c) a payload missing a required field → `400`, zero rows written; (d) a free-text answer over its `maxLength` → `400`, zero rows written; (e) the form closed → `409`, zero rows written; (f) a forced Postgres error (e.g. temporarily break the RPC name) → non-2xx JSON, never an HTML body.
- **Per-AC verification:** AC #1 → inspect the written `directory_listings`/`members` rows after sending a payload with disallowed extra keys and confirm they are absent/ignored; AC #2 → confirm `member_consents.consent_text`/`consent_version` match the published config, not anything sent in the request; AC #3 → missing-field and over-length cases both return 400 with zero writes; AC #4 → response body is byte-for-byte `{ ok: true }` with `200`; AC #5 → force a throw and confirm JSON, not HTML; AC #6 → toggle `form_settings.is_open` and confirm `409`; AC #7 → grep captured log output for any of the submitted PII values and confirm absence.
- **Fixtures/mocks:** a minimal valid payload built from the 2.1 registry; a copy with extra/forbidden keys; a copy with an over-long free-text answer; a copy with a missing required field. A test-only published `form_config_versions` row (or the seeded one from 1.3) to resolve consent text against.
- **Edge cases:** empty body; non-JSON body; wrong `Content-Type`; `answers` present but not an object; a question key in the payload that does not exist in the registry at all (must be ignored, not error).
