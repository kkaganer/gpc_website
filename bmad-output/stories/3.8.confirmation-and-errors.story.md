# 3.8: Confirmation and submission-time errors

**Story ID:** 3.8
**Epic:** 3 — The public form
**Slug:** confirmation-and-errors
**Status:** ready-for-dev

## Story

As a **member who has just pressed Submit**,
I want **a confirmation that reflects exactly what I told the form, or — if something went wrong
— a clear reason and my answers still intact**,
so that **I always know whether I'm done, and I never lose 25 answers to a network blip or a
server error**.

## Acceptance Criteria

<!-- LOCKED. External dev tools must not edit Acceptance Criteria. -->

1. Given `POST /api/join/submit` returns 2xx, when the confirmation renders, then every value
   shown — the first name in the heading, the listing "pending review" block, and the "what you
   agreed to" recap — is taken **from the request payload the client just sent**, never from a
   server response body or a subsequent read of stored records; the `<form>` is **replaced**, not
   merely followed, by this screen.
2. Given the response is a duplicate-email success, or a honeypot-triggered success, then the
   member sees the **identical** confirmation screen as a genuine first submission — no
   distinguishing copy, no different heading, no extra state.
3. Given the request fails for any reason (network failure, 4xx, 5xx, or a non-JSON body), when
   the failure is handled, then the form and every value the member typed **remain on screen and
   remain editable** — nothing is cleared, nothing is disabled — and exactly one error banner
   renders in the same `ErrorSummary`-shaped slot above Submit, matching the failure to one of:
   validation (400), network, rate-limited (429), server (5xx / bad JSON), or form-closed (409).
4. Given a 429 rate-limit response, when the error renders, then it shows a countdown to retry
   that updates only at 60s/30s/10s/ready — never once per second — and never implies the member
   is suspected of being a bot.
5. Given a 409 form-closed response arrives mid-session, then the page is replaced by the closed
   state (3.2's `ClosedNotice`) with a leading, focused alert stating nothing was saved.
6. Given the member double-taps Submit or retries after a failed attempt, then the same
   client-generated idempotency key is reused on every attempt in that session, so a retry can
   never create a second member record.

## Dev Notes

<!-- LOCKED. Concrete guidance compiled from the planning docs WITH SOURCE CITATIONS. -->

- **Adjudication A2 is the exact ruling this story implements — apply it verbatim:** *"The
  confirmation screen is rendered from the request payload the client sent, never from the
  database result. The 'what you agreed to' recap echoes what the member submitted... this is a
  security property, not a preference. Rendering from stored records tells a honeypot-caught bot
  it was caught (no records exist), and tells a duplicate submitter that their email was already
  registered — breaking FR-006 and FR-007's non-disclosure rule."*
  [Source: ux-drafts/ADJUDICATIONS.md#a2-confirmation-rendered-from-payload-not-stored-records]
- **The same rule stated by the API contract:** *"the confirmation UI renders from the **request
  payload**, never from a server echo of stored records... otherwise the non-disclosure rule is
  defeated at the presentation layer."* And: *"`200 { ok: true }` — the same response for a
  genuine submission, a duplicate email, and a honeypot catch."*
  [Source: architecture.md#adr-005-error-and-response-convention]
  [Source: architecture.md#6-api-specifications — `POST /api/join/submit`]
- **FR-001, FR-006, FR-007 acceptance criteria this story must satisfy:** the form is *replaced*
  by a confirmation state naming what happens next; a rejected submission (honeypot) still
  returns an ordinary success response with no moderation task created; a duplicate submitter
  "sees the ordinary confirmation state — the response never reveals whether the email was
  already registered." [Source: prd.md#FR-001] [Source: prd.md#FR-006] [Source: prd.md#FR-007]
- **Screen S5/D-4 content, verbatim, tailored by `{ listingRequested, newsletterConsented,
  group }` taken from the outgoing payload:**
  - `<h1 tabindex="-1">` "You're in, Bea." (or Carla's name) — **focus lands here**.
  - Listing block (only if `listingRequested`): status pill `Pending`; *"Your listing isn't live
    yet — and that's normal. A GPC admin reads every listing before it goes on the site."*; a
    real `<ol>` — (1) *"We check it — we usually review new listings within a week."* (2) *"If
    it's all fine, we publish it and email you the link."* (3) *"If something needs changing,
    we'll email and explain how to fix it."*; closing line *"Nothing about your listing is public
    until then."*
  - "What you agreed to" block: lines in **words** ("you said yes"/"you said no"), not glyphs
    alone — hold-my-data, publish-my-listing (only if requested), newsletter — echoing exactly
    what was ticked in the outgoing payload, sourced from 3.6's consent state, not re-derived.
  - Buttons: `Browse the directory` (primary), `See what's on` (outline).
  - Carla's variant (no listing requested): list becomes (1) *"We've added you to the GPC Mums in
    Business & Work community."* (2) *"We use your answers to plan events people can actually
    come to — that's the whole reason we asked."* (3) *"Watch out for our next event."*; buttons
    become `See what's on` / `Back to home`. **There is no generic "thanks!" fallback** — every
    member sees a list describing *her* submission.
  [Source: EXPERIENCE.md#1-joining--the-public-form — Screen S5 wireframe and "Carla's variant"]
  [Source: EXPERIENCE.md#2-the-directory-opt-in-and-consent — Screen D-4 wireframe]
- **A9 — one confirmation, one timeframe, never the internal metric:** the member-facing wording
  is exactly **"We usually review new listings within a week"**, appearing in both D-2 (3.5, pre-
  submit) and here — never phrased differently, and never "within 5 working days" (that figure is
  an internal median success-metric target, not a promise made to a member).
  [Source: ux-drafts/ADJUDICATIONS.md#a9-one-confirmation-screen-and-no-delivery-promise]
- **First name comes from in-memory client state only** — never a URL parameter, query string, or
  route segment, so it appears in no shareable link, referrer, analytics path, or history entry.
  If a future build ever needs this screen to survive a reload, it must re-render the generic
  "You're in." rather than persist the name anywhere URL-addressable. Back-button: the route
  stays `/join`, so pressing Back leaves the page rather than returning to a filled-in form — the
  idempotency key (AC #6) is what makes an accidental duplicate resubmission harmless, not a
  reason to invite one. [Source: EXPERIENCE.md#1-joining--the-public-form — Screen S5
  accessibility notes]
- **Focus and announcement order, exact:** the polite live region (3.1a's `useLiveRegion`)
  announces the outcome first — *"Your answers have been sent. Your directory listing is with us
  for review."* — then, ~100ms **after**, focus moves to the `<h1 tabindex="-1">`. Live region
  gives the outcome; focus gives navigable position; in that order. No confetti in either motion
  mode — a full-screen particle effect after handling personal data reads as flippant.
  [Source: EXPERIENCE.md#1-joining--the-public-form — Screen S5 states table, accessibility
  notes]
- **Idempotency key (A19, D5):** the client generates one key per form session and sends it with
  every attempt; retries reuse it. *"This is what makes S6's retry copy true rather than merely
  reassuring."* The key's server-side handling (Epic 4) is out of this story's scope — this story
  only owns generating it once and sending it unchanged on every retry.
  [Source: ux-drafts/ADJUDICATIONS.md#a19-idempotency-key-on-submission]
  [Source: EXPERIENCE.md#1-joining--the-public-form — "D5"]
- **Error-state copy table, verbatim, keyed by failure kind (all render in the same `ErrorSummary`
  slot 3.7 built, above Submit):**

  | Kind | Trigger | Heading + body | Action |
  |---|---|---|---|
  | validation (server, 400) | server rejected a field | same shape as client validation; unmapped server field keys fall back to *"Something in this answer isn't accepted. Please shorten or simplify it."* | same as client validation |
  | network | `fetch` rejected or no response | *"We couldn't reach GPC just now"* / *"Your answers are still here. Check your connection and try again — nothing has been lost."* | `Try again` re-posts with the **same** idempotency key |
  | rate_limited (429) | FR-006 threshold exceeded | *"Just a moment"* / *"You've sent this a few times in a row. Please wait a moment and try again. Your answers are still here."* **Never** "you look like a bot" | `Try again in 47s`, counting down, announced only at 60s/30s/10s/ready |
  | server (5xx, or non-JSON body) | any other non-2xx, or `res.json()` threw | *"Something went wrong at our end"* / *"That's our fault, not yours. Your answers are still here — please try again in a moment. If it keeps happening, email gpc.communitynews@gmail.com."* | `Try again` |
  | form_closed (409) | admin closed the form mid-session | page **replaced** by `ClosedNotice` (3.2) with a leading, focused alert: *"Sorry — sign-ups closed while you were filling this in. Nothing was saved."* | `Back to home` |

  **Duplicate submission has no error state and must never gain one** — FR-007 requires the
  response never reveal registration status; a duplicate renders the success screen identically
  to a first submission (AC #2). [Source: EXPERIENCE.md#1-joining--the-public-form — Screen S6
  error-kind table]
- **The universal recovery rule:** *"the form and every answer in it stay on screen and stay
  editable. Nothing is cleared, nothing is disabled, no field loses its value. Only two things
  change — an alert appears above Submit, and Submit becomes actionable again."*
  [Source: EXPERIENCE.md#1-joining--the-public-form — Screen S6 "Universal rule"]
- **Double-submit guard, exact:** Submit enters `loading` — label becomes "Sending…",
  `aria-busy`, `aria-disabled` (never the native `disabled` attribute — the button must stay
  focusable), pointer-inert. D5's idempotency key is what makes a genuine double-post harmless
  even if the guard is somehow bypassed. **Fields are never disabled while sending** — if the
  request fails, the member needs them editable and focusable immediately.
  [Source: EXPERIENCE.md#1-joining--the-public-form — Journey J1 states table; Screen S5 "Loading"
  state row]
- **Error object shape from the server, per ADR-005:** every non-2xx response is `{ error: string
  }` plus an HTTP status — `400` validation, `403` bad origin, `409` form closed, `429`
  rate-limited, `500` unexpected. Parse defensively: `await res.json().catch(() => ({}))`, the
  pattern already used by `NewsletterBanner.jsx`. [Source: architecture.md#adr-005-error-and-
  response-convention] [Source: architecture.md#6-api-specifications]
  [Source: inputs/codebase-constraints-brief.md#4]
- **This story's boundary with Epic 4:** `POST /api/join/submit` itself (the endpoint, its
  allowlist mapping, the anti-abuse layers, and the actual transaction) is Epic 4's build,
  currently out of scope for Epic 3. This story implements the **client-side** call, its
  success/failure branching, and every screen state — against a stubbed/mocked endpoint until
  Epic 4 ships. [Source: epics.md#epic-3-the-public-form — "Out of scope: the server write path
  and anti-abuse (Epic 4)."] [Source: epics.md#epic-4-submission-pipeline]

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify per AC, test types, fixtures, edge cases. -->

- **Approach:** component tests for `SubmissionSuccess` rendering purely from injected payload
  props (no fetch involved), integration tests for the submit handler against a mocked
  `POST /api/join/submit` covering each response kind in the table above, and a manual pass
  confirming the announce-then-focus order and the rate-limit countdown's throttled schedule.
- **Key scenarios:** a 2xx response with `listingRequested: true` renders the pending-listing
  block with Bea's copy; a 2xx with `listingRequested: false` renders Carla's shorter variant; a
  simulated duplicate-shaped 2xx renders byte-identical output to a first-submission 2xx (same
  props in, same DOM out — the mock never differs, which is the point); each of the five non-2xx
  kinds renders its exact copy and action; a second click on Submit while a request is in flight
  produces no second network call; a retry after a network failure reuses the same idempotency
  key value captured before the failure.
- **Per-AC verification:** AC #1 → mock a 2xx response with an arbitrary/differing server body and
  assert the rendered confirmation matches the **request** payload's values, not the mock
  response's; AC #2 → run the same test with the mock 2xx tagged (in the test only, never exposed
  to the component) as "duplicate" and "honeypot" and assert identical rendered output to the
  genuine case; AC #3 → mock each non-2xx status and assert every previously-typed field value is
  still present in the DOM and still editable (not `disabled`), and assert exactly one error
  region renders; AC #4 → mock 429 and fast-forward the countdown, asserting the live region
  announces only at the 60/30/10/ready marks, not every second; AC #5 → mock 409 and assert
  `ClosedNotice` replaces the page with a `tabindex="-1"` focused alert; AC #6 → capture the
  idempotency key value on first submit, force a network failure, retry, and assert the second
  request's key is identical to the first.
- **Fixtures / mocks:** a mock `fetch`/`POST /api/join/submit` returning each of: 2xx, 400 (with
  a mapped and an unmapped field key), 403, 409, 429, 500, and a non-JSON body — this story is
  explicitly built against a stub since Epic 4 owns the real endpoint.
- **Edge cases to cover:** a 2xx response body that is missing or malformed (the confirmation must
  still render correctly since it never reads the response body for content, only for the 2xx/
  non-2xx branch); a fetch that resolves with a non-JSON body on a *success* status (defensive
  parsing must not crash the success path either); rapid retry-spam after a 429 before the
  countdown reaches zero (the retry action must stay inert until `ready`).

## Learnings from Previous Stories

- 3.7 built `ErrorSummary` to accept an externally-supplied error map, not only its own
  client-computed one, specifically so this story could route server/network-originated errors
  through the same component without a second one — use that seam rather than building a
  parallel banner. (from 3.7)
- 3.2 built `ClosedNotice` as a mountable component (not only a route-level state) precisely so
  this story's 409 mid-session transition could reuse it — mount it directly rather than
  duplicating its copy/markup. (from 3.2)
- 3.1a's `Button` `loading` state (spinner + "Sending…" + `aria-busy`/`aria-disabled`, never the
  native `disabled` attribute) is exactly this story's double-submit guard — consume it rather
  than reimplementing a busy state on Submit. (from 3.1a)
