# 3.1b: Form primitives — choice controls and the character counter

**Story ID:** 3.1b
**Epic:** 3 — The public form
**Slug:** form-primitives
**Status:** ready-for-dev

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.
> **Split notice:** second half of the assigned story 3.1 (`form-primitives`). Ships the
> grouped-choice primitives (`RadioGroup`, `Checkbox`, `ChoiceChipGroup`) and the
> `CharacterCounter`, all of which announce through 3.1a's shared `LiveRegion`.

## Story

As a **developer building any `/join` form section that asks a choice question**,
I want **shared, accessible `fieldset`/`legend`-grouped radio, checkbox and chip controls, and a
throttled character counter**,
so that **every choice question on `/join` (group choice, event types, business "looking for",
career situation, consent) shares one correct ARIA and keyboard contract instead of five
divergent hand-rolled ones**.

## Acceptance Criteria

<!-- LOCKED. External dev tools must not edit Acceptance Criteria. -->

1. A `RadioGroup` component renders a `<fieldset>` with a `<legend>` carrying the question text
   and a set of native radio inputs (default row style, or a `variant="card"` style with a 2px
   border, `--radius-2xl`, and a check icon on selection). Selecting an option is single-select
   by construction (native radio semantics); arrow keys move and select.
2. A `Checkbox` component renders one labelled checkbox with a ≥44×44px hit area (achieved via
   label padding, not a shrunk visual control), a 24×24px visual control, and a focus-visible
   outline on the control itself.
3. A `ChoiceChipGroup` component renders a `<fieldset>`/`<legend>`-grouped set of real checkboxes
   styled as chips (the chip is the `<label>`), does not change a chip's width when it becomes
   selected, and exposes the count of selected chips to its caller so the caller can report it
   through 3.1a's shared live region.
4. Given a `RadioGroup` or `ChoiceChipGroup` has more than 8 options, when it renders, then the
   group carries an internal `role="group"` and the group's error (if any) attaches to the
   `<fieldset>` via `aria-describedby` — never to an individual option.
5. A `CharacterCounter` component computes remaining/over characters against a passed `limit`,
   switches to `--color-warning` inside 30 characters remaining and `--color-error` when over
   the limit, and announces through 3.1a's `useLiveRegion()` throttled to at most one
   announcement per 1.5 seconds — never on every keystroke.

## Dev Notes

<!-- LOCKED. Concrete guidance compiled from the planning docs WITH SOURCE CITATIONS. -->

- **Control geometry, verbatim:** control size 24×24px visual; hit area **44×44px minimum**
  achieved by label padding; unselected border 2px `--color-border`; selected fill
  `--color-primary-700` with a white check/dot; focus-visible ring 2px `--color-dark`, 2px
  offset, **on the control**; checkbox radius `--radius-lg` (8px), radio radius `--radius-full`;
  ≥8px gap between adjacent options. [Source: DESIGN.md#2.5-checkbox-radio]
- **Card-style radio** (used for the group choice in 3.2/3.3 and other high-stakes single
  choices): the whole row is the tap target — 2px border, `--radius-2xl`, 16px padding; selected
  state is `--color-primary-700` border **plus** `--color-primary-100` fill **plus** a check
  icon — never fill alone, because colour must not be the sole carrier of state (WCAG 1.4.1).
  [Source: DESIGN.md#2.5-checkbox-radio]
- **Grouping is mandatory, not optional:** every group is a `<fieldset>` with a `<legend>`
  carrying the full question text, so a screen reader announces e.g. "Which group would you like
  to join? Business Mums, radio button, 1 of 3." Groups with >8 options additionally get an
  internal `role="group"`. [Source: DESIGN.md#2.5-checkbox-radio]
- **Multi- vs single-select must be stated in the legend** — multi-select groups say "Choose as
  many as you like"; single-select groups say "Choose one". This is copy the consuming section
  supplies, not something `RadioGroup`/`ChoiceChipGroup` hard-codes, but the component must
  render whatever hint text is passed adjacent to the legend. **A concrete defect this
  component's existence fixes:** the source form's "How often would you like events?" is
  currently a checkbox group that wrongly permits "Weekly + Quarterly" simultaneously — the
  question is corrected to a single-select `RadioGroup` in the question registry (owned by Epic
  2 story 2.1), not by anything in this story, but this story's `RadioGroup` is what makes that
  fix renderable. [Source: DESIGN.md#2.5-checkbox-radio]
- **Chips must not change width on selection.** A wrapping chip group that reflows on every tap
  is unusable one-handed — this is a **layout** rule, not a motion rule, and applies regardless
  of the reduced-motion setting. [Source: EXPERIENCE.md#1-joining--the-public-form — Screen S3
  accessibility notes]
- **Error attachment for groups:** chip-group and matrix-style errors attach to the `<fieldset>`
  via `aria-describedby` — **never** to individual options/cells. One control (the fieldset), one
  error. [Source: EXPERIENCE.md#1-joining--the-public-form — Screen S3 states table]
- **`ChoiceChipGroup`'s count is reported by the caller, not announced by the component itself** —
  this story's components must not call `useLiveRegion().announce()` directly for routine
  selection changes (that would violate the one-shared-region throttling contract owned
  end-to-end by consuming sections); instead `ChoiceChipGroup` exposes the current selected count
  as a value/callback so callers (3.3's B6 "looking for", 3.4's event types) decide when and how
  to announce it, consistent with D7's single shared region.
  [Source: EXPERIENCE.md#1-joining--the-public-form — "D7 — one polite region, one alert region"]
- **`CharacterCounter` copy convention** (used verbatim by 3.5's description field): counts down
  as `"{N} characters left"`, then `"0 characters left"`, then `"{N} characters over the limit"`.
  Neutral tone to 31 remaining, `--color-warning` from 30 remaining, `--color-error` past the
  limit. **Never truncates; never blocks typing** — over-limit is a validation error at submit
  time, not an input constraint. Throttled to at most one live-region announcement every 1.5s,
  and stays silent until fewer than 30 characters remain (an un-throttled counter on a
  300-character field is a screen-reader denial of service).
  [Source: EXPERIENCE.md#2-the-directory-opt-in-and-consent — "Counter" note under Screen D-2]
  [Source: DESIGN.md#2.4-text-input-textarea-select — "Character-limited" state]
- **Keyboard behaviour is intentionally native**, not a custom widget: arrowing within a
  `RadioGroup` moves **and selects** (native radio behaviour) — a later story (3.3) relies on
  this exact behaviour to trigger its discard-confirmation dialog on a single key press, and
  "fixing" it to arrow-without-select would break that contract. Do not build a custom
  `role="radiogroup"` listbox. [Source: EXPERIENCE.md#1-joining--the-public-form — Screen S2
  accessibility notes]
- **Do not build a `role="grid"` day/time matrix here.** The 21-slot day/time control (3.4) is a
  distinct, purpose-built component using plain checkboxes, not `RadioGroup`/`ChoiceChipGroup`
  reused wholesale — it is out of this story's scope; 3.4 may still reuse `Checkbox` internals if
  convenient but owns its own matrix component. [Inference — the matrix's row/column toggle
  behaviour and disabled-when-flexible state do not fit either primitive's contract cleanly, and
  EXPERIENCE.md specifies it as its own component `DayTimeMatrix`.]
- **No new runtime dependency.** [Source: architecture.md#adr-007-client-state]
  [Source: prd.md#NFR-012]

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify per AC, test types, fixtures, edge cases. -->

- **Approach:** component-level tests plus a manual keyboard/AT smoke pass (arrow-key selection,
  chip tap targets at 320px, screen-reader announcement of the legend + option count).
- **Key scenarios:** `RadioGroup` (default and card variants) exposes correct
  `fieldset`/`legend`/`radio` roles and single-select behaviour; `Checkbox` hit area measures
  ≥44×44px including label padding; `ChoiceChipGroup` reports the correct selected count on
  toggle and does not resize a chip on selection; `CharacterCounter` throttles announcements and
  switches colour class at the 30-remaining and over-limit thresholds.
- **Per-AC verification:** AC #1 → render `RadioGroup` with 3 options, simulate arrow-key
  navigation, assert exactly one radio is checked at any time; AC #2 → measure the rendered
  `Checkbox` label's bounding box in a DOM test or note it for the manual touch-target pass; AC
  #3 → toggle 2 of 5 chips and assert the reported count is 2, and assert computed chip width is
  unchanged before/after; AC #4 → render a 12-option group with an error and assert the error id
  is only in the fieldset's `aria-describedby`, not on any individual input; AC #5 → simulate
  rapid keystrokes and assert the live-region text updates at most once per 1.5s window, and
  assert the colour class transitions at 300→31 (neutral), 30→1 (warning), 0 and below (error).
- **Fixtures / mocks:** none — no network dependency.
- **Edge cases to cover:** a `ChoiceChipGroup` with zero options (renders an empty fieldset, does
  not throw); a `CharacterCounter` with `limit=0`; rapid selection toggling on a chip group to
  confirm no dropped or duplicated DOM nodes.

## Learnings from Previous Stories

- 3.1a establishes `useLiveRegion()` as the single announcement channel and `FormField`'s
  above-input helper-text convention — this story's components should match that visual rhythm
  (label → helper → control → error) rather than introduce a second convention. (from 3.1a)
- 3.1a flags that DESIGN.md §2.4's "error containers carry `role=alert`" is **overridden** by
  adjudication A13 for per-field errors; the same override applies here — group errors are
  `aria-describedby` text on the `<fieldset>`, not their own alert region. (from 3.1a)
