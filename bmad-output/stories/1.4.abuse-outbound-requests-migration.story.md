# 1.4: Abuse, outbound email and data-rights migration — sweep + erase_member()

**Story ID:** 1.4
**Epic:** 1 — Data foundation
**Slug:** abuse-outbound-requests-migration
**Status:** ready-for-dev

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As **the data controller**,
I want **the tables and functions that record abuse attempts, queue outbound email, track data-subject requests, and erase a member's data completely on request**,
so that **the anti-abuse layers (Epic 4), the moderation notification queue (Epic 5) and the data-rights journey (Epic 8) have somewhere durable to write to, and a member's erasure request removes every trace of them in one atomic, auditable action**.

## Acceptance Criteria

3. 4. 5. Given `anon` or `authenticated` attempts to call `erase_member(...)` or `sweep_abuse_events(...)` directly, when the call executes, then it is rejected — `EXECUTE` is granted to `service_role` only on both.
6. Given migration `031_abuse_and_outbound.sql` is applied a second time, when `supabase db push` executes, then it completes with no error.

### `abuse_events` and the sweep

Four anti-abuse layers run inside `POST /api/join/submit` in this order: origin check → honeypot → Postgres rate limit on a **salted SHA-256 hash of the client IP** → server-side length limits. `abuse_events` is the third layer's storage and the source for the FR-006 "abuse blocked" admin counter [Source: architecture.md#adr-011-anti-abuse-in-postgres-and-the-request-handler--no-new-third-party-processor]. **The raw IP is never stored or logged** — only the hash [Source: architecture.md#adr-011-anti-abuse-in-postgres-and-the-request-handler--no-new-third-party-processor].

```sql
create table if not exists abuse_events (
  id         uuid primary key default gen_random_uuid(),
  ip_hash    text not null,
  reason     text not null check (reason in ('honeypot','rate_limit','origin','length')),
  created_at timestamptz not null default now()
);

create index if not exists abuse_events_ip_hash_created_at_idx
  on abuse_events (ip_hash, created_at desc);

alter table abuse_events enable row level security;
-- No anon policy, no authenticated policy — written by the submission service
-- (Epic 4) via service-role, read by GET /api/admin/abuse-summary (Epic 2.7).
```
Columns and `reason` vocabulary are verbatim from ADR-011 [Source: architecture.md#adr-011-anti-abuse-in-postgres-and-the-request-handler--no-new-third-party-processor]; the supporting index is not specified in the source but is necessary for the rate-limit query (3/hour, 20/24h per `ip_hash`) to be efficient rather than a full table scan on every submission [Inference].

"Rows are swept after 48 hours" [Source: architecture.md#adr-011-anti-abuse-in-postgres-and-the-request-handler--no-new-third-party-processor], and there is **no cron** anywhere in this deployment (`vercel.json` has no scheduled functions) [Source: architecture.md#10-deployment-architecture]. This migration therefore only creates the sweep as a **callable function**, following the existing `dedupe_london_events(p_dry_run boolean default true)` precedent of defaulting destructive functions to a dry run [Source: inputs/codebase-constraints-brief.md#2-data-layer-conventions-a-new-migration-must-follow-these-exactly]. Wiring it into an automated schedule is out of scope for this story and for this release — `FR-D08`, an automated retention sweep, is explicitly deferred [Source: architecture.md#adr-015-erasure-and-withdrawal-run-through-one-security-definer-function].

```sql
create or replace function sweep_abuse_events(p_dry_run boolean default true)
returns integer
language plpgsql
as $$
declare
  v_count integer;
begin
  if p_dry_run then
    select count(*) into v_count
    from abuse_events
    where created_at < now() - interval '48 hours';
  else
    with deleted as (
      delete from abuse_events
      where created_at < now() - interval '48 hours'
      returning 1
    )
    select count(*) into v_count from deleted;
  end if;
  return v_count;
end;
$$;

revoke execute on function sweep_abuse_events(boolean) from public, anon;
grant execute on function sweep_abuse_events(boolean) to service_role;
```

### `outbound_emails`

```sql
create table if not exists outbound_emails (
  id              uuid primary key default gen_random_uuid(),
  to_member_id    uuid references members(id) on delete cascade,
  template_key    text not null,
  payload         jsonb not null default '{}'::jsonb,
  status          text not null default 'queued'
                    check (status in ('queued','sent','failed','given_up','not_applicable')),
  attempts        integer not null default 0,
  last_error      text,
  last_attempt_at timestamptz,
  sent_at         timestamptz,
  created_at      timestamptz not null default now(),
  updated_at      timestamptz not null default now()
);

create index if not exists outbound_emails_status_idx on outbound_emails (status);

create trigger outbound_emails_set_updated_at
  before update on outbound_emails
  for each row execute function update_updated_at();

alter table outbound_emails enable row level security;
-- No anon policy, no authenticated policy — written in the same transaction as
-- a moderation decision (Epic 5) or a submission (Epic 4), drained by Epic 5.5.
```
Column set and `status` vocabulary are verbatim from ADR-014 [Source: architecture.md#adr-014-outbound-email-is-a-queue-table-drained-by-a-pluggable-sender]. The moderation decision commits regardless of send outcome — the decision and the queue row are one atomic write; the *send* is a separate, later step, never inline in the request handler [Source: architecture.md#adr-014-outbound-email-is-a-queue-table-drained-by-a-pluggable-sender]. `payload jsonb` holds only what the template needs (a listing id, a slug, a reason key) — **no personal data beyond the recipient reference** [Source: architecture.md#adr-014-outbound-email-is-a-queue-table-drained-by-a-pluggable-sender]. The `status` index is not specified in the source but is necessary for Epic 5.5's drain worker to efficiently find `queued` rows [Inference].

### `data_requests`

```sql
create table if not exists data_requests (
  id           uuid primary key default gen_random_uuid(),
  member_id    uuid not null references members(id) on delete cascade,
  kind         text not null check (kind in ('unlist','unsubscribe','erase')),
  requested_at timestamptz not null default now(),
  deadline_on  date not null,
  status       text not null default 'pending'
                 check (status in ('pending','actioned')),
  actioned_by  uuid,
  actioned_at  timestamptz,
  created_at   timestamptz not null default now(),
  updated_at   timestamptz not null default now()
);

create index if not exists data_requests_status_deadline_idx
  on data_requests (status, deadline_on);

create trigger data_requests_set_updated_at
  before update on data_requests
  for each row execute function update_updated_at();

alter table data_requests enable row level security;
-- No anon policy, no authenticated policy — written via POST /api/my-data/request
-- (a signed-token flow, not a raw anon insert) and actioned via /api/admin/data-requests.
```
`member_id`, `kind`, `requested_at`, `deadline_on`, `status`, `actioned_by`, `actioned_at` are named directly in the source; `deadline_on` "is computed as 20 working days from `requested_at`" [Source: architecture.md#adr-015-erasure-and-withdrawal-run-through-one-security-definer-function]. That computation is **not** done in this migration — working-day arithmetic belongs in the application layer (Epic 8's `my-data-request` endpoint), which will pass a computed `deadline_on` value at insert time; this column is a plain `date not null` with no DB-side default or generated-column formula [Inference]. The `status` vocabulary (`pending`/`actioned`) is not enumerated verbatim in the source — architecture.md names the column but not its values. This is the minimal vocabulary that distinguishes "not yet actioned" from "actioned"; "overdue" is a derived state (comparing `deadline_on` to `now()`), not a stored one [Inference]. **Epic 8 must not edit this migration file** if it needs additional status values (e.g. `in_progress`) — it would need a new migration (`032+`), since ownership of `031` is exclusive to this story.

### `erasure_tombstones` and `erase_member()`

FR-023 requires that a full erasure delete the member record, listing and survey answers, keeping "only a minimal non-identifying record of the erasure" [Source: prd.md#FR-023]. ADR-015 names the tombstone's exact two fields: `erased_at` and `request_id` [Source: architecture.md#adr-015-erasure-and-withdrawal-run-through-one-security-definer-function]. This is implemented as its own minimal table, deliberately separate from `data_requests`, so the tombstone survives even if the originating `data_requests` row is itself later removed by an unrelated cascade — `request_id` therefore carries **no foreign key**, on purpose [Inference — the source specifies the two fields but not the table shape; a dedicated minimal table matches "only a minimal non-identifying record" more literally than repurposing a column on a larger table].

```sql
create table if not exists erasure_tombstones (
  id         uuid primary key default gen_random_uuid(),
  request_id uuid,
  erased_at  timestamptz not null default now()
);
-- FK to data_requests.id deliberately omitted: the tombstone must outlive
-- data_requests should that row itself later cascade away for any reason.

alter table erasure_tombstones enable row level security;
-- No anon policy, no authenticated policy.
```

`erase_member()` follows ADR-015's four numbered steps exactly: (1) disable the `member_consents_immutable` trigger for the transaction — the one documented exemption from **1.2**'s append-only guarantee; (2) delete the member — `directory_listings.member_id … on delete cascade` (from **1.1**) removes the listing, so the public page cannot outlive the erasure; (3) write the tombstone; (4) re-enable the trigger [Source: architecture.md#adr-015-erasure-and-withdrawal-run-through-one-security-definer-function].

```sql
create or replace function erase_member(p_member_id uuid, p_request_id uuid default null)
returns void
language plpgsql
security definer
set search_path = public
as $$
begin
  alter table member_consents disable trigger member_consents_immutable;

  delete from members where id = p_member_id;

  insert into erasure_tombstones (request_id) values (p_request_id);

  alter table member_consents enable trigger member_consents_immutable;
end;
$$;

revoke execute on function erase_member(uuid, uuid) from public, anon, authenticated;
grant execute on function erase_member(uuid, uuid) to service_role;
```
The signature takes an optional `p_request_id` beyond ADR-015's illustrative `erase_member(p_member_id uuid)` — the ADR's own step 3 requires the function to write `request_id` into the tombstone, which is only possible if the function receives it [Inference, resolving an apparent gap between the one-argument signature shown and the three-step body the same ADR describes]. **`erase_member` is never granted to `authenticated`** — reachable only through the admin API route, so it cannot be invoked with a stolen anon key or directly from a browser session [Source: architecture.md#adr-015-erasure-and-withdrawal-run-through-one-security-definer-function]. Partial withdrawal (`unlist`, `unsubscribe`) is **not** erasure and does not call this function — those two `kind`s are actioned by Epic 8 appending a `member_consents` row (`publish_listing:false` or `newsletter:false`) and, for `unlist`, setting `directory_listings.status = 'unpublished'` [Source: architecture.md#adr-015-erasure-and-withdrawal-run-through-one-security-definer-function].
