# 8.3b: The outcome page and the "this wasn't me" cancel link

**Story ID:** 8.3b
**Epic:** 8 — Data rights and privacy

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

> see 8.3a's header and the orchestrator summary for the split rationale.

## Story

As **a member who has just asked to unlist, unsubscribe or delete everything, or who wants to
stop a request she didn't mean to make**,
I want **a page that tells me a real date instead of "soon", and a link that can undo an
unintended request before an admin acts on it**,
so that **I can trust the 20-working-day promise, and a moment's misclick isn't irreversible**.

## Acceptance Criteria

<!-- LOCKED. External dev tools must not edit Acceptance Criteria. -->

1. Given `/my-data/done` loads with `{ kind, deadlineOn }` in router state (set by story 8.3a's
   "I'm done for now"), then it renders the matching success variant naming what was requested and
   the concrete `deadlineOn` date — never the word "soon" and never a recomputed date.
2. Given `/my-data/done` loads with no router state and no cancel token in the URL, then it renders
   the empty variant ("There's nothing to show here…") with a link back to `/my-data`, never a
   blank page.
3. Given `/my-data/cancel?t=<token>` loads with a valid, unexpired cancel token whose
   `data_requests` row is still `open`, then the page marks that row `status = 'cancelled'` and
   renders the Cancelled variant: "Nothing has been deleted and nothing has changed."
4. Given `/my-data/cancel?t=<token>` loads for a request an admin has already completed, then no
   row is modified and the page renders the "Too late" variant naming the completion date and the
   direct contact address.
5. Given `/my-data/cancel?t=<token>` loads with an invalid, expired or unresolvable token, then the
   page renders a plain error state directing the member to email the contact address — it never
   silently redirects to `/my-data`'s "expired, try again" flow, because a cancel link and a manage
   link are different token purposes and confusing them would send her down the wrong path.
6. Given any variant of `/my-data/done` that shows a date, then the date is written out in full in
   the page's accessible text (e.g. "Tuesday 15 September 2026") even where the visual shows an
   abbreviated form (e.g. "Tue 15 Sep").

## Dev Notes

<!-- LOCKED. Concrete guidance compiled from the planning docs WITH SOURCE CITATIONS.
     Cite every fact: [Source: prd.md#anchor] / [Source: architecture.md#anchor] /
     [Source: ux-design.md#anchor]. Label your own inferences [Inference]. -->

- **Why a date, not "soon".** "She has no account and cannot check status, so D-5 and the email
  both state a **date** computed from working days, not 'soon'." NFR-005's 20-working-day
  commitment is the number this date is computed from
  [Source: EXPERIENCE.md#7-data-rights-errors-and-edge-cases — §J2 Drop-off];
  [Source: prd.md#NFR-005].
- **D-5 variants, exact copy.** Default success: "We've got it." + what was asked for + "1. An
  admin will action this — usually within a day or two. 2. We'll email you when it's done. 3. It'll
  be done by `<date>` at the very latest." Erasure variant swaps step 3's wording to "It'll all be
  gone by `<date>` at the very latest" and adds "This page is the last one that works from your
  link — it's now used up." Cancelled: heading "Cancelled.", "Nothing has been deleted and nothing
  has changed." Too late: heading "That's already done.", with the contact address
  [Source: EXPERIENCE.md#7-data-rights-errors-and-edge-cases — Screen D-5].
- **The "this wasn't me" link is live until the erase runs, not just until D-5.** "a 'This wasn't
  me — cancel it' email that works until the erase runs" is one of the five identity-model rules
  [Source: EXPERIENCE.md#7-data-rights-errors-and-edge-cases — §7.1, rule 4]; every confirmation
  email (2a unlist, 2b erase) carries this link with the load-bearing line **"This wasn't me —
  cancel it"** [Source: EXPERIENCE.md#7-data-rights-errors-and-edge-cases — §7.2 email copy table].
- **Cancel ≠ Manage.** The cancel token is a distinct `purpose` from the request-centre token this
  epic already defines — reusing the same `purpose: 'manage'` token for cancellation would let a
  60-minute manage-link leak double as a cancel link for a request that might complete long after
  the manage link's own window. Story 8.3a mints the `purpose: 'cancel'` token with a `requestId`
  claim at the moment it creates the `data_requests` row `[Inference — see 8.3a's Dev Notes]`, and
  this story is the token's only consumer.
- **"Too late" is the documented residual risk, not a bug to route around.** "Honest residual
  risk: **a stolen inbox is a completed erasure**, and an attacker with inbox access will delete
  the warning email too." [Source: EXPERIENCE.md#7-data-rights-errors-and-edge-cases — §J2
  Drop-off] The "Too late" copy exists precisely because cancellation cannot always win the race
  against an admin who has already acted — do not attempt to also roll back the admin's action from
  this screen.
- **Full dates in the accessible text.** "Dates are written in full in the accessible text
  (`Tuesday 15 September 2026`) even where the visual shows `Tue 15 Sep`, so they are unambiguous
  when spoken." [Source: EXPERIENCE.md#7-data-rights-errors-and-edge-cases — Screen D-5] Use two
  renderings of the same `Date`/ISO string — a short visual string and a long string in the
  element's accessible name or as visible body text, not merely a `title` attribute (which is not
  reliably announced).
- **Cancelling never rolls back an in-flight admin action.** The cancel handler must be a single
  conditional `UPDATE ... WHERE status = 'open'` (or equivalent guarded transition), never a
  read-then-write in two round trips, so a concurrent admin action and a cancel click cannot race
  into an inconsistent state. `[Inference]` — no source document states the exact SQL shape, but
  the "no orphaned state" discipline is consistent with ADR-002's idempotency requirement for all
  new SQL [Source: architecture.md#adr-002-persistence-conventions].
- **Accessibility floor (NFR-008)** applies: one `<h1>` per state, focus moves to it on arrival,
  `role="alert"` for the error variant with focus moved to it
  [Source: EXPERIENCE.md#7-data-rights-errors-and-edge-cases — Screen D-5 ARIA column];
  [Source: bmad-output/context/sharding-context.md#accessibility-floor-nfr-008--applies-to-every-ui-story].
- **No new dependency.** Date formatting uses the browser's built-in `Intl.DateTimeFormat`; no
  date library is added, consistent with the "no new runtime dependency without a logged decision"
  constraint [Source: prd.md#constraints].

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. NEVER run tests or quote coverage here. -->

- **Approach:** No automated test runner exists in this repo
  [Source: inputs/codebase-constraints-brief.md#1-stack--deployment-reality-non-negotiable].
  Verify `/my-data/done` by navigating with router state set programmatically (dev tools or a
  temporary debug route) for each variant; verify `/my-data/cancel` against seeded `data_requests`
  rows in each status.
- **Key scenarios:** success variant reflects exactly the `kind`/`deadlineOn` handed off from
  8.3a; empty variant never shows a blank page; a cancel on an `open` request flips it to
  `cancelled` and nothing else; a cancel on a `completed` request changes nothing and shows "Too
  late"; a garbage or expired cancel token never silently redirects into the manage-token flow.
- **Per-AC verification:** AC #1 → set router state for each `kind` and confirm the matching
  copy/date renders; AC #2 → load the route with no state/token and confirm the empty variant, not
  a blank `<main>`; AC #3 → seed an `open` request, hit the cancel route, re-query the row and
  confirm `status = 'cancelled'` and nothing else changed; AC #4 → seed a `completed` request, hit
  the cancel route, confirm the row is untouched and the completion date shown matches
  `actioned_at`; AC #5 → hit the cancel route with a tampered/expired token and confirm the error
  copy, not a redirect; AC #6 → inspect the accessible name/text of every rendered date for the
  full weekday-day-month-year form.
- **Fixtures / mocks:** three seeded `data_requests` rows — one `open`, one `cancelled` already,
  one `completed` with an `actioned_at` — plus a valid cancel token for each and one deliberately
  expired token.
- **Edge cases to cover:** two rapid clicks on the same cancel link (e.g. an email client's link
  preview firing the GET/POST twice) must not error on the second attempt — the second call should
  see `status` already `cancelled` and render the same Cancelled outcome, not an error; a cancel
  token whose `data_requests` row has since been deleted entirely (should not happen outside
  erasure, but erasure's own row survives as part of the tombstone reference per ADR-015) is
  treated as "Too late", not a 500.
