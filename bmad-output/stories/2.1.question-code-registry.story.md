# 2.1: Question code registry

**Story ID:** 2.1
**Epic:** 2 — Form configuration
**Slug:** question-code-registry
**Status:** ready-for-dev

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As a **developer implementing the join form, its config API and its admin editor** (all of
Epics 2 and 3),
I want **one code-defined registry of every question — its permanent key, its data type, its
branch membership and its server-enforced validation limit**,
so that **the admin overlay, the public renderer and the submission validator all read from a
single source of structural truth and can never drift apart, per ADR-008's code-registry
layer.**

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. `src/lib/join/questions.js` exports an array with one entry for every question key listed
   in Dev Notes — 28 entries total (11 `always`, 7 `business`, 4 `career`, 6 `listing`) —
   each carrying `key`, `type` (`text | long_text | email | url | single_choice | multi_choice`),
   `branch` (`always | business | career | listing`), and `maxLength` (a number for every
   `text`/`long_text`/`email`/`url` entry, `null` for choice types).
2. Choice-type entries (`single_choice` / `multi_choice`) carry a fixed `options: [{ key }]`
   array matching the counts in Dev Notes, **except** `listing_category`, whose options are
   `null` in the registry because the category taxonomy is owned by `directory_categories`
   (Epic 5) and resolved at render/validate time, never hard-coded here.
3. `event_frequency`'s `type` is `single_choice` (fixes source-form defect 4 — the live form
   renders it as checkboxes, permitting "Weekly + Quarterly" simultaneously) and
   `current_situation`'s `options` array has exactly 10 entries with no key appearing twice
   (fixes source-form defect 3 — "Looking for work" was listed twice).
4. `listing_description`'s `maxLength` is `300` (fixes the source form, which has no cap on
   any field) and is enforced as a **rejection** boundary downstream, never a truncation —
   this story only declares the number; enforcement is Epic 3/4's.
5. An exported pure function `getQuestionsForBranch(groupChoice)`, called with
   `'business_mums' | 'career_mums' | 'both'`, returns exactly the `always`-branch questions
   plus the matching branch question(s) — 18 for `business_mums`, 15 for `career_mums`, 22 for
   `both` (11 always + 7 business + 4 career) — with no key duplicated and no `listing`
   question ever included (listing is reached via the opt-in, not the group branch).
6. The module has zero side effects, no JSX, no network or Supabase import, and no dependency
   on `window`/`document` — it is importable unmodified by a Vercel serverless function
   (`/api`) and by the Vite client bundle.

**Why this file exists and what it does not do.** ADR-008 defines three layers: this code
registry (keys, types, branch membership, validation — structural, never runtime-editable),
a DB overlay (`form_question_config`/`form_options` — labels, help text, required flags,
option labels/order/retirement), and a versioned publish snapshot. "Admins cannot add,
delete, or re-parent questions, and cannot alter branching logic" because there is no table
that could express it — this file is the only place that can.
[Source: architecture.md#adr-008-form-configuration--code-defined-registry-database-overlay-and-versioned-publish]
This story writes **only** the first layer. It does not write the seed migration that
populates `form_question_config`/`form_options` defaults (that is Epic 1 story 1.3), and it
does not write the API that merges this registry with the DB overlay (that is 2.2).

three defect fixes and the FR-003 listing fields added. `type` values used throughout:

Listing-field limits (`listing_business_name` 80, `listing_description` 300,
`listing_website` 200, `listing_instagram` 100, `listing_enquiry_email` 254) are cited, not
inferred: [Source: EXPERIENCE.md#2-the-directory-opt-in-and-consent] the D-2 field table and
adjudication A8 ("Public description exceeds 300 characters"). All other `maxLength` values
are `[Inference]` — no source document states a limit for the identity/branch free-text
fields, and FR-006 requires every free-text field to have a server-side maximum
[Source: prd.md#FR-006 — "Free-text fields enforce maximum lengths server-side"], so a
reasonable value must exist even where undocumented. Flag these as tunable, not load-bearing.

**`day_time_slots` — the 21-slot control plus the escape hatch.** The 21 options are the
cross product of 7 days × {morning, afternoon, evening}; splitting into two questions was
explicitly rejected because it destroys the cross-product signal FR-014's insights view
depends on [Source: EXPERIENCE.md#1-joining--the-public-form — "The 21-checkbox problem" /
"an inner scroll box was also rejected"]. This story additionally registers a 22nd option key,
`flexible`, because "I'm flexible" is presented as one tap that satisfies the required
question without any slot ticked [Source: EXPERIENCE.md#1-joining--the-public-form — Screen
S3 wireframe and its Disabled state row]. **The exact stored shape when `flexible` is chosen
(whether slot answers are cleared or merely excluded from the payload) is Epic 3/4's
concern** — this story only guarantees `flexible` exists as a valid option key so the
registry's option count is stable. [Inference]

**Business branch fields vs. listing fields are deliberately separate keys, not one shared
key.** `EXPERIENCE.md`'s own architecture notes flag this as an unresolved overlap between
FR-002 (which fixes the Business branch at exactly 7 questions, three of them business
name/website/Instagram) and FR-003 (which independently requires the same three fields in the
directory section), and states its own resolution is "an inference, not a stated requirement"
[Source: EXPERIENCE.md#1-joining--the-public-form — "D4 is an inference... Asking twice is
indefensible, and moving the fields would contradict FR-002's explicit seven"]. This registry
follows that resolution: `business_name`/`business_website`/`business_instagram` (branch
`business`, optional, part of the 7) are distinct keys from
`listing_business_name`/`listing_website`/`listing_instagram` (branch `listing`, part of the
FR-003 six). Pre-filling the listing fields from the business answers when both are present
is a client-side UX behaviour for Epic 3, not a registry concern — flagged here so Epic 3
does not invent a merged key that would break FR-002's "exactly 7" acceptance criterion.
[Inference] `architecture.md`'s own illustrative registry snippet uses `business_name` with
`branch: 'listing'`
[Source: architecture.md#adr-008-form-configuration--code-defined-registry-database-overlay-and-versioned-publish],
which is a shape example ("shape only"), not an exhaustive schema — this story's fuller
enumeration takes precedence for actual key names, and the divergence is called out here as
a citation gap for the orchestrator.

**Consent is explicitly NOT a registry entry.** The three consents (`hold_data`,
`publish_listing`, `newsletter`) are governed by ADR-010's `member_consents` table with
server-assigned verbatim text, version and timestamp
[Source: architecture.md#adr-010-consent-records-are-append-only-and-version-bearing-enforced-by-trigger]
— they are not "questions" with a type/branch/maxLength shape and do not belong in this file.

**Categories are explicitly NOT a registry entry.** `listing_category`'s options live in
`directory_categories`, owned by Epic 5, applied immediately, one editor
[Source: architecture.md#adr-008-form-configuration--code-defined-registry-database-overlay-and-versioned-publish
— "Categories are not here... One editor, one home."]. This registry declares the *question*
(key, type, branch) but never a static option list for it.

**Naming.** `snake_case`, permanent once shipped, matching every other identifier in this
codebase [Source: architecture.md#adr-006-naming-conventions]. A key is a stable identifier
the same way a DB column name is — ADR-009 requires every stored choice answer to keep both
`key` and a `label` snapshot, and the `key` it stores is exactly this registry's `key`
[Source: architecture.md#adr-009-answers-store-option-keys-and-a-label-snapshot].

## Testing

- **Approach:** unit-level verification of a pure data module. No test runner is currently
  configured anywhere in this repository (no `vitest`/`jest` config or `*.test.js` file
  exists outside `node_modules`) — introducing one is a new dependency and needs a logged
  decision per NFR-012 [Source: prd.md#NFR-012]. Until/unless that decision is made, verify
  by a throwaway Node script (`node -e "..."` or a scratch file, deleted after use) that
  imports the module and asserts the shapes below; do not commit a test file that depends on
  an uninstalled runner.
- **Key scenarios:** total entry count is 28; per-branch counts are 11/7/4/6; every key is
  unique across the whole array; every `text|long_text|email|url` entry has a numeric
  `maxLength`; every `single_choice|multi_choice` entry (except `listing_category`) has a
  non-empty `options` array with unique option keys; `event_frequency.type ===
  'single_choice'`; `current_situation.options.length === 10`.
- **Per-AC verification:** AC #1 → count and shape assertions above. AC #2 → assert
  `listing_category.options === null` while every other choice entry has options. AC #3 →
  assert the two defect fixes directly (type + de-duplicated array). AC #4 → assert
  `listing_description.maxLength === 300`. AC #5 → call `getQuestionsForBranch` with each of
  the three values and assert result length (18/15/22) and that no `listing`-branch key is
  ever present. AC #6 → static check: no `import` of `react`, `supabase-js`, or any `api/`
  helper anywhere in the file.
- **Fixtures/mocks:** none needed — the module takes no arguments beyond a branch string and
  has no I/O.
- **Edge cases:** `getQuestionsForBranch` called with an unrecognised string should return
  just the `always` questions rather than throw, so a malformed stored `group_choice` on an
  old submission never crashes the admin member-record view that reads it later. [Inference]
